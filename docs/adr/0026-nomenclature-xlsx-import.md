# ADR-0026. Двухэтапный импорт номенклатуры из XLSX

- Status: Accepted
- Date: 2026-11-06
- Related: [ADR-0020](0020-product-types-and-products.md), [ADR-0023](0023-product-defaults-and-task-copy.md), [ADR-0025](0025-cavities-mold-product-task.md)

## Контекст

Исходная номенклатура ПЗП находится в Excel: 474 изделия и 268 ПФ. Файл содержит
технологические поля, заказчика, комментарий и сырьё в свободной форме. Часть рецептов
не имеет однозначных пропорций, а у двух пластиков через `;` пропорции осознанно не заданы.
Нужно загрузить справочники без угадывания данных, показать замечания до записи и поддержать
повторный импорт исправленного файла без удаления уже существующих позиций.

## Решение

1. **`POST /api/nomenclature-import` принимает XLSX и флаг `skipInvalidRows`.** Без блокирующих
   ошибок файл применяется сразу. Если они есть и флаг снят, возвращается `ConfirmationRequired`
   и отчёт, а БД не меняется. Пользователь может скачать CSV-отчёт, выбрать исправленный файл,
   отменить операцию или повторно отправить тот же файл с `skipInvalidRows=true`.
2. **Серверный черновик и токен preview не хранятся.** Повторная отправка файла делает проверку
   и применение одним без состояния между запросами: отчёт не может устареть относительно токена,
   а отмена не требует очистки серверного хранилища.
3. **Блокирующая ошибка и технологическое замечание различаются.** Ошибки обязательных полей,
   чисел, дублей и конфликтов справочников исключают строку. Неоднозначный рецепт не исключает
   изделие: оно сохраняется с пустым рецептом и попадает в отчёт для ручной доработки.
4. **Два разных пластика через `;` импортируются как две строки по 0 %.** Это осознанный маркер
   незаполненных пропорций и неблокирующее замечание. Импорт записывает строки напрямую, не вызывая
   `RecipeRules.Validate`: обычное ручное сохранение по-прежнему требует 0,01…100 % и заставит
   пользователя заменить нули.
5. **Один пластик получает 100 %; краситель — указанный процент и не входит в сумму пластиков.**
   «Без красителя»/«Нет» с пустым или нулевым процентом означает отсутствие красителя. Смеси,
   неполные пары краситель/процент и свободные указания вроде «зависит от заказа» не угадываются.
6. **Upsert выполняется по `Mold.FormId` и `Product.FullArticle` в одной транзакции.** Совпадения
   обновляются и возвращаются из архива; записи, отсутствующие в файле, не удаляются и не
   архивируются. Существующие задания, копии рецептов и циклы не изменяются. Максимум ПФ —
   максимум гнёздовости её строк; `Product.Cavities` сохраняется из собственной строки.
7. **Материалы сопоставляются по типу и имени без учёта регистра.** Предпочтителен материал без
   производителя; если имя встречается один раз, используется оно. При нескольких производителях
   создаётся отдельный материал без производителя, а не произвольный выбор. Новый краситель
   получает `ColorName` из колонки красителя, артикул новых материалов — технический `IMP-*`.
8. **`Product.Comment` — необязательный текст из колонки F**, доступный в DTO и карточке изделия.
   Для явной очистки при редактировании используется `ClearComment`, поскольку `null` в PATCH-подобном
   DTO означает «не менять». XLSX читается через ClosedXML как данные; макросы и внешние связи не выполняются.
9. **Проверка и запись выполняются в одной `Serializable`-транзакции.** Это исключает параллельное
   добавление изделия между проверкой гнёздовости и уменьшением максимума ПФ. HTTP ограничивает исходный
   файл 10 МБ, parser — распакованный размер 100 МБ и 10 000 строк; CSV нейтрализует начальные символы
   формул Excel в значениях отчёта.

## Отвергнутые альтернативы

- **Хранить preview в памяти или БД по токену.** Требует TTL, очистки, защиты от повторного
  применения и разрешения устаревания после правок справочников; повторная загрузка файла проще
  и каждый раз проверяет актуальное состояние.
- **Любой неоднозначный рецепт считать ошибкой строки.** Теряется в остальном корректное изделие,
  хотя пользователь выбрал сохранение таких позиций с пустым рецептом и отчётом.
- **Разрешить нулевые проценты в обычном `RecipeRules`.** Убрало бы понятное ручное исправление
  пропорций и ослабило бы правило редактирования ради одного импортного маркера.
- **Синхронизировать файл и БД как полный снимок.** Удаляло бы или архивировало позиции, которых
  нет в очередном исправленном файле; согласован только upsert без удалений.
- **Выбирать материал только по первому совпадению имени.** При разных производителях это молча
  подставляло бы неправильное сырьё.

## Последствия

- Повторная проверка одного файла может дать новый результат после внешних изменений справочников —
  это намеренное поведение stateless-контракта.
- Нулевые доли видны в рецепте изделия как сумма пластиков ≠ 100 %, но обычное сохранение такого
  рецепта без исправления не пройдёт валидацию.
- CSV формируется на frontend из уже возвращённого отчёта; отдельного серверного файла отчёта нет.
- Импорт меняет только справочники. Для переноса новых умолчаний в старые задания нужна отдельная
  осознанная операция, а не побочный эффект загрузки Excel.
