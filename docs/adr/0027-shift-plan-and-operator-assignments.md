# ADR-0027. Позиционный план смен и интервальные назначения литейщиков

- Status: Accepted
- Date: 2026-11-08
- Related: [ADR-0004](0004-single-role-source-user-role.md), [ADR-0016](0016-task-longer-than-shift.md)

## Контекст

ПЗП требуется отдельная роль старшего смены, который работает только со своей ближайшей
сменой, видит ТПА и задания в режиме чтения и назначает литейщиков. Руководитель должен
планировать старших по датам и интервалам изменяемого справочника смен. При этом прошлые
окна нельзя пересчитывать задним числом, а назначения литейщиков должны сохранять историю
для последующего отчёта PZP-31. Нужны одновременные назначения двух литейщиков на один ТПА,
повторные назначения одного человека и защита от параллельных изменений графика, старших,
состава смены, архивации ТПА и смены роли Operator.

## Решение

1. **`ShiftLead` — самостоятельная роль вне `Adjuster < Manager < Admin`.** Она не входит в
   `AdjusterOrHigher`; новые операции защищены политикой `ShiftLeadOrManagerOrAdmin`. План
   старших находится в семействе `/api/shift-plan` и доступен только Manager/Admin. Работа с
   литейщиками и разрешённое чтение смены находятся в `/api/shift-staffing`; `nearest` и
   `history` — персональные endpoint'ы только ShiftLead. Отдельное frontend-семейство
   `/shift-lead` не использует мобильный UI наладчика и не открывает общие API заданий,
   произвольной истории ТПА и полного справочника персонала.
2. **Позиция графика вместо стабильной смены.** `ShiftPlanItem` содержит `Position`,
   `StartAtUtc`, `EndAtUtc`, `TimeZoneId` и одного необязательного `ShiftLeadId`, но не
   содержит `ShiftId` и FK к справочнику `Shifts`. День без сохранённого `ShiftPlanDay`
   виртуально вычисляется из актуального графика. Сохранённый день — полный snapshot всех
   позиций графика на свою заводскую `ShiftDate`, включая позиции без старшего.
3. **Первый старший материализует весь день; последний очищенный удаляет его.** Назначение
   первого старшего в одной транзакции создаёт день и все позиции. Переназначение до начала
   сохраняет интервалы литейщиков. Очистка старшего при наличии таких интервалов запрещена;
   после очистки последнего старшего пустой день удаляется и снова становится виртуальным.
   Постоянной привязки человека к смене справочника нет.
4. **Синхронизируются только будущие заводские даты.** Сохранение справочника смен и
   синхронизация плана выполняются в одной транзакции для `ShiftDate > factoryToday`.
   Позиции сопоставляются по номеру: лишние будущие позиции удаляются, новые добавляются
   пустыми, окна оставшихся обновляются. Их `Id`, старшие и assignments сохраняются. Дни без
   оставшихся старших удаляются. Сохранённые текущие и прошлые даты не изменяются; виртуальные
   дни продолжают отражать актуальный график.
5. **Состояние и ближайшая смена — чистые функции серверного `now`.** Интервал текущей смены
   полуоткрыт: `StartAtUtc <= now < EndAtUtc`; при `now >= EndAtUtc` смена историческая и
   read-only. Для ShiftLead nearest — текущая, иначе earliest future среди его назначений;
   history — только его собственные завершённые смены. Manager/Admin читают любой сохранённый
   план, но меняют литейщиков только в текущем либо earliest future вхождении той же позиции
   со старшим; старшего меняют только до `StartAtUtc`. Поля статуса и background worker для
   переходов или завершения назначений нет. Окончание смены не завершает задание и не
   останавливает ТПА.
6. **Назначения литейщиков — интервальный журнал.** `ShiftImmOperatorAssignment` ссылается на
   сохранённую позицию, ТПА и Operator и хранит серверные `AssignedAt`/`UnassignedAt`.
   Назначение требует старшего, но не требует производственного задания. Снятие только
   заполняет `UnassignedAt`; повторное назначение создаёт новую строку. На одном ТПА позиции
   допустимо не более двух активных литейщиков в технических `Slot` 1/2; один Operator может
   одновременно быть на разных ТПА. Partial unique indexes на
   `(ShiftPlanItemId, ImmId, Slot)` и `(ShiftPlanItemId, ImmId, OperatorId)` действуют только
   при `UnassignedAt IS NULL`.
7. **Блокировки сериализуют взаимосвязанные изменения.** `ShiftScheduleLock` использует
   транзакционную PostgreSQL advisory lock и сериализует изменения графика, старших и состава
   смены. При назначении и снятии дополнительный `FOR UPDATE` родительского `ShiftPlanItem`
   сериализует выбор и освобождение `Slot`; проверки выполняются повторно после ожидания.
   Свежие `FOR UPDATE`-чтения блокируют IMM и Operator до commit, поэтому параллельная
   архивация ТПА либо архивация/смена роли Operator не может пройти между проверкой и записью.
   Нарушения уникальности, serialization failure и deadlock преобразуются в конфликт 409.
8. **Фактическая работа ограничена окном смены.** Для будущего PZP-31 API вычисляет
   `WorkStart = max(AssignedAt, StartAtUtc)` и
   `WorkEnd = min(UnassignedAt ?? EndAtUtc, EndAtUtc)`. Интервал с `WorkEnd < WorkStart`
   пустой. У неснятого назначения `UnassignedAt` остаётся `null`, но фактическая работа всё
   равно заканчивается в `EndAtUtc`, без отложенной записи worker'ом. Сам отчёт, распределение
   выработки, ручной выпуск и брак в PZP-32 не реализуются.

## Отвергнутые альтернативы

- **Стабильный `ShiftId` в назначениях.** Справочник смен пересоздаётся при редактировании, а
  одинаковая по смыслу позиция не имеет устойчивого identity. Позиционный snapshot позволяет
  менять будущий график без переписывания истории и без ложной связи с удалённой строкой.
- **Отдельное вхождение смены без старшего.** Хранение всех дат и пустых позиций потребовало бы
  синхронизировать весь календарь и отличать пустую историю от отсутствия плана. Материализация
  только при первом старшем сохраняет виртуальные дни дешёвыми и однозначными.
- **Хранение только текущего состава.** Перезапись или удаление строки при снятии потеряло бы
  время работы, повторные назначения и основание для PZP-31. Интервальный журнал сохраняет эти
  факты, а partial indexes ограничивают только активную часть.
- **Фоновое закрытие назначений и статус смены в БД.** Worker создавал бы гонку с ручным
  снятием, задержку перехода nearest и лишнее хранимое состояние. Чистое сравнение с `now`
  даёт переход ровно в `EndAtUtc`, а вычисленный `WorkEnd` не требует записи.
- **Редактирование истории Manager/Admin.** Изменение прошлых окон, старших и интервалов
  разрушило бы достоверность учёта. Исторические смены read-only для всех ролей; синхронизация
  графика затрагивает только будущие заводские даты.

## Последствия

- Справочник смен можно развивать независимо: уже сохранённые текущие и прошлые окна не
  пересчитываются, а будущий план обновляется атомарно вместе с графиком.
- Позиционная синхронизация не угадывает перестановку смысловых смен: сохраняется именно номер
  позиции. Удалённые лишние будущие позиции теряют предварительный план; исторические записи
  этим путём не удаляются.
- Клиент обновляет nearest и права после `EndAtUtc` и периодически перезапрашивает данные;
  устаревший UI не обходит серверные проверки. Отдельного планировщика и recovery-процедуры для
  незакрытых назначений не требуется.
- Общая advisory lock делает изменения графика, старших и состава последовательными. Это
  осознанный компромисс ради согласованности; чтение плана и смен этой lock не блокируется.
- В PZP-32 появляются только данные и read model для будущего учёта выработки. Правила
  распределения циклов между двумя одновременно назначенными литейщиками остаются предметом
  PZP-31 и здесь не выбираются.
