# ADR-0011: Детекцию цикла литья переносим на коннектор (MQTT-контракт v2)

- **Статус:** Accepted
- **Дата:** 2026-08-10

## Контекст

`CycleProcessingHandler` детектировал завершение цикла литья по изменению сигнала
`cycleCounter` и использовал **метки MQTT-сообщений** как границы цикла — неточно:
между реальным физическим событием на ТПА (смыкание/раскрытие формы) и ближайшим
опросом коннектора лежит до одного интервала опроса (обычно 500 мс), и обе границы
окна дают такую ошибку независимо.

Более ранняя спека (`2026-08-01-cycle-boundaries-from-connector-design.md`) предлагала
латать это точечно: коннектор публикует два новых типа сенсоров `cycleStart`/`cycleEnd`
(защёлкнутые unix-мс), Control пересобирает границы цикла из пары значений. Контракт не
был реализован ни на одном коннекторе; при проработке следующего шага (работа с
подушкой/впрыском, живой статус цикла) стало ясно, что этот путь просто откладывает ту
же проблему — Control всё равно вынужден бы сам сопоставлять пары значений и защищаться
от протухшей/перевёрнутой защёлки, хотя коннектор уже прогоняет эти данные через
собственный надёжный автомат состояний, отслеживающий цикл по фронтам сигналов формы.

## Решение

Коннектор ведёт детекцию цикла целиком сам (автомат состояний по сигналам
`MoldClosed`/`Injection`/`MoldOpened`) и в каждом MQTT-сообщении публикует три раздела:
мгновенное состояние (`mode` + сигналы с флагом ошибки чтения), параметры **текущего**
незавершённого цикла (`currentCycle`, `null` если цикл не идёт) и параметры
**последнего завершённого** цикла (`lastCycle`, `null` до первого завершения с рестарта
коннектора). Полная схема — `docs/superpowers/specs/2026-08-09-mqtt-contract-v2-design.md`.

Control перестаёт детектировать цикл — `CycleProcessingHandler` только открывает
`ImmCycle` (`EndTime = null`) при получении `currentCycle` и закрывает его при
совпавшем `lastCycle`. Идентичность цикла — составной ключ `(CycleNumber, StartTime)`,
**не** один номер: автомат коннектора легитимно обнуляет счётчик между сериями выпуска
без разрыва связи, поэтому номер может повториться для разных физических циклов;
дедупликация/сопоставление по одному номеру рисковала бы принять новый цикл за уже
записанный старый. Перед созданием новой открытой строки — проверка в БД по
`(ImmId, CycleNumber, StartTime)`, что переживает рестарт самого Control (in-memory
трекер обнуляется, коннектор может прислать тот же `currentCycle` повторно).

Открытые (`EndTime = null`) циклы — новое, намеренное явление: незавершённый цикл уже
изнашивает пресс-форму, поэтому такие строки учитываются в агрегатах остатка ресурса
формы, но исключены из агрегатов длительности/среднего цикла до момента закрытия
(`DurationSeconds` не заполнен на открытой строке).

Старый узкий контракт `cycleStart`/`cycleEnd` отменяется целиком — `injectionDuration`/
`cyclePause`/`cycleCounter` как типизированные `ParameterType` тоже уходят из контракта
(`cycleCounter` становится зарезервированным именем сигнала, не типом).

## Альтернативы

- **Публиковать только `cycleStart`/`cycleEnd`, пересобирать цикл в Control** (спека
  2026-08-01) — отвергнуто: Control всё равно обязан заново реализовать защиту от
  протухшей/перевёрнутой защёлки и логику сопоставления пар, которую коннектор уже
  реализовал надёжно в своём автомате состояний. Контракт v2 передаёт результат этой
  работы напрямую, а не сырые точки для повторного вычисления.
- **Гейтить закрытие цикла политикой `ShouldProcessCycle` наравне с открытием** —
  отвергнуто при реализации: уже открытая строка обязана закрыться независимо от
  режима/задания на момент прихода `lastCycle` (иначе `IsSuccessful`, которое
  определяется именно в момент закрытия по режиму из закрывающего сообщения, никогда
  не будет уточнено для циклов, закрывшихся в Alarm без активного задания). Политика
  по-прежнему гейтит **открытие** новых строк и создание "внезапных" (без замеченного
  старта) строк на закрытии — наладка не должна порождать новые записи цикла, но обязана
  дозакрывать уже начатые.

## Последствия

- Breaking change контракта: коннекторы, не обновлённые под v2, не смогут публиковать
  телеметрию (сообщения отклоняются на decode). USR-Modbus переписывается отдельной
  спекой сразу под v2; Keba и OpcUa остаются на текущем контракте до отдельной миграции
  (см. пункты в `feature_backlog.md`).
- `ImmCycle.PauseDurationMs` в v2 контракте ничем не заполняется (пауза между циклами —
  забота потребителя данных, не Control) — поле осталось в схеме, но пока всегда `null`.
  Кандидат на отдельную задачу, если пауза понадобится напрямую в `ImmCycle`.
- Детект «зависших» открытых циклов (обрыв связи, коннектор так и не восстановился,
  строка остаётся с `EndTime = null` навсегда) — не реализован в этом изменении,
  вынесен в беклог; `Template.DeviceTimeoutSeconds` уже существует и подходит как основа.
- `UnplannedRunController.RollbackBindingAsync`/окно бэкфилла сирот-циклов не подхватывает
  открытый (`EndTime = null`) цикл на момент переназначения задания — известное,
  задокументированное ограничение, не блокирующее эту миграцию.
