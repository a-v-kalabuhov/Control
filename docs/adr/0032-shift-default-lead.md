# ADR-0032. Старший смены по умолчанию и эффективная ответственность

- Status: Accepted
- Date: 2026-11-25
- Related: [ADR-0004](0004-single-role-source-user-role.md), [ADR-0027](0027-shift-plan-and-operator-assignments.md), [ADR-0030](0030-shift-closure-report.md), [ADR-0031](0031-shift-closure-identity-and-output-conservation.md)

## Контекст

ADR-0027 разрешал ответственного за смену только явным `ShiftPlanItem.ShiftLeadId`. Поэтому
руководитель должен был назначать одного и того же старшего на каждую дату, а без такого назначения
план, nearest, staffing и сменный рапорт считали смену не имеющей ответственного. Для постоянного
графика нужны старшие по умолчанию по позициям и детерминированный резерв, если настройка не задана.

Fallback меняет не только отображение плана, но и владение nearest/pending/history и проверки доступа.
При этом нельзя массово создавать пустые смены за прошлые и будущие даты, терять назначения литейщиков
при замене ответственного или менять уже закрытый рапорт. Решение уточняет правила материализации
ADR-0027 и неизменяемость ответственного Closed из ADR-0030/0031.

## Решение

1. **Default хранится по позиции графика.** `ShiftDefaultLead` содержит только `Position` (PK,
   `Position >= 1`) и обязательный `ShiftLeadId` с FK на `Users.Id` и `Restrict`. FK на `Shifts` нет:
   строки справочника пересоздаются. Один пользователь может быть default для нескольких позиций.
   Настройки читаются и полностью заменяются через `GET`/`PUT /api/shifts/default-leads` только для
   Manager/Admin; общий `GET /api/shifts` не раскрывает персональные настройки. PUT под
   `ShiftScheduleLock` требует ровно одну запись на каждую актуальную позицию, повторно проверяет
   активность и роль кандидатов и атомарно применяет весь набор. Рассинхронизированный, неполный,
   лишний или повторный набор позиций даёт 409; недопустимый кандидат — 400.
2. **Единый resolver определяет эффективного старшего.** Для виртуальной и сохранённой позиции действует
   цепочка:

   ```text
   ShiftPlanItem.ShiftLeadId (Explicit)
       ?? ShiftDefaultLead[Position].ShiftLeadId (Default)
       ?? FirstActiveManager.Id (ManagerFallback)
       ?? null
   ```

   Источник вычисляется, не хранится; отсутствие старшего и источника представлено `null`, отдельного
   значения `None` нет. Resolver используют план и его warning/edit flags, nearest, staffing,
   pending/history, materialize, чтение и mutations closure. Подстановка только в DTO плана недопустима.
   `ShiftLeadId/Name` в плане становятся эффективными, а `ShiftLeadSource` принимает `Explicit`,
   `Default` или `ManagerFallback`. ManagerFallback не даёт менеджеру персональный контур ShiftLead.
3. **Резервный Manager выбирается по серверным данным.** В `User` добавлено обязательное UTC
   `CreatedAt`; приложение заполняет его при создании, обычные API редактирования не принимают это поле.
   Первый активный пользователь ровно с ролью `Manager` выбирается по `CreatedAt ASC`, затем `Id ASC`.
   Admin и другие роли не участвуют. Индекс `(IsActive, Role, CreatedAt, Id)` поддерживает выборку.
   Миграция заполняет существующие строки общим временем `now()` транзакции: прежние даты создания не
   восстанавливаются, а взаимный порядок таких пользователей определяет `Id`, не фактическая хронология.
4. **До закрытия fallback динамичен, операционные данные сохраняются.** Очистка explicit удаляет только
   override и возвращает default либо ManagerFallback; отдельного состояния «на этой дате намеренно нет
   старшего» нет. Замена default меняет эффективного ответственного всех незакрытых позиций без explicit,
   не переписывая назначения литейщиков, черновики и явные назначения. Очистка default переводит их к
   первому активному Manager. Только если активного Manager нет, очистка отклоняется, когда затронутая
   материализованная незакрытая позиция без explicit осталась бы с назначениями или рапортом, но без
   старшего. Пустые сохранённые дни без эффективного старшего и данных удаляются; данные не удаляются.
5. **Материализация ленивая и идемпотентная.** Сохранённый день допустим при наличии хотя бы одного
   эффективного старшего либо назначений/рапорта, но fallback сам не создаёт строки. Общий materializer
   под `ShiftScheduleLock` сохраняет полный snapshot дня, когда Manager/Admin явно назначает старшего,
   открывает виртуальную fallback-смену из плана через `materialize`, либо когда nearest выбирает смену
   текущего ShiftLead. Повторный вызов возвращает тот же постоянный `itemId`; fallback в `ShiftLeadId`
   при этом не копируется, closure, назначения и задания не создаются. Nearest рассматривает сохранённые
   и виртуальные текущие/будущие позиции, повторно проверяет выбор после блокировки и при гонке даёт 409.
   History/pending читают только материализованные позиции и не перебирают прошлый календарь; прошлую
   виртуальную смену при необходимости материализует Manager/Admin из плана.
6. **График, план и default синхронизируются позиционно и атомарно.** При сохранении справочника
   настройки позиций `1..N` сохраняются, новые позиции остаются без default, строки выше нового `N`
   удаляются с той же защитой операционных данных. Существующие правила синхронизации будущих дней,
   окон, `Id`, explicit и назначений не меняются. Ошибка откатывает справочник, план и настройки вместе.
   Перестановка интервалов по смыслу не угадывается: default принадлежит номеру позиции.
7. **Close замораживает ответственного.** В транзакции успешного закрытия под `ShiftScheduleLock` и
   блокировкой позиции сервер повторно разрешает доступ и выполняет `ShiftPlanItem.ShiftLeadId ??=
   effectiveShiftLeadId`. Зафиксированный default/ManagerFallback далее читается как Explicit. Смена
   настройки, архивация или изменение роли и состава активных Manager не меняют Closed DTO, PDF и
   владение закрытой историей. Замораживается FK пользователя; отдельного снимка ФИО старшего нет,
   поэтому текущее `User.FullName` по-прежнему допустимо по ADR-0030/0031.
8. **Изменения персонала не переписывают назначения.** Архивация, смена роли и очистка логина сохраняют
   default, explicit и Closed. Сохранённый архивный/ставший недопустимым default остаётся видимым и
   продолжает участвовать в resolver, но его нельзя выбрать заново; вход и персональный контур по-прежнему
   определяются актуальными ролью, активностью и логином. При изменении состава активных Manager
   ManagerFallback для незакрытых позиций без explicit/default автоматически пересчитывается по
   `CreatedAt, Id`. Фактические изменения активности пользователя и изменения роли, где старая или новая
   роль — Manager, сериализуются со staffing/materialize/close через `ShiftScheduleLock`; проверки после
   ожидания используют актуальный состав. Создание более позднего Manager текущий fallback не меняет.

## Отвергнутые альтернативы

- **FK `ShiftDefaultLead` на `Shift.Id`.** Справочник пересоздаёт строки и Guid при сохранении, поэтому
  такая ссылка либо обрывалась бы, либо требовала искусственной стабильной сущности смены. Позиция
  соответствует существующей модели плана.
- **Копировать default и ManagerFallback в каждый `ShiftPlanItem`.** Массовая перезапись нужна была бы
  при каждой смене настройки или первого Manager и смешивала бы override с вычисляемым fallback.
  Динамический resolver меняет только незакрытые позиции без более приоритетного источника.
- **Выбирать резервного Manager по табельному номеру, ФИО или клиентскому времени.** Эти значения не
  выражают порядок создания и могут меняться или различаться между клиентами. Серверные `CreatedAt, Id`
  дают общий детерминированный порядок.
- **Массово материализовать календарь или запускать background worker.** Пустые прошлые рапорты и
  бесконечный будущий план увеличивали бы БД и создавали гонки. Текущая/ближайшая смена вычисляется по
  серверному `now`, а строки появляются только при реальном открытии или назначении.
- **Подставлять fallback только во frontend.** Тогда nearest, staffing, pending и closure не признавали
  бы ответственного и давали бы другой результат доступа. Единый серверный resolver обязателен для всех
  чтения и mutations.
- **Вычислять fallback динамически для Closed.** Позднейшая настройка или архивация меняла бы
  ответственного закрытого документа и его историю. Close фиксирует FK в той же транзакции со снимком.
- **Ручной выбор резервного Manager и отдельный override «старшего нет».** Они добавляют независимые
  состояния и не нужны для исходного сценария; остаются возможными отдельными решениями, а не скрытыми
  параметрами этой модели.

## Последствия

- Постоянный график требует настройки только при изменении ответственного; явное назначение остаётся
  точечным override на конкретную дату. Все серверные контуры видят одного эффективного старшего.
- Замена default или первого Manager изменяет доступ к незакрытым сменам без миграции операционных
  данных. Клиент обязан обновлять nearest/pending/history; устаревший mutation получает 403 либо 409 по
  существующим правилам и не обходит серверную проверку.
- Default привязан к номеру позиции, а не к смыслу «первая/ночная смена». При переупорядочивании
  интервалов руководитель должен проверить настройки позиций.
- Backfill не восстанавливает реальную хронологию старых пользователей. Если для них нужен другой
  порядок fallback, потребуется отдельная осмысленная миграция данных либо новая функция выбора;
  обычное редактирование `CreatedAt` намеренно недоступно.
- Сохранённый default не очищается автоматически при архивации или смене роли. Это сохраняет
  ответственность и исторические ссылки, но требует от руководителя своевременно заменить такого
  человека для дальнейшей работы.
- Ленивая модель не показывает никогда не открытые виртуальные прошлые смены как пустые рапорты.
  Для ретроактивной работы Manager/Admin сначала материализует нужную позицию из плана.
