# ADR-0007: Каталог изделий (ProductType) как общая номенклатурная основа

- **Статус:** Accepted
- **Дата:** 2026-07-25

## Контекст

В системе нет явной сущности «тип изделия / номенклатурная позиция». `Mold`
(пресс-форма) неявно играет роль «что производим». Это упирается сразу в две
запланированные задачи:

- **PZP-05 (заказы):** заказ = одна номенклатурная позиция; прогресс заказа считается
  по типу изделия через цепочку задание → ПФ → тип изделия.
- **BL-27 (партии / цифровой паспорт):** партия и паспорт привязаны к типу изделия.

Обе задачи требуют одного и того же примитива — каталога изделий. Если каждая заведёт
свой, появится дубль и рассинхрон. Нужен один общий каталог, вводимый заранее (PZP-09),
как фундамент.

## Решение

Вводим сущность `ProductType` — каталог изделий:

- Поля минимальны: `Article` (уникальный человекочитаемый артикул для людей и внешних
  систем — CRM/1С), `Name`, `IsActive` (архивный флаг). Суррогатный `Id` (Guid) — ключ
  СУБД и цель FK.
- Связь **`ProductType → Mold = 1:N`**: `Mold.ProductTypeId` (**nullable** — старые ПФ
  без типа). Для новых ПФ привязка обязательна на уровне формы; колонка остаётся nullable
  ради существующих записей.
- FK `OnDelete(SetNull)`: тип физически не удаляют (только `IsActive=false`), правило
  единообразно с прочими FK.
- Архивирование типа с привязанными ПФ **разрешено** — единообразно с семантикой `IsActive`
  (CLAUDE.md): тип скрывается из выбора новых ПФ, существующие сохраняют ссылку.

`ProductType` — **общая основа**: PZP-05 (заказы) и BL-27 (партии/паспорт) ссылаются на
неё, а не заводят свои каталоги.

## Альтернативы

- **Оставить `Mold` в роли «что производим»** — отвергнуто: одна номенклатура может
  выпускаться несколькими ПФ (1:N), а заказ/партия должны агрегировать по изделию, а не по
  оснастке. Без отдельной сущности прогресс заказа и паспорт не собрать.
- **Каждая задача (PZP-05, BL-27) заводит свой каталог** — отвергнуто: дубль сущности и
  рассинхрон номенклатуры.
- **Сразу богатый `ProductType`** (единицы, описание, профиль паспорта по типу процесса) —
  отложено: для PZP-09 избыточно (YAGNI). Атрибуты паспорта добавит BL-27 поверх этой основы.

## Последствия

- Появляется явная иерархия **Изделие(тип) → ПФ → выпуск(циклы)**; открывает вертикаль
  Заказ → Задание → Партия → Изделие (PZP-05, BL-27, PZP-07).
- Миграция `AddProductType`: таблица `ProductTypes` + колонка `Molds.ProductTypeId`
  (nullable) + unique-индекс на `Article`.
- `CreateMold` начинает требовать `ProductTypeId` (обязателен для новых ПФ); старые ПФ без
  типа остаются валидны, `UpdateMold` их не блокирует. Принятый компромисс совместимости.
- Каталог сознательно «тонкий»; обобщение за пределы ТПА и атрибуты паспорта — будущие
  задачи, этот ADR — их основа (не заменяется, а расширяется).
