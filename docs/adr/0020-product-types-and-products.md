# ADR-0020: Типы изделий и изделия (артикулы)

- **Статус:** Accepted
- **Дата:** 2026-10-18
- **Заменяет:** [ADR-0007](0007-product-type-catalog.md); п.1 и п.8 [ADR-0009](0009-orders-module.md)

## Контекст

На пилоте ПЗП выяснилось, что одна ПФ выпускает несколько товарных позиций (одну деталь в разных
цветах), у каждой свой артикул в 1С/CRM. По ADR-0007 и ADR-0009 заказ и задание определяли, что
выпускается, только через ПФ (`Mold.ProductTypeId`), и позиции различить было нельзя: наладчик не
видел, какой цвет загружать, прогресс заказа не отделял «чёрный» от «белого». Обратная связь —
одному изделию могут соответствовать несколько ПФ (изношенную заменяют новой) — сохраняется
(`ProductType → Mold` = 1:N).

## Решение

1. **Двухуровневый каталог.** «Тип изделия» (`ProductType`) содержит «изделия» (`Product`). ПФ
   привязана к **типу**, заказ и задание ссылаются на **изделие** (`ProductId` обязателен).
   `Mold.ProductTypeId` не меняется.
2. **У типа всегда есть изделие.** Создание типа создаёт изделие по умолчанию: часть артикула `0`,
   наименование «По умолчанию».
3. **Полный артикул = `артикул типа + "." + часть изделия`** (`A123.BLK`). Буквы и точки в частях
   разрешены. Нормализация на сервере: `Trim()` + `ToUpperInvariant()` (`ProductArticle`).
4. **Единое пространство артикулов.** Полный артикул не совпадает ни с другим полным артикулом, ни с
   артикулом какого-либо типа (и наоборот): тип `123.А` с изделием `0` и тип `123` с изделием `А.0`
   дают один `123.А.0`. Строка из 1С «123.А» указывает ровно на одну сущность.
5. **Артикулы правятся всегда.** Правка артикула типа пересчитывает `FullArticle` всех его изделий в
   одной транзакции; при конфликте откат целиком. Заморозки после использования нет.
6. **Архив и удаление.** Архивное изделие (и изделия архивного типа) нельзя выбрать в новом заказе и
   задании, ссылки сохраняются. Последнее активное изделие активного типа в архив отправить нельзя;
   вернуть из архива тип без активных изделий нельзя. Изделие без заказов и заданий, не последнее у
   типа, можно удалить физически.
7. **Хранимый `Product.FullArticle` с unique-индексом.** Уникальность полных артикулов гарантирует
   БД; пересечение с артикулами типов проверяет приложение (при гонке нарушение индекса
   превращается в тот же 409).
8. **`Order.ProductId` вместо `Order.ProductTypeId`.** Тип заказа берётся через изделие — один
   источник правды. Привязка задания к заказу — по совпадению изделий
   (`task.ProductId == order.ProductId`).
9. **Автоподстановка.** Если у типа ровно одно активное изделие, оно подставляется само: в форме
   заказа при выборе типа, в форме задания при выборе ПФ (без привязки к заказу).
10. **Каталог по-прежнему тонкий и расширяется** (принцип ADR-0007 сохраняется): у изделия кроме
    артикула только наименование; прочие свойства добавляются по мере появления потребителей.
11. Смена цвета на той же ПФ — обычное новое задание: норматив наладки и буфер (PZP-14) сам
    учитывает неизменную ПФ.

Изделие задания должно принадлежать типу ПФ (`task.Product.ProductTypeId == task.Mold.ProductTypeId`)
и меняется только в `Planned` без заказа. Тип ПФ нельзя сменить при наличии заданий (правило
ADR-0007 сохраняется) — оно держит этот инвариант.

## Отвергнутые альтернативы

- **Связь ПФ ↔ изделие многие-ко-многим.** Ломает все проверки на ПФ и заставляет хранить тип в
  задании отдельно.
- **Отдельная ПФ на каждый цвет.** Ресурс, ТО и QR одной физической формы разъезжаются по записям.
- **Иерархия «изделие → вариант» поверх ПФ.** Усложняет модель без выигрыша: тип + изделия
  покрывают ту же потребность.
- **Запрет точек в частях артикула.** Склейка стала бы однозначной, но артикулы вида `123.А` из 1С
  не завести.
- **Склейка без разделителя.** Больше коллизий, хуже читается.
- **Заморозка артикулов после первого использования.** Выбрана свободная правка; история показывает
  актуальный артикул.
- **Вычисляемый полный артикул.** Уникальность только в приложении, поиск без индекса.
- **Единый реестр `Articles`.** Гарантирует п.4 на уровне БД, но требует синхронизации при каждой
  правке; для справочника на сотни записей избыточно.

## Последствия

- Миграция `AddProducts`: таблица `Products`, изделие `0` «По умолчанию» каждому типу,
  `ShiftTasks.ProductId` и `Orders.ProductId` заполняются им, `Orders.ProductTypeId` удаляется.
  Миграция останавливается сообщением `PZP-19:`, если у задания ПФ без типа. Перед выкаткой на ПЗП
  её прогоняют на копии их БД.
- Физическое удаление неиспользованного изделия — **исключение** из правила мягкого удаления
  (CLAUDE.md): у такой записи нет истории.
- Рецепты (BL-36) будут привязаны к `Product`.
- Отчёты по изделиям («Выпуск по изделиям», колонка «Изделие») — будущая задача.
- Правила — `Core/Policies`: `ProductArticle`, `ProductSelection`, `OrderTaskBinding`;
  `ShiftTask.SetProduct`.
- Спека: `docs/superpowers/specs/2026-10-18-pzp-19-product-articles-design.md`.
