# ADR-0019: «Нет связи» при задании в работе — это «Нет связи», а не «Работа»

- **Статус:** Superseded by [ADR-0021](0021-offline-dominates.md)
- **Дата:** 2026-10-15
- **Уточняет:** матрицу эффективного состояния из спеки
  `docs/superpowers/specs/2026-06-24-effective-status-dashboard-design.md` (строка 4); ADR-0006 не меняется.

## Контекст

Эффективное состояние ТПА (`ImmEffectiveStatus.Resolve`) не хранится — вычисляется на лету из сырого
статуса, интервалов задания и событий простоя (ADR-0006). По исходной матрице «задание `InProgress` +
сырой не-`Auto` без простоя» = `Production` («до порога остановка растворена в работу»), в том числе для
`Offline`. Расчёт был на то, что `DowntimeDetectionWorker` за 900 с без `Auto` заведёт `Event(Downtime)`,
и период станет «Простоем».

Пилот ПЗП, 14→15.10.2026: вечером завис Docker Desktop, API не работал до утра. Сырой `Offline`
(18:04 → 10:50) записан корректно — `ImmOfflineWorker` успел его зафиксировать, кеш после рестарта
восстановлен из БД. Но воркер простоев не работал, событие не появилось, и все 16 ч без связи при
задании «В работе» карточка ТПА и отчёт по оборудованию показали как «Работу» (+2 ч 50 мин в смене).

Когда данных нет, утверждать, что ТПА работал, нельзя.

## Решение

Строка матрицы «`InProgress` + не-`Auto` + нет простоя и порог не пройден» делится:

| Сырой режим | Было | Стало |
|---|---|---|
| `Offline` | `Production` | **`Offline`** |
| `Idle`/`Manual`/`Alarm` | `Production` | `Production` (без изменений — короткая остановка при живой связи) |

Остальное без изменений: открытый простой или пройденный порог → `Downtime`; `Setup` доминирует.
Правка в одной чистой функции, поэтому сразу действует везде — плитка дашборда, хронология карточки,
отчёт по оборудованию — и ретроспективно на всех уже собранных данных (пересчёт не нужен).

## Отвергнутые альтернативы

- **Дозаводить простой задним числом при старте API** (воркер видит, что с последнего статуса прошло
  больше порога). Период стал бы «Простоем» — тоже неправда: ночью завод мог не работать; кроме того,
  ложные простои попали бы в журнал и Парето простоев, а наладчику пришлось бы их разбирать. Не чинит
  уже накопленную историю.
- **Только для истории считать порог по длительности сырого сегмента** (`Offline` дольше 900 с →
  `Downtime`). Та же подмена неизвестного на «Простой», и расхождение логики live и истории.

## Последствия

- На плитке ТПА с заданием короткие обрывы связи теперь видны как «Нет связи» (раньше растворялись в
  «Работе»). Это честнее и полезно для диагностики коннектора/сети.
- Если API жив, через порог воркер по-прежнему открывает простой, и `Offline` становится `Downtime`,
  как раньше.
- Время без связи при задании больше не засчитывается в «Работу» в отчётах — выработка по
  эффективному статусу у пилота ПЗП за 15.10 уменьшится.
- `Setup` + `Offline` по-прежнему `Setup`: наладку не трогали, отдельного случая пока не было.
