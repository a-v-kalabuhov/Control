# 0009. Модуль учёта заказов (`Order`)

- Статус: Принято
- Дата: 2026-07-26

## Контекст и проблема

В системе не было уровня **над** заданиями: иерархия ограничивалась `ShiftTask` (задание) →
`ImmCycle` (выпуск). Это не позволяло вести заказы (номер, срок, требуемое количество), видеть
их прогресс по факту выпуска и отчитываться «что выполнено / что в работе». Нужен фундамент под
будущую вертикаль **Заказ → Задание → Партия → Изделие** (BL-27, PZP-07) без завязки на CRM/1С —
сначала ручное ведение заказов (PZP-05).

## Решение

1. **`Order` = одна номенклатурная позиция** (`ProductType` + `Quantity`), не многострочный
   заказ. Многострочный коммерческий заказ из CRM раскладывается на позиции — отдельные `Order`.
2. **`Order.Number` не уникален.** Одна пара `(Number, OrderDate)` может повторяться — по строке
   на каждую позицию одного коммерческого заказа. Идентичность — суррогатный `Id` (Guid);
   unique-индекс на `Number` не создаётся (в отличие от `ProductType.Article`).
3. **`Order → ShiftTask` — 1:N, `ShiftTask.OrderId` nullable.** Заказ исполняется параллельно
   несколькими заданиями на разных ТПА/ПФ; привязка задания к заказу опциональна — модуль заказов
   по сути отключаемый (задел под feature-flag ROS-07).
4. **Прогресс — derive-on-read по годным, не хранится.** Расчёт при чтении:
   `producedQuantity = Σ ActualQuantity`, `defectQuantity = Σ DefectQuantity`,
   `goodQuantity = producedQuantity − defectQuantity`,
   `progressPercent = goodQuantity * 100 / Quantity` (не капается, `>100%` допустим).
   `ActualQuantity` уже live-инкрементальное (`TaskOutputHandler` + переназначение сирот PZP-04) —
   второй источник правды не нужен. Тот же паттерн, что `UnplannedRun` (ADR-0008).
5. **Ручной брак — `ShiftTask.DefectQuantity`.** Вводится оператором/наладчиком при завершении
   задания (`0..ActualQuantity`, валидация в сущности). Брака как величины раньше не было:
   `TaskOutputHandler` считает только успешные циклы, `ImmCycle.IsSuccessful=false` — авария,
   не QC-брак. Поле — минимальное зерно для будущего контроля качества (ROS-05).
6. **Две независимые семантики «выполнения».**
   - Выполнение **задания** = выпущен `PlanQuantity` (по `ActualQuantity`), независимо от брака;
     компенсация брака — существующая функция PZP-08 «Продолжить выпуск» (`AddPlannedQuantity`).
   - Выполнение **заказа** = `Σ(ActualQuantity − DefectQuantity) ≥ Quantity` (только годные).
7. **Завершение заказа — вручную менеджером**, только при достаточном выпуске годных
   (`Order.Complete(goodQuantity)` — гард в сущности, паттерн ADR-0002). Нет авто-перехода:
   устойчиво к браку/перевыпуску, не нужен хук в конвейере циклов. При недостатке — заказ можно
   только отменить (`Cancel`); статусы `Active` / `Completed` / `Cancelled`, физически не удаляются.
8. **Жёсткая валидация изделия при привязке.** Привязать задание к заказу можно только если
   `task.Mold.ProductTypeId == order.ProductTypeId` (иначе `DomainException` → 400); ПФ без типа
   привязать нельзя; привязка возможна только к заказу в статусе `Active` (`OrderTaskBinding.EnsureCanBind`).
9. **Отвязка — только из карточки заказа** (`DELETE /api/orders/{id}/tasks/{taskId}`, UC-7).
   Форма/карточка задания привязывает или меняет заказ (`set-order`), но не может его снять —
   единственная точка отвязки исключает риск случайного разрыва привязки из мест, где это не
   основной сценарий.

## Альтернативы

- **Хранимый счётчик прогресса на `Order`** (Вариант B, обновляемый Стадией-2 хендлера конвейера
  циклов) — отклонён: дублирование правды, риск изоляции `DbContext` в хендлерах, лишняя
  синхронизация при привязке/отвязке; заказов немного, `Σ` по индексу `OrderId` тривиальна.
- **Многострочный заказ** (одна сущность = весь коммерческий заказ с позициями) — отклонён:
  усложняет модель и агрегацию прогресса без немедленной пользы; позиции проще вести как плоские
  `Order` с повторяющимся `Number` (следующий шаг — CRM/1С-интеграция, BL-10/ROS-11).
- **Авто-завершение заказа** по достижению плана — отклонено: не нужен хук в конвейере циклов,
  устойчивее к браку/донабору; завершение — осознанное действие менеджера.
- **Брак из аварийных циклов** (`ImmCycle.IsSuccessful=false`) — отклонён: авария ≠ QC-брак
  (авария — сбой цикла ТПА, брак — дефект годного с точки зрения оборудования изделия); брак
  вводится вручную оператором при завершении задания.

## Последствия

- Модуль заказов опционален по конструкции (`OrderId` nullable, нет обязательной зависимости
  заданий от заказов) — готов под будущий feature-flag ROS-07 без переделки схемы.
- Переназначение сирот-циклов (PZP-04) меняет `ActualQuantity` привязанного задания — прогресс
  заказа отражает это автоматически на чтении, без дополнительной синхронизации (UC-12).
- Заказ ссылается на `ProductType` (PZP-09) — жёсткая валидация привязки по нему; закладывает
  фундамент вертикали Заказ → Задание → Партия → Изделие (BL-27) и планирования по заказам (PZP-07).
- `DefectQuantity` — минимальное зерно; расширяется причинами/приёмкой в полноценном контроле
  качества (ROS-05).
