# Деплой демо-VPS: пакет `deploy/demo/` — дизайн

**Дата:** 2026-10-19 · **Ветка:** `feature/demo-deploy` · **Версия:** 0.18.0

## Цель

Обновить публичное демо Control на VPS `control-demo.ru` (195.208.2.44) до текущей версии и собрать
всё, что нужно для деплоя, в одной папке `deploy/demo/`, как уже сделано для `deploy/pzp/` и
`deploy/smoke-test/`. Одновременно:

- перевести демо на **HTTPS** с сертификатом домена;
- убрать устаревший эмулятор (`Wintime.Control.Emulator`, контракт v1) из деплоя;
- заменить БД на VPS свежей, сгенерированной новым `seed_demo.sql` под текущую схему и фичи.

Демо — публичная песочница: `DemoMode=true`, на экране входа открытые демо-аккаунты всех ролей,
включая админа. Так задумано, закрывать демо не нужно.

## Вне рамок

- **Живые данные.** Телеметрии нет, все ТПА показывают «Нет связи». Мини-эмулятор, который
  повторяет действия наладчика, вынесен в отдельную задачу (BL-46).
- Чистка `HttpEmulatorControlService`/`EmulatorSettings`. При `DemoMode` действия наладчика
  пишут в лог warning о недоступном эмуляторе, на работу это не влияет. Уйдёт вместе с BL-46.
- Автоматический сброс БД по cron. Сброс выполняется вручную перед показом.
- CI-публикация образов. Сборка и push идут с машины автора.

## Акторы и сценарии (use cases)

**Акторы:** автор (разработчик, деплоит со своей Windows-машины), посетитель демо (любой
человек из интернета), VPS (Linux, пользователь `deploy`, Docker).

### UC-1. Первичная настройка VPS (автор, один раз)

1. Под `root` положить свой `id_rsa.pub` в `/home/deploy/.ssh/authorized_keys` и добавить
   `deploy` в группу `docker`.
2. Остановить и удалить старый стек (корневой `docker-compose.prod.yml` с эмулятором) **вместе с
   volume** (`docker compose down -v`), удалить его образы (`docker image prune -a`). Это и
   освобождает диск: на 2026-10-19 свободно 628 МБ из 8,6 ГБ (93%), потому что старый эмулятор
   всё время пишет телеметрию в БД. Порты 5000/5002/1883/9001 освобождаются. Проверить
   `df -h`: нужно ≥ 3 ГБ свободного места.
3. Открыть в файрволе TCP 80 и 443.
4. Заполнить локальный `deploy/demo/deploy.local.psd1` (хост, пользователь, удалённая папка).
5. `.\deploy.ps1 -Certs`: сертификат собирается в `fullchain.pem` и вместе с ключом копируется
   на VPS в `~/wtctrl-demo/certs/`.
6. Создать `~/wtctrl-demo/.env` на VPS из `.env.example` (пароль БД).
7. `.\deploy.ps1 -ResetDb` — первый полный деплой.

**Альтернативы:** нет ключа или `deploy` не в группе `docker` — `deploy.ps1` падает на шаге
`ssh` с понятным сообщением; на VPS нет `.env` или `certs/` — скрипт останавливается до
`compose up`, ссылаясь на UC-1.

Описание — `ASSEMBLE.md`, раздел «Первичная настройка».

### UC-2. Обновление версии (автор)

1. Поднять `VERSION`, закоммитить.
2. `.\deploy.ps1`: проверки (чистое дерево, `VERSION` ≠ версии на VPS) → сборка фронта и
   `dotnet publish` → `docker build` → push `api:<VERSION>` и `api:latest` в GHCR → `scp` пакета
   и сида → `ssh`: `docker compose pull && docker compose up -d` → ожидание `200` от
   `https://control-demo.ru/health` → проверка версии (см. «Проверка версии»).

**Альтернативы:** грязное рабочее дерево или `VERSION` не поднят — отказ до сборки (флаг
`-Force` пропускает проверку версии); push в GHCR без авторизации — ошибка с подсказкой
`docker login ghcr.io`; после `up -d` сайт не отвечает 120 с — скрипт выводит
`docker compose logs --tail 100 api` и завершается с ошибкой.

### UC-3. Сброс БД перед показом (автор)

1. `.\deploy.ps1 -ResetDbOnly` (или `-ResetDb` вместе с обновлением).
2. На VPS `reset-db.sh`: `compose stop api` → удалить volume postgres → `up -d postgres`
   (ждать healthcheck) → `up -d api` (миграции и 4 демо-аккаунта) → ждать `200` от `/health` →
   `psql -v ON_ERROR_STOP=1 -f seed_demo.sql` в контейнере postgres → `compose restart api`
   (кеши статусов перечитывают историю).
3. Итог: история за последние 30 суток, заканчивающаяся моментом сброса.

**Альтернативы:** сид упал — скрипт завершается с ошибкой, API остаётся на пустой БД с
демо-аккаунтами; исправить сид и повторить. Демо-аккаунта `adjuster` нет (сид запущен раньше
API) — сид сам выбрасывает исключение `RAISE EXCEPTION`.

### UC-4. Посетитель смотрит демо

1. Открывает `https://control-demo.ru` (http редиректит на https), сертификат валиден.
2. Входит под любым демо-аккаунтом с экрана входа (`admin`, `manager`, `adjuster`).
3. Видит: дашборд (все ТПА «Нет связи» — живых данных нет), задания, заказы, справочники,
   отчёты за последние 30 суток, историю на карточке ТПА.

### UC-5. Посетитель проходит сценарий наладчика (с телефона)

1. Входит под `adjuster`, видит 6–8 выданных ему заданий (`Issued`, плановое начало — сегодня, в
   уже прошедшие часы).
2. «Начать» → наладка; сканирует QR пресс-формы с экрана ноутбука (`QrCodeDialog`). Камера
   работает, потому что страница открыта по HTTPS (secure context). Верификация необязательна.
3. «Завершить наладку» → задание в работе. Плитка ТПА показывает «Нет связи», а не «Работа»
   (ADR-0019: нет данных — нет работы), выпуск 0.
4. «Завершить» с ручным вводом количества; «Простои» → указать причину неразмеченного простоя.

**Альтернативы:** задания закончились (их выдают общему `adjuster` все посетители) — автор
выполняет UC-3.

## Состав пакета

```text
deploy/demo/
├── ASSEMBLE.md            # автору: UC-1, UC-2, UC-3, устранение неполадок
├── deploy.ps1             # единая точка входа (машина автора)
├── deploy.local.psd1      # хост/пользователь/папка/пути к сертификату — НЕ в git
├── deploy.local.example.psd1
├── test-seed.ps1          # локальная проверка сида (см. «Проверка сида»)
├── seed/
│   ├── seed_demo.sql      # новый сид
│   └── check_seed.sql     # SQL-проверки инвариантов для test-seed.ps1
└── package/               # копируется на VPS в ~/wtctrl-demo/
    ├── docker-compose.yml
    ├── .env.example       # DB_PASSWORD
    ├── mosquitto.conf
    ├── reset-db.sh        # LF-окончания (.gitattributes)
    └── certs/             # только на VPS и локально — НЕ в git
```

`deploy.ps1` копирует на VPS `package/` (кроме `.env` и `certs/`) и `seed/seed_demo.sql`.

### `deploy.ps1` — параметры

| Флаг | Действие |
| --- | --- |
| (нет) | сборка → push в GHCR → `scp` → `pull && up -d` → проверка |
| `-ResetDb` | то же + `reset-db.sh` после `up -d` |
| `-ResetDbOnly` | только `scp` сида и `reset-db.sh` |
| `-Certs` | только сборка `fullchain.pem` и копирование `certs/` на VPS, затем `restart api` |
| `-Force` | пропустить проверку «`VERSION` поднят» |

Конфиг `deploy.local.psd1`:
`@{ Host = '195.208.2.44'; User = 'deploy'; RemoteDir = '~/wtctrl-demo'; Domain = 'control-demo.ru';
CertFile = '...'; CaFile = '...'; KeyFile = '...' }`.

Образ: `ghcr.io/a-v-kalabuhov/control/api:<VERSION>`, compose ссылается на `${API_TAG:-latest}`.
`deploy.ps1` передаёт `API_TAG=<VERSION>` при `up`, поэтому на VPS работает именно собранная версия;
при откате достаточно `API_TAG=<старая> docker compose up -d`.

## `docker-compose.yml` (демо)

- **postgres** `16-alpine`, healthcheck `pg_isready -h 127.0.0.1`, `shared_buffers=128MB`,
  `max_connections=20`, `mem_limit: 384m`, volume `postgres_data`, портов наружу нет.
- **mosquitto** `2.0`, `mem_limit: 64m`, портов наружу нет (только сеть compose). Брокер сейчас
  открыт анонимно всему интернету — это закрывается.
- **api** `ghcr.io/a-v-kalabuhov/control/api:${API_TAG:-latest}`, `mem_limit: 512m`,
  `restart: unless-stopped`, `depends_on: postgres (service_healthy)`:
  - `ASPNETCORE_ENVIRONMENT=Production`, `DemoMode=true`, `DOTNET_gcServer=0`;
  - `ASPNETCORE_URLS=http://+:8080;https://+:8443`, `ASPNETCORE_HTTPS_PORT=443`,
    `Https__Redirect=true`;
  - `ASPNETCORE_Kestrel__Certificates__Default__Path=/certs/fullchain.pem`,
    `ASPNETCORE_Kestrel__Certificates__Default__KeyPath=/certs/privkey.pem`;
  - строка подключения с `${DB_PASSWORD}`, `MqttSettings__BrokerUrl=mosquitto`;
  - порты `80:8080`, `443:8443`; volume `./certs:/certs:ro`.
- Эмулятора нет.
- Все сервисы: `logging: json-file, max-size: 10m, max-file: 3` (логи не съедают диск).

**Защита диска (VPS 8,6 ГБ).** `deploy.ps1` перед `pull` и `reset-db.sh` перед сидом проверяют
свободное место (`df` на разделе `/var/lib/docker`); меньше 1,5 ГБ — остановка с сообщением.
После успешного `up -d` — `docker image prune -f`: удаляются образы без тега, работающая версия
остаётся.

**Сертификат.** `fullchain.pem` = `domain.crt` + `ca.crt` (корневой/промежуточный от УЦ), ключ —
`privkey.pem` (`chmod 600`). Kestrel отдаёт цепочку из `Path`; лишний self-signed корень браузеры
игнорируют. Если ключ зашифрован паролем — `Certificates__Default__Password` из `.env`
(решается на месте, в `ASSEMBLE.md`).

**Проверка версии.** Отдельного API-endpoint версии нет (версия вшита во фронт и сборки .NET,
спека `2026-09-29-app-version-design.md`). После `up -d` скрипт по `ssh` сверяет образ запущенного
контейнера (`docker inspect wtctrl-demo-api --format '{{.Config.Image}}'`) с `api:<VERSION>`;
при расхождении — ошибка.

## Новый `seed_demo.sql`

### Принципы

- **Только прошлое.** Ни одной записи со временем позже `now()` в момент загрузки.
- **Даты относительные:** якорь `t0 := now()`, «сутки» и смены — по Europe/Moscow; история —
  последние 30 суток. Каждый сброс даёт ту же картину, сдвинутую ко «сегодня».
- **Детерминированно:** `setseed(...)` в начале.
- **Под текущую схему:** запуск после миграций (БД создаёт API); пишет `ShiftTasks`, `Products`,
  `ProductTypes`, `Orders`, `MoldCompatibleImms`, `UnplannedRuns`, `PlanningDefaults` и т. д.
- **Демо-аккаунты не трогает.** Пользователей `admin`/`manager`/`adjuster`/`emulator` создаёт API;
  сид находит `adjuster` по `UserName` (нет — `RAISE EXCEPTION`).
- **Соблюдает инварианты CLAUDE.md**, их проверяет `check_seed.sql`.

### Справочники

- 2 шаблона ТПА; ~10 ТПА, один в архиве (`IsActive=false`, история сохранена).
- ~10 типов изделий, у каждого 1–3 изделия (часть `0` «По умолчанию» + варианты), полный артикул
  `ТИП.ЧАСТЬ`; один тип в архиве.
- ~15 ПФ, у каждой задан тип; у части ПФ — список совместимых ТПА (`MoldCompatibleImms`), у
  остальных пусто (любой ТПА).
- Причины простоев (плановые и внеплановые), 2 смены 08:00–20:00 и 20:00–08:00 (Europe/Moscow),
  `PlanningDefaults` (норматив наладки, буфер).
- 5 наладчиков и 1 мастер сида с непубличным паролем (случайный хеш, войти нельзя) — для отчётов
  «по наладчикам».

### История (последние 30 суток)

- **Заказы** ~12: `Completed`, `Active`, `Cancelled`; `ProductId` заказа = изделию заданий
  (`OrderTaskBinding`). Часть заданий без заказа.
- **Задания** `Completed`/`Closed`, в том числе длиннее смены (несколько суток); `PlannedDate`,
  `PlannedSetupStartTime`, снапшот норматива наладки и буфера, `WorkMode` (в основном `Auto`,
  часть `SemiAuto`), `PlannedFullCycleSeconds`/`PlannedInjectionCycleSeconds`.
- **Циклы** `ImmCycles`: закрытые, `Cavities` — снапшот, `PauseDurationMs`,
  `InjectionDurationMs`, `Cushion`; выпуск задания = Σ гнёзд закрытых циклов, остановка при
  достижении плана (ТПА сам останавливается по плану), затем `idle` до завершения задания.
- **Статусы** `ImmStatusHistory`: наладка `manual`, работа `auto`, простои `idle`/`alarm`, пара
  окон `Offline`; **простои** `Events` с причинами и без (часть неразмеченных — для UC-5);
  эпизоды «работы без задания» (`UnplannedRuns`).
- **Телеметрия** `Telemetry` за все 30 суток, чтобы «Мониторинг» → «История» не был пустым ни
  за какой день: по одной точке на каждый датчик шаблона на каждый закрытый цикл, плюс
  записи статуса (≈2 млн строк, ~300–400 МБ). Датчики (`Sensors`) задаются в `JsonConfig` обоих
  шаблонов, иначе на странице «Мониторинг» нечего выбрать. Если на VPS после чистки (UC-1)
  места окажется меньше расчётного, объём уменьшается до ~6 ТПА или 14 суток (параметр в начале
  сида).

### Срез «сейчас» (на момент `t0`)

- 3–4 ТПА: задание `InProgress` с частичным выпуском.
- 1–2 ТПА: задание `Setup`.
- `adjuster`: 6–8 заданий `Issued` на разных свободных ТПА, плановое начало — сегодня, в
  прошедшие часы (на ТПА без активного задания, совместимых с ПФ).
- Ещё 2–3 задания `Planned`/`Issued` других наладчиков с датой сегодня/вчера.
- Остальные ТПА — без задания. Все открытые записи статуса — с `EndedAt = NULL`; после старта API
  `ImmOfflineWorker` переведёт ТПА в «Нет связи».

### Объём

~10 ТПА × 30 суток ≈ 300–500 тыс. строк `ImmCycles`; время загрузки на VPS (1 ядро) — порядка
минут. После сида — `ANALYZE`.

## Проверка сида — `test-seed.ps1`

По образцу `deploy/smoke-test/build-report-dump.ps1`:

1. `dotnet ef migrations script` → временный контейнер `postgres:16-alpine` → схема.
2. Вставить фиктивного пользователя `adjuster` (Role = Adjuster), как это сделал бы API.
3. Прогнать `seed_demo.sql` с `ON_ERROR_STOP=1`, замерить время.
4. Прогнать `check_seed.sql`: каждый запрос возвращает число нарушений, всё ≠ 0 — ошибка.
   Проверки:
   - нет записей позже `t0` (все временные колонки);
   - у каждого типа ≥1 изделия, у активного — ≥1 активного; `FullArticle` уникален и не
     совпадает с артикулом типа;
   - у задания `ProductId` из типа его ПФ; при заказе `task.ProductId = order.ProductId`;
   - ТПА задания входит в непустой список совместимости ПФ;
   - `PlannedFullCycleSeconds` > 0 у всех заданий; `PlannedDate` задан;
   - выпуск задания ≤ плана; на ТПА не больше одного `Setup`/`InProgress`;
   - у `Issued` есть наладчик; у `adjuster` 6–8 `Issued`;
   - открытая запись статуса — не больше одной на ТПА.
5. Удалить контейнер.

  поднимать до запуска).
- `VERSION` → 0.18.0.
- Кода приложения изменения не касаются. ADR не нужен: пакет деплоя легко откатить, паттерн
  уже задан `deploy/pzp/`.

## Критерии готовности

1. `test-seed.ps1` проходит локально, все проверки 0.
2. `deploy.ps1 -ResetDb` на VPS завершается успешно, версия на VPS = 0.18.0.
3. `https://control-demo.ru` открывается с валидным сертификатом; `http://` редиректит на https;
   порты 5000/1883/9001 снаружи закрыты.
4. Вход `admin / Admin123!` работает; отчёты за последние 30 суток заполнены; в БД нет данных
   позже момента сброса.
5. С телефона под `adjuster` видны выданные задания, камера QR-сканера включается, сценарий
   UC-5 проходит до конца.
