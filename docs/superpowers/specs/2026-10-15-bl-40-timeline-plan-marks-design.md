# BL-40 — Плановые метки и факт наладки на хронологии карточки ТПА

- **Дата:** 2026-10-15
- **Задача:** BL-40 (🔴; из брейнсторминга ARCH-03). Заодно закрывает follow-up ARCH-03
  «бары заданий в одном ряду перекрываются».
- **Статус:** дизайн утверждён, готов к плану реализации
- **ADR:** не нужен — изменение только UI, без схемы БД и контракта API

## Проблема

В карточке ТПА (окно подробностей `ImmDetailModal` → `ShiftTimeline`) хронология смены показывает
статусы машины и факт заданий: бар от `setupStartedAt` до завершения, наладка — светлым оттенком.
Плана на ленте нет. Мастер не видит, когда наладку должны были начать и закончить, опоздал ли
наладчик и уложился ли он в норматив (PZP-14). Всё это приходится сверять вручную по карточке
задания.

Вторая проблема (follow-up ARCH-03): бары заданий лежат в одном ряду. Если наладка следующего
задания началась до закрытия предыдущего, бар рисуется поверх соседнего.

## Акторы и сценарии (use cases)

- **Мастер/менеджер смены (Manager, Admin)** открывает карточку ТПА на дашборде.
  1. Задание запланировано на эту смену, наладка ещё не началась. В ряду «План» он видит
     плановое окно наладки и норматив и понимает, когда наладчик должен подойти.
  2. Наладка идёт. По плановому бару видно, на сколько наладка опоздала (или началась раньше)
     и сколько осталось до планового окончания.
  3. Наладка завершена. Видно фактическую длительность наладки рядом с нормативом.
  4. На ТПА два задания подряд, и наладка второго наложилась на выпуск первого. Бары
     раскладываются по дорожкам и не перекрывают друг друга.
- **Наладчик (Adjuster)** открывает ту же карточку (доступ к `GET /api/tasks` есть) и видит
  свой план на смену.
- **Плитка ТПА на дашборде (`ImmCard`)** не меняется: метки там **не** показываются.

## Решения (зафиксированы при брейнсторминге 2026-10-15)

1. **Отдельный ряд «План»** над рядом «Задания». Это контурный бар цвета задания на интервале
   плановой наладки. Так же будет выглядеть ряд «план/факт» на Гантте PZP-07.
   - Отвергнуто: вертикальные риски на ряду «Задания». Когда заданий несколько, риски
     путаются и не видно, к какому заданию относится риска.
2. **Плановое окончание считается от планового начала**:
   `plannedSetupEnd = plannedStartAt + plannedSetupMinutes`. Это чистый план, как на Гантте.
   Фактическую длительность наладки сравниваем с нормативом текстом.
3. **Текстовые метки — внутри планового бара** (обрезаются многоточием, если не помещаются).
   Полный текст всегда виден в тултипе планового бара и бара факта.
   - Отвергнуто: третья строка в баре факта. Ряд станет выше, а с дорожками будет тесно.
   - Отвергнуто: только тултип. Отклонения не видны без наведения.
4. **Ранний старт показываем:** «раньше на N». Опоздание — красным, «раньше на N» — нейтральным
   серым. При |Δ| < 1 мин пишем «вовремя».
5. **В ряд «План» попадают только задания, у которых плановое окно наладки пересекает смену.**
   Просроченные неначатые задания из прошлых смен не показываем: просрочка видна в списке
   заданий (PZP-13).
   - Отвергнуто: прижимать такие задания к левому краю с пометкой «просрочено».
6. **Дорожки при перекрытии.** Пересекающиеся бары (отдельно в ряду «План» и в ряду «Задания»)
   раскладываются по дорожкам. Высота дорожки фиксирована, ряд растёт с числом дорожек. Без
   перекрытий остаётся одна дорожка, вид как сейчас.
7. **Данные — второй запрос с фронта, бэкенд не меняется** (см. «Данные»).
   - Отвергнуто: новый параметр `GET /api/tasks` («активные **или** плановые»). Он меняет
     контракт API ради экономии одного запроса.

## Данные

Все нужные поля уже есть в `TaskDto`: `plannedStartAt` (UTC, `PlannedTaskStart.Resolve`),
`plannedSetupMinutes`, `setupStartedAt`, `startedAt`, `completedAt`, `closedAt`, `status`.

`ImmDetailModal.loadData` делает параллельно два запроса:

1. как сейчас: `GET /api/tasks?immId&activeFrom=<начало смены>&activeTo=<конец смены>` — факт;
2. новый: `GET /api/tasks?immId&plannedFrom=<дата начала смены − 1 день>&plannedTo=<дата конца
   смены + 1 день>` без `status`, то есть без `Completed`/`Closed`. `PlannedDate` хранится
   в календаре завода, а даты считаются в поясе браузера (см. память «время на фронте — пояс
   браузера»), поэтому берём запас ±1 день. Даты передаются в формате `YYYY-MM-DD`.

Результаты объединяются по `id`; если задание пришло в обоих ответах, берём версию из запроса 1.
Объединённый список сортируется по `plannedStartAt` (при равенстве — по `id`) и передаётся
в `ShiftTimeline` пропом `tasks`. Индекс цвета задания — позиция в этом списке, поэтому цвет
задания в рядах «План» и «Задания» совпадает.

Отбор по рядам внутри `ShiftTimeline`:

- ряд «Задания» — задания с `setupStartedAt`, окно активности которых пересекает смену
  (`taskBarLayout`, как сейчас; задания из запроса 2 без `setupStartedAt` сюда не попадают);
- ряд «План» — задания, у которых `[plannedStartAt, plannedSetupEnd)` пересекает смену.

**Известный пробел:** задание запланировано на эту смену, но целиком выполнено и закрыто до её
начала. Его не вернёт ни один из запросов, поэтому планового бара не будет. Случай редкий,
принимаем.

## Отображение

### Ряд «План»

- Бар: пунктирная рамка цвета задания и полупрозрачная заливка того же цвета, обрезка по
  границам смены. Если `plannedSetupMinutes = 0`, вместо бара рисуется узкий вертикальный маркер
  (минимальная ширина 4 px) с тем же тултипом.
- Если бар обрезан слева или справа, у этого края нет скругления: видно, что план выходит
  за смену.
- Содержимое: строка 1 — `moldName` (или «Задание»); строка 2 — метки (ниже).

### Текстовые метки (строка 2 и тултип)

Δ = `setupStartedAt − plannedStartAt`, округляется до минут.

| Состояние задания | Строка 2 |
|---|---|
| наладка не началась (`setupStartedAt` нет) | `норм 45м` |
| наладка идёт или закрыта без выпуска (`setupStartedAt` есть, `startedAt` нет) | отклонение |
| наладка завершена (`startedAt` есть) | отклонение · `наладка 1ч 10м / норм 45м` |

Отклонение: Δ ≥ 1 мин → `опозд. 25м` (красный); Δ ≤ −1 мин → `раньше на 10м` (серый);
иначе — `вовремя`. Фактическая наладка = `startedAt − setupStartedAt`. Формат длительностей —
как в `durStr` (`1ч 10м`, `45м`, `2ч`).

### Тултипы

- **Плановый бар:** название ПФ; `План наладки: 10:00 — 10:45 (норм 45м)` с полными временами,
  даже если бар обрезан сменой; строка отклонения (если наладка началась); `Наладка: 1ч 10м`
  (если завершена).
- **Бар факта:** к текущему тексту `taskTitle` добавляются строки `План наладки: …` и
  отклонение / фактическая наладка в той же формулировке.

### Дорожки

- `assignLanes(items)` получает элементы с `{ start, end }` в мс и возвращает номер дорожки
  для каждого. Алгоритм жадный: по возрастанию `start` элемент кладётся в первую дорожку, где
  `end` предыдущего ≤ `start`; если такой нет, заводится новая дорожка.
- Высота дорожки: ряд «Задания» — 44 px (текущая высота бара), ряд «План» — 34 px.
  Высота ряда = число дорожек × высота дорожки + отступы. Вид с одной дорожкой не меняется.
- Раскладка считается по видимым (обрезанным сменой) интервалам. Для маркера с нулевым
  нормативом это интервал минимальной ширины.

## Код

- `src/utils/shiftTimeline.js` — чистые функции:
  - `planBarLayout(task, shiftStart, shiftEnd)` → `{ leftPct, widthPct, clippedLeft,
    clippedRight, isMarker } | null`;
  - `setupDeviation(task)` → `{ minutes, kind: 'late' | 'early' | 'onTime', label } | null`;
  - `setupActualMs(task)` → число мс | `null`;
  - `assignLanes(items)` → массив номеров дорожек.
- `src/components/dashboard/ShiftTimeline.vue` — ряд «План», дорожки в обоих рядах, тултипы.
- `src/views/dashboard/ImmDetailModal.vue` — второй запрос, слияние, сортировка.
- `docs/user-guide/manager.md`, раздел 2.5 — описать ряд «План», метки отклонения и дорожки.

## Тесты (Vitest)
