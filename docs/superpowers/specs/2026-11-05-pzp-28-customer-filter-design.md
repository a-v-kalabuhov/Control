# PZP-28 — Фильтр по заказчику

- **Дата:** 2026-11-05
- **Задача:** PZP-28, блок В фидбека пилота ПЗП
- **Зависимость:** PZP-23 — заказчик у типа изделия и заказа, общие подсказки ранее введённых названий
- **Статус:** реализовано 2026-11-05
- **ADR:** не нужен — расширение существующих списков и GET-контрактов без новых сущностей и изменения доменных инвариантов

## Цель

Дать пользователю возможность отфильтровать три существующих списка по одному заказчику:

- справочник типов изделий — по `ProductType.Company`;
- справочник пресс-форм — по `Company` связанного типа изделия;
- список заказов — по `Order.Customer`.

Названия для выбора берутся из уже существующих подсказок PZP-23, то есть из значений, ранее введённых
в типах изделий и заказах. Отдельный пункт «(не указано)» находит записи без заказчика.

## Акторы и сценарии (use cases)

| Актор | Сценарий | Endpoint | Тест |
|---|---|---|---|
| Менеджер / админ | **UC-1.** Открывает типы изделий, вводит фрагмент в фильтре «Заказчик», выбирает одно из ранее введённых названий и нажимает «Применить». Видит только типы с точно таким `Company`. | `GET /api/producttypes?customer=…` | `ProductTypesControllerTests.List_FiltersByCustomer` |
| Менеджер / админ | **UC-2.** Фильтрует пресс-формы по выбранному заказчику. Видит ПФ, связанные с типами изделий этого заказчика; значение `Order.Customer` на результат не влияет. | `GET /api/molds?customer=…` | `MoldCustomerFilterTests.List_FiltersByProductTypeCompany` |
| Менеджер / админ / наблюдатель | **UC-3.** Фильтрует заказы по выбранному заказчику. Учитывается только `Order.Customer`; компания типа изделия не подставляется. | `GET /api/orders?customer=…` | `OrderCustomerFilterTests.List_FiltersByOrderCustomer_WithoutProductTypeFallback` |
| Пользователь списка | **UC-4.** Выбирает «(не указано)». Видит типы и заказы с `null` в соответствующем поле, а также ПФ без типа или с типом без компании. | Три GET с `customerEmpty=true` | `List_FiltersUnspecifiedCustomer` в каждом наборе integration-тестов |
| Пользователь списка | **UC-5.** Очищает фильтр. Заказчик больше не ограничивает список; остальные фильтры сохраняются. Выбор заказчика и «(не указано)» также работает через И с поиском, активностью, статусом и остальными параметрами конкретного списка. | Существующие GET с комбинацией параметров | `List_CustomerFilterCombinesWithExistingFilters`; Vitest трёх views |
| Пользователь списка | **UC-6.** Вводит фрагмент названия. Получает до 20 подсказок из объединения компаний типов и заказчиков заказов, включая архивные записи; свободное значение не становится фильтром. | `GET /api/producttypes/suggestions/companies?search=…` | Существующие `Suggestions_Companies_*`; `CustomerFilterSelect.spec.js` |
| Пользователь списка / система | **UC-7.** Выбирает название, которого нет ни в одной подходящей записи, либо ошибочно передаёт одновременно `customer` и `customerEmpty=true`. В первом случае получает пустой список (`200`), во втором — `400`. | Три GET списков | `List_UnknownCustomer_ReturnsEmpty`, `List_CustomerAndCustomerEmpty_ReturnsBadRequest` |

Права не меняются. Наладчик по-прежнему может читать типы и ПФ через API, но новых экранов не получает;
наблюдатель использует фильтр только в доступном ему списке заказов.

## Решения

1. **Источник подсказок — существующий endpoint PZP-23.** Новый endpoint и отдельная история вводов не нужны.
   `GET /api/producttypes/suggestions/companies` уже объединяет `ProductType.Company` и `Order.Customer`,
   делает `Distinct`, ищет фрагмент через `ILike`, включает архивные записи, сортирует по алфавиту и возвращает
   не более 20 значений.
2. **Один общий источник для всех трёх экранов.** Подсказка может дать пустой результат в конкретном списке:
   например, заказчик есть только в заказе, но ни одна ПФ не связана с его типом изделия. Это допустимо.
3. **Выбор одного значения, без свободного ввода.** В отличие от поля заказчика в PZP-23, фильтр разрешает только:
   - пустое состояние — все заказчики;
   - «(не указано)»;
   - одно значение из подсказок.
4. **Фильтрация на сервере.** Выбранное название сравнивается точно, как хранится (`=` в PostgreSQL), а не через
   `ILike`. Регистронезависимым остаётся только поиск подсказок. Разные написания свободного текста не склеиваются.
5. **Никакого fallback в заказах.** `Order.Customer = null` означает «не указано» даже если у изделия заказа задана
   компания. Правило показа компании типа в карточке задания на этот фильтр не распространяется.
6. **ПФ без типа считается записью без заказчика.** Такие записи возможны только среди старых ПФ: при выборе
   «(не указано)» они включаются, при выборе конкретного названия — нет.
7. **Фильтр сочетается с остальными через И.** Сортировка, DTO, агрегаты прогресса заказов и права не меняются.
8. **Схема БД не меняется.** `Company` и `Customer` уже хранятся; миграция, сущность заказчика и нормализация
   названий в отдельный справочник не входят в задачу.

## API

Изменяются только параметры трёх существующих GET. Тела ответов и статусы успешных ответов не меняются.

| Метод | Путь | Новые параметры | Правило |
|---|---|---|---|
| GET | `/api/producttypes` | `customer`, `customerEmpty` | `customer` → `p.Company == customer`; `customerEmpty=true` → `p.Company == null` |
| GET | `/api/molds` | `customer`, `customerEmpty` | `customer` → `m.ProductType != null && m.ProductType.Company == customer`; `customerEmpty=true` → `m.ProductType == null \|\| m.ProductType.Company == null` |
| GET | `/api/orders` | `customer`, `customerEmpty` | `customer` → `o.Customer == customer`; `customerEmpty=true` → `o.Customer == null` |
| GET | `/api/producttypes/suggestions/companies` | Без изменений | Используется всеми тремя фильтрами |

### Параметры

| Параметр | Тип | Семантика |
|---|---|---|
| `customer` | `string?` | Одно точное название заказчика. Перед сравнением применяется `CustomerRules.Clean`: Trim, пустая строка → отсутствие фильтра |
| `customerEmpty` | `bool = false` | `true` — только записи без заказчика; `false` или отсутствие параметра не влияет на список |

- Одновременная передача непустого `customer` и `customerEmpty=true` — **400** с сообщением
  «Параметры customer и customerEmpty нельзя передавать вместе.».
- Неизвестное название — **200 и пустой массив**, не ошибка.
- Параметры фильтрации не добавляются в DTO и не сохраняются на клиенте между сеансами.
- Специальное UI-значение для «(не указано)» в query string не передаётся; magic-строки в API не используются.

### Примеры

```http
GET /api/producttypes?isActive=true&customer=ООО%20Ромашка
GET /api/molds?search=Крышка&customerEmpty=true
GET /api/orders?status=Active&customer=ООО%20Ромашка
GET /api/producttypes/suggestions/companies?search=рома
```

## UI

### Общий `CustomerFilterSelect.vue`

Новый компонент в `src/components/common` на основе `el-select` с `filterable`, `remote` и `clearable`.

- Label в форме фильтров — **«Заказчик»**; placeholder — **«Все»**.
- При открытии загружает подсказки через `productTypesApi.suggestCompanies(search)`.
- Ввод фрагмента обновляет только варианты подсказок (debounce 300 мс), но не фильтрует таблицу сам по себе.
- Пункт **«(не указано)»** — отдельная статическая опция, не значение из БД.
- Выбранное значение остаётся видимым, даже если следующий поиск изменил набор подсказок.
- Очистка возвращает состояние «все заказчики».
- Произвольный введённый текст без выбора опции не передаётся в список.
- Наружу компонент отдаёт состояние, которое родительский view преобразует в пару
  `customer` / `customerEmpty`; внутреннее представление специальной опции в API не попадает.
- Ошибка загрузки подсказок не очищает уже выбранное значение и не перезагружает таблицу; пользователь видит
  сообщение об ошибке и может повторить поиск.

`SuggestInput.vue` не меняется: он остаётся контролом свободного текста для форм PZP-22/PZP-23.

### Три списка

Фильтр добавляется между общим поиском и статусом/активностью:

- `views/dictionary/ProductTypeDictionary.vue`;
- `views/dictionary/MoldDictionary.vue`;
- `views/OrdersView.vue`.

Во всех трёх списках загрузка выполняется существующей кнопкой **«Применить»**. Изменение подсказок при вводе
не вызывает GET списка. При применении передаются как новые параметры заказчика, так и все остальные заполненные
фильтры. Новых колонок в таблицы не добавляем.

## Тесты

### xUnit integration

**Типы изделий — `ProductTypesControllerTests`:**

- выбранный `customer` возвращает только типы с точно таким `Company`;
- другое написание по регистру не считается совпадением; неизвестное название возвращает пустой список;
- `customerEmpty=true` возвращает только типы с `Company == null`;
- фильтр работает через И с `isActive` и `search`;
- `customer` вместе с `customerEmpty=true` → 400.

**Пресс-формы — новый `MoldCustomerFilterTests`:**

- выбранный `customer` находит ПФ через `ProductType.Company`;
- компания, встречающаяся только в `Order.Customer`, не создаёт совпадений у ПФ;
- `customerEmpty=true` включает ПФ с типом без компании и старую ПФ с `ProductTypeId == null`;
- конкретный заказчик исключает обе эти категории;
- комбинация с `isActive`/`search`, неизвестное название и конфликт параметров — как у типов.

**Заказы — новый `OrderCustomerFilterTests`:**

- выбранный `customer` учитывает только `Order.Customer`;
- заказ с `Customer == null` не попадает в фильтр по компании типа его изделия и попадает в `customerEmpty=true`;
- заказ с собственным `Customer` фильтруется по нему независимо от отличающейся компании типа;
- комбинация со `status`/`search` и ранее существовавшими `productTypeId`/`productId`;
- неизвестное название → пустой список; конфликт параметров → 400.

Права и существующий endpoint подсказок повторно не перепроектируются: текущие тесты PZP-23 должны остаться зелёными.

### Vitest

**`CustomerFilterSelect.spec.js`:**

- вызывает `suggestCompanies` с введённым фрагментом и показывает возвращённые значения;
- позволяет выбрать только одну подсказку;
- имеет статический пункт «(не указано)» и отличает его от обычного названия;
- очистка восстанавливает состояние «все»;
- свободный текст без выбора не эмитится как заказчик;
- выбранная подпись не теряется при смене набора подсказок;
- ошибка загрузки подсказок не сбрасывает выбор.

**Тесты трёх views:**

- «Применить» передаёт `customer` при выборе названия;
- передаёт `customerEmpty=true` без `customer` для «(не указано)»;
- не передаёт оба параметра после очистки;
- сохраняет существующие фильтры и не запрашивает список на каждый введённый символ в поиске подсказок.

## Документация и версия

- Обновить разделы о типах изделий, пресс-формах и заказах в `docs/user-guide/manager.md`: один заказчик,
  поиск по ранее введённым названиям, пункт «(не указано)».
- CLAUDE.md и доменные ADR не меняются: новых доменных инвариантов нет.
- Перед PR поднять `VERSION` **1.23.0 → 1.24.0** (новая функциональность — минор).

## Вне задачи

- Множественный выбор заказчиков и сохранение фильтров между сеансами.
- Отдельный справочник заказчиков, слияние дубликатов и регистронезависимая нормализация названий.
- Новые колонки заказчика в таблицах.
- Фильтры в заданиях, планировании и отчётах; отчёты по заказчику — PZP-25.
- Изменение состава или лимита существующих подсказок PZP-23.
