# PZP-04 — Журнал «работы без задания» + конвейер обработки цикла

> Дизайн-спека. Дата: 2026-07-25. Статус: утверждён к реализации.
> Связанные: ADR-0006 (эффективное состояние), ADR-0001 (снапшот Cavities), PZP-06 (счётчик на карточке ТПА),
> BL-24 (Гантт), BL-21 (учёт выпуска/сирот при наладке), BL-01 (ресурс ПФ).

## 1. Проблема

Наладчик забыл принять задание: установил ПФ, настроил параметры, запустил ТПА. Станок в Auto выпускает
изделия, но активного задания на ТПА нет → цикл пишется как **сирота**: `ImmCycle` с `TaskId = null`,
`MoldId = null`, `Cavities = 0` (см. [CycleProcessingHandler.cs:99-111](../../../Wintime.Control.Infrastructure/Handlers/CycleProcessingHandler.cs#L99)),
выпуск не засчитывается (`ShouldCountOutput` требует `InProgress`). Эффективный статус отрезка — `Unplanned`
(«работа без задания»). В результате продукция выпущена, а в системе не учтена; ресурс ПФ (смыкания) тоже
не списан.

**Цель:** дать менеджеру **журнал** таких эпизодов и возможность **назначить каждому задание** постфактум,
после чего сироты-циклы привязываются к ПФ задания, а выпуск и ресурс ПФ пересчитываются.

## 2. Ключевые проектные решения

1. **Персистентный журнал, а не эфемерная выборка.** Эпизод — сущность `UnplannedRun`. Причина: журнал
   позволяет **исправить** ошибочную привязку (эфемерный вариант после привязки убрал бы событие из UI).
2. **Эпизод — лёгкий конверт, derive-on-read.** Число сирот-циклов, эффективный `EndTime` и средняя
   длительность цикла **не хранятся** — выводятся агрегатом из уже сохранённых `ImmCycles`. Цикл — источник
   правды. Это устраняет «постоянное обновление эпизода на каждый (в т.ч. 10-секундный) цикл»: за жизнь
   эпизода к нему идёт ~3 записи (создание, закрытие, назначение), а не запись на цикл. Никакой in-memory
   структуры для счётчика — дашборд читает открытый эпизод/агрегат из БД.
3. **Рефактор `CycleProcessingHandler` в конвейер `ICycleHandler`.** Монолитный хендлер (детекция + запись +
   расчёт выпуска) разбивается: детекция остаётся в оркестраторе, производные действия — отдельные хендлеры.
   Журнал сирот становится одним из хендлеров; задел под уведомления (PZP-11/MUN-09).
4. **Двухстадийная долговечность.** Цикл сохраняется в БД **сразу** после детекции завершения, до конвейера.
   Сбой/исключение в производной обработке не теряет данные о смыкании (а выпуск/ресурс отчёт пересчитывает
   из циклов).
5. **Назначение = привязка существующего задания того же ТПА** (вариант А), допустимого по правилу
   смежности во времени (UC-5): без разрыва между заданием и эпизодом либо задание без циклов в ту же дату.
   Задания другого ТПА недопустимы. Создание нового задания из журнала (вариант B) — вне первого среза.
6. **Закрытие эпизода — детерминированно в `StartTask`** (`Issued→Setup`). Явного sweep-воркера нет (B1).

## 3. Акторы и сценарии (use cases)

### Актор: Система (конвейер обработки телеметрии)

**UC-1. Открытие эпизода работы без задания.**
Основной поток: приходит завершённый цикл, активного задания на ТПА нет (`activeTask == null`), режим Auto →
цикл сохранён как сирота (Стадия 1) → `UnplannedRunHandler` проверяет наличие открытого `UnplannedRun`
для ТПА; открытого нет → создаёт (`StartTime = EndTime` цикла, `ClosedAt = null`).
Альтернативы:
- Открытый эпизод уже есть → ничего не создаёт (эпизод продлевается неявно, через деривацию по циклам).
- Исключение в `UnplannedRunHandler` → залогировано, цикл (Стадия 1) не пострадал, прочие хендлеры отработали.
Тест: `UnplannedRunHandlerTests` (открытие, не-дублирование, изоляция сбоя).

**UC-2. Долговечная запись цикла до производной обработки.**
Основной поток: детекция `cycleEnded` → `ImmCycle` создан и сохранён немедленно → затем конвейер.
Альтернатива: сбой в `TaskOutputHandler`/`UnplannedRunHandler` → цикл уже в БД; дрейф денормализованного
`ActualQuantity` допустим (отчёт считает выпуск из `IsSuccessful`-циклов).
Тест: `CycleProcessingHandlerTests` (цикл сохранён даже при исключении хендлера стадии 2).

### Актор: Наладчик (Adjuster)

**UC-3. Закрытие эпизода при запуске задания.**
Основной поток: наладчик наконец принимает задание → `POST /api/tasks/{id}/start` (`Issued→Setup`) →
открытый `UnplannedRun` этого ТПА получает `ClosedAt = now`. После Setup сироты не пишутся (гейтинг циклов).
Альтернатива: открытого эпизода нет → ничего не делаем.
Тест: `StartTask_ClosesOpenUnplannedRun`.

### Актор: Начальник цеха / Менеджер (Manager, Admin)

**UC-4. Просмотр журнала работы без задания.**
Основной поток: `GET /api/unplanned-runs?from&to&immId&assigned` → список эпизодов с деривированными
`cycleCount`, `endTime`, `avgCycleDuration`, именем ТПА, признаком/данными привязанного задания.
Альтернатива: пустой период → пустой список.
Тест: `GetUnplannedRuns_ReturnsDerivedAggregates`.

**UC-5. Получение кандидатов на привязку (правило смежности по времени).**
Основной поток: `GET /api/unplanned-runs/{id}/candidates` → **только задания этого ТПА**
(`task.ImmId == episode.ImmId`; задания другого ТПА не показываются вовсе), из них — только те, у которых
**нет разрыва во времени** с эпизодом. Задание допустимо, если выполнено ЛЮБОЕ условие
(окно эпизода `E = [StartTime, Eend]`, `Eend = COALESCE(ClosedAt, max cycle EndTime)`;
рабочий интервал задания `T = [Tstart, Tend]`, `Tstart = SetupStartedAt ?? StartedAt`,
`Tend = ClosedAt ?? CompletedAt`):
- **(a) пересечение:** `T` пересекается с `E` (`Tstart < Eend AND Tend > StartTime`);
- **(b) сразу после эпизода:** задание — ближайшее, чья работа началась в момент/после конца эпизода, без
  активности между ними (классический «забыл принять»: эпизод и был закрыт стартом этого задания —
  `Tstart ≈ episode.ClosedAt`);
- **(c) сразу перед эпизодом:** задание — ближайшее, закончившееся перед началом эпизода, если разрыв
  между **концом последнего цикла задания** и `StartTime` эпизода **меньше полутора средних длительностей
  цикла эпизода** (`StartTime − task.lastCycleEndTime < 1.5 × avgCycleDuration`); больший разрыв → не смежно;
- **(d) задним числом без следа:** у задания **нет ни одного цикла** и его дата
  (`PlannedDate ?? IssuedAt ?? CreatedAt`) совпадает с датой эпизода — случай, когда задание не выдавали,
  а менеджер создал его постфактум для приведения отчётности в порядок (сюда же попадает выданное, но так и
  не принятое задание — у него тоже нет циклов).

Задания, отделённые от эпизода **положительным разрывом** (между ними была иная активность/простой),
в кандидаты не попадают.

**Рекомендованный кандидат — по приоритету:**

1. задание, **пересекающееся** с эпизодом (a);
2. иначе — задание, **начавшееся сразу после** эпизода (b);
3. иначе — задание, **закончившееся непосредственно перед** эпизодом (c) (с уже применённым порогом
   `< 1.5 × avgCycleDuration`).
Альтернатива: кандидатов нет → пустой список (создание нового задания из журнала — вариант B, вне среза).
Тест: `GetCandidates_SameImmOnly`, `GetCandidates_ExcludesGappedTasks`, `GetCandidates_AllowsAdjacentAndOverlapAndBackdated`, `GetCandidates_RecommendsOverlapThenAfterThenBefore`.

**UC-6. Назначение задания эпизоду (ретро-привязка).**
Основной поток: `POST /api/unplanned-runs/{id}/assign { taskId }` → валидация (задание того же ТПА;
проходит правило смежности UC-5; ПФ имеет тип) → бэкфилл сирот-циклов окна эпизода (`TaskId`, `MoldId`,
`Cavities` = снапшот `Mold.Cavities`) → пересчёт `ActualQuantity`/материала по `IsSuccessful`-циклам →
запись аудита (`AssignedTaskId/AssignedByUserId/AssignedAt`). Ресурс ПФ подхватится (циклы теперь с `MoldId`).
Сервер **обязан перепроверить** смежность и принадлежность ТПА (клиент показывает только допустимых
кандидатов, но верить ему нельзя).
Альтернативы (коды ответов):
- Задание другого ТПА / нарушает правило смежности (разрыв во времени) / ПФ без типа → `400`.
- Эпизод/задание не найдены → `404`.
- Эпизод уже привязан → переназначение (UC-7).
Тест: `AssignTask_BackfillsCyclesAndRecomputesOutput`, `AssignTask_RejectsOtherImm`, `AssignTask_RejectsGappedTask`, `AssignTask_ValidationErrors`.

**UC-7. Переназначение (исправление ошибки).**
Основной поток: повторный `assign` с другим `taskId` → откат бэкфилла прежней привязки (по окну эпизода:
циклы возвращаются в `TaskId = null`, `MoldId = null`, `Cavities = 0`, выпуск прежнего задания уменьшается)
→ применяется новая привязка → аудит перезаписывается.
Тест: `AssignTask_Reassign_RollsBackPreviousBinding`.

## 4. Модель данных

### Сущность `UnplannedRun` (Core/Entities)

```csharp
public class UnplannedRun : BaseEntity
{
    public Guid ImmId { get; set; }
    public DateTime StartTime { get; set; }      // = EndTime первого сироты-цикла
    public DateTime? ClosedAt { get; set; }      // ставится в StartTask; null = открыт
    public Guid? AssignedTaskId { get; set; }    // назначенное задание (ретро-привязка)
    public string? AssignedByUserId { get; set; }// аудит: кто назначил (User.Id)
    public DateTime? AssignedAt { get; set; }    // аудит: когда

    public Imm Imm { get; set; } = null!;
    public ShiftTask? AssignedTask { get; set; }
}
```

**Не хранятся** (derive-on-read из `ImmCycles`): `CycleCount`, эффективный `EndTime`, `AvgCycleDuration`.
Окно эпизода: `EndTime ∈ [StartTime, COALESCE(ClosedAt, now())]`, `TaskId IS NULL` (до назначения)
либо `TaskId = AssignedTaskId` (после — для отображения/переназначения).

### Индексы (миграция `AddUnplannedRun`)

- `UnplannedRuns (ImmId) WHERE ClosedAt IS NULL` — partial, поиск открытого эпизода (крошечный).
- `ImmCycles (ImmId, EndTime) WHERE TaskId IS NULL` — partial, под агрегат деривации и счётчик дашборда.

**Обоснование derive-on-read (перф):** UPDATE в Postgres создаёт новую версию строки (MVCC); индексируемые
колонки при UPDATE плодят записи в индексах. Мы этого избегаем, не обновляя эпизод на каждый цикл вообще —
`CycleCount/EndTime` деривятся из циклов, которые и так пишутся (Стадия 1). Мутируемых горячих колонок в
индексе нет. Даже наивный вариант (~2 UPDATE/сек на 20 ТПА) не был бы узким местом, но derive-on-read чище
и согласуется с «цикл — источник правды».

## 5. Конвейер обработки цикла (рефактор)

**Оркестратор** (`CycleProcessingHandler` после рефактора): только детекция завершения цикла — трекер
(`ICycleTracker`), счётчик, режим, вычисление `cycleEnded`. Формирует контекст `CompletedCycle`
(immId, start/end, mode, isSuccessful, cavities, activeTask?).

**Стадия 1 — долговечность:** оркестратор создаёт `ImmCycle`, `SaveChanges` немедленно.

**Стадия 2 — конвейер `ICycleHandler`** (упорядоченный DI-список, общий `DbContext`, каждый хендлер в
try/catch — сбой одного логируется и не роняет остальные; цикл Стадии 1 не затрагивается):
1. `TaskOutputHandler` — перенос текущей логики выпуска/материала `InProgress`-задания (+ `SetModeAsync`
   при достижении плана; чтение `hasOpenDowntime`).
2. `UnplannedRunHandler` — при `activeTask == null`: открыть эпизод, если открытого нет (UC-1).
3. *(вне среза)* `NotificationHandler` — задел под PZP-11/MUN-09.

Регистрация: `IEnumerable<ICycleHandler>` в DI, порядок явный.

## 6. API — `UnplannedRunController`

Роли: чтение — `Admin, Manager, Adjuster`; назначение — `Admin, Manager`.
Даты из query приводить `DateTime.SpecifyKind(..., Utc)` (правило Npgsql из CLAUDE.md).

| Метод | Endpoint | UC | Назначение |
| --- | --- | --- | --- |
| GET | `/api/unplanned-runs?immId&from&to&assigned` | UC-4 | Список эпизодов + деривированные агрегаты |
| GET | `/api/unplanned-runs/{id}/candidates` | UC-5 | Задания-кандидаты + флаг рекомендованного |
| POST | `/api/unplanned-runs/{id}/assign` | UC-6/7 | Ретро-привязка `{ taskId }` |

## 7. Флоу назначения (транзакционно, один `SaveChanges`)

1. Валидация: задание того же ТПА; проходит правило смежности по времени (UC-5: пересечение / сразу после /
   сразу перед / без следа в ту же дату — иначе `400`); ПФ задания имеет `ProductTypeId` (правило ADR-0007).
2. Если эпизод уже привязан — откат прежнего бэкфилла (UC-7).
3. Бэкфилл сирот-циклов окна (`TaskId IS NULL`): `TaskId = task.Id`, `MoldId = task.MoldId`,
   `Cavities = task.Mold.Cavities` (снапшот, ADR-0001). Трогаем **только** `TaskId IS NULL`.
4. Пересчёт: `task.ActualQuantity += Σ Cavities` по `IsSuccessful`-циклам; материал
   `+= Σ (Cavities · PartWeightGrams) + RunnerWeightGrams` на цикл.
5. `UnplannedRun`: `AssignedTaskId/AssignedByUserId/AssignedAt`. Эпизод остаётся в журнале.

Ресурс ПФ (смыкания) и отчёты подхватываются автоматически (циклы теперь с `MoldId`; отчёт суммирует
выпуск по `IsSuccessful`-циклам). Эффективный таймлайн (`EffectiveStatusTimeline.Build`) — чистая функция,
на следующем построении отрезок станет `Production` (пересчёт не персистится).

## 8. Фронт (первый срез)

- Страница «Журнал работы без задания» (desktop, Manager) — таблица по образцу «Журнала простоев»
  (`MUN-03`): ТПА · начало–конец · циклов · наладчик · задание/«не назначено» · «Назначить».
- Диалог назначения: список кандидатов, рекомендованный подсвечен + подпись «примыкает к заданию №…».
- API-клиент, роут, пункт меню.

## 9. Тесты

- **Unit:** `UnplannedRunHandler` (открытие/не-дублирование/изоляция сбоя); закрытие в `StartTask`;
  эвристика примыкания; assign (бэкфилл/пересчёт/валидации/переназначение с откатом); рефактор-регресс
  `CycleProcessingHandlerTests` (долговечность цикла при сбое стадии 2).
- **Integration:** end-to-end (сироты → журнал → assign → выпуск пересчитан, ресурс ПФ учтён); деривация
  агрегата; роли/коды ответов.
- **Vitest:** компонент журнала + сортировка/подсветка кандидатов.

## 10. ADR-0008

Новый ADR фиксирует: (а) конвейер обработки цикла + двухстадийную долговечность; (б) `UnplannedRun` как
конверт с derive-on-read; (в) ретро-привязку сирот и её влияние на выпуск/ресурс. Обоснование: меняет
паттерн обработки телеметрии и вводит новый контракт — по конвенции ADR оправдан.

## 11. Вне первого среза (follow-ups)

- **PZP-06:** счётчик сирот на карточке ТПА (дешёвый — тот же агрегат по открытому эпизоду); включить, если
  останется время в спринте.
- **BL-24:** Гантт как второе представление журнала (задания + эпизоды на таймлайне).
- **B2:** sweep-воркер явного закрытия по порогу простоя без сирот-циклов (если понадобится живой статус).
- **Вариант B:** создание нового задания из журнала (когда задание не выдавалось вовсе).
- **BL-17:** превентивное уведомление «работа без задания» через `NotificationHandler`.
