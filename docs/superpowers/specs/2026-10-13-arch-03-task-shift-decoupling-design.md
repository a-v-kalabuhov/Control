# ARCH-03 — Развязка задания и смены (задание длиннее смены)

- **Дата:** 2026-10-13
- **Задача:** ARCH-03 (🔴; предпосылка PZP-07 «Планирование на Гантте»). Модель A зафиксирована
  2026-07-23: задание = непрерывный прогон, смена/сутки = ось отчётности (проекция).
- **Статус:** дизайн утверждён, готов к плану реализации
- **ADR:** ADR-0016 «Задание длиннее смены: окно активности и правила отнесения к периоду»
  (пишется в рамках задачи)
- **Предшествующий PR:** переименование `TaskStatus.Draft` → `Planned` (отдельный маленький PR,
  без изменения логики; в этой спеке статус уже называется `Planned`)

## Проблема

Код писался в предположении «задание короче смены». Большая партия идёт через несколько смен и суток,
а с планированием (PZP-07) длинные задания станут нормой.

Выпуск, циклы, статусы и простои уже везде считаются по времени и корректно режутся границами
периода. Ломаются только места, где задание подтягивается в период **по одной точке**:

| # | Где | Сейчас | Что ломается для задания на 3 суток |
|---|---|---|---|
| 1 | `ReportService.GenerateDailyImmItemAsync` (отчёт «Рабочий день») | одно задание с `StartedAt ∈ период`, `FirstOrDefault` | на 2-е и 3-и сутки «Пресс-форма» пусто, «План» = 0, «Расход сырья» = 0; при двух заданиях за сутки — случайное |
| 2 | `ReportService`, отчёт «Наладчики» | задания с `StartedAt ∈ период` и `Status ≥ Completed` | задание, начатое до периода и завершённое в нём, не учитывается |
| 3 | `ShiftWorkCalculator` («Отработано смен», «Время работы») | смена = смена начала задания | прогон на 9 смен = 1 смена |
| 4 | `ReportService`, отчёт «Наладчики по ТПА» | как 2 и 3 | как 2 и 3 |
| 5 | `GET /api/tasks?dateFrom&dateTo` → карточка ТПА (`ImmDetailModal`) | `IssuedAt ∈ смена` | задание выдано вчера и идёт сейчас — на хронологии смены его нет; выданное, но не начатое — есть |

Найдено попутно:

- **«Время наладки» и «Ср. время наладки» в отчётах по наладчикам всегда 0.** Они читают события
  `EventType.Setup`, которые нигде не создаются. Создаются только `Downtime`
  (`DowntimeController`, `DowntimeDetectionWorker`); `Alarm`, `CycleComplete`, `CycleAborted`
  тоже мёртвые.
- **Бар задания на хронологии смены** (`ShiftTimeline.taskStyle`) начинается в
  `startedAt ?? issuedAt`, поэтому наладка не видна, а не начатое задание тянется от момента выдачи.
- `Status >= Completed` захватывает и `Setup = 5`: значения enum идут не в порядке жизненного цикла.
- Комментарий `ShiftTask.Close` — «ручное закрытие в конце дня» — та же ложная модель.

## Акторы и сценарии (use cases)

Термины UI: **карточка ТПА** — окно подробностей ТПА с хронологией смены (`ImmDetailModal` +
`ShiftTimeline`), открывается кликом по плитке ТПА (`ImmCard`) на дашборде.

**UC-1. Менеджер смотрит карточку ТПА, на котором идёт задание, начатое вчера.**
- Основной поток: дашборд → клик по ТПА → хронология текущей смены показывает бар задания от начала
  смены (обрезан) до «сейчас»; если наладка попадает в смену, её отрезок выделен оттенком.
- Альтернативы: задание выдано, но наладка не начата → бара нет (плановые метки — BL-40);
  задание завершилось в середине смены → бар до `CompletedAt`.
- Endpoint: `GET /api/tasks?immId&activeFrom&activeTo`. Тесты: интеграционный на фильтр `active*`,
  Vitest на `taskStyle`.

**UC-2. Менеджер ищет задания на странице «Задания».**
- Основной поток: задаёт одно или несколько полей периода — «Выдано», «Плановая дата», «В работе» —
  и получает задания, удовлетворяющие **всем** заданным условиям.
- Альтернативы: «Выдано» задано → задания без `IssuedAt` (статус «Планируется») исключены;
  «В работе» задано → задания без начатой наладки исключены; ни одно поле не задано → без фильтра по датам.
- Endpoint: `GET /api/tasks?issuedFrom&issuedTo&plannedFrom&plannedTo&activeFrom&activeTo`.
  Тесты: интеграционные на каждый фильтр и на комбинацию через И.

**UC-3. Менеджер смотрит отчёт «Рабочий день» за вторые сутки трёхсуточного задания.**
- Основной поток: строка ТПА показывает ПФ задания, нормативный план за сутки, факт по циклам суток,
  расход сырья по циклам суток.
- Альтернативы: за сутки два задания → ПФ через запятую, план = сумма; последний день партии →
  план не больше остатка плана задания; текущие сутки → план растёт до «сейчас»; задания нет, циклы
  есть (работа без задания) → план 0, факт и расход по циклам.
- Endpoint: `GET /api/reports/daily`. Тесты: unit на формулу плана, интеграционный на отчёт.

**UC-4. Менеджер смотрит отчёт по наладчикам за неделю.**
- Основной поток: по каждому наладчику — выполнено заданий, выполнено наладок, время наладки,
  среднее время наладки (в виде «по ТПА» — то же с разбивкой).
- Альтернативы: наладка началась в воскресенье 23:30, завершилась в понедельник 01:10 → целиком
  относится к периоду, где завершилась; наладка отменена (`CancelSetup`) → не считается;
  задание начато до периода, завершено в нём → «Выполнено заданий» +1.
- Endpoint: `GET /api/reports/assets?reportType=Personnel|PersonnelByImm`, экспорт
  `POST /api/reports/export/excel`. Тесты: интеграционные на каждый случай.

## Решения (зафиксированы при брейнсторминге 2026-10-13)

### 1. Окно активности задания — одно определение на всю систему

`TaskActivityWindow` (чистая функция, `Core/Policies`):

- окно активности = `[SetupStartedAt, CompletedAt ?? ClosedAt ?? now)`; нет `SetupStartedAt` → окна нет;
- окно выпуска = `[StartedAt, CompletedAt ?? ClosedAt ?? now)`; нет `StartedAt` → окна нет.

Задание **относится к периоду `[from, to)`**, если его окно активности пересекается с периодом.
Для EF — один хелпер-выражение, чтобы условие не расходилось с функцией:

```csharp
t.SetupStartedAt != null && t.SetupStartedAt < to
    && ((t.CompletedAt ?? t.ClosedAt) == null || (t.CompletedAt ?? t.ClosedAt) > from)
```

`EffectiveStatusHistoryService` уже реализует эту логику вручную — переводится на общий хелпер без
изменения поведения.

- Отвергнуто: модель B (цепочка сменных заданий + партия) — решено 2026-07-23.
- Отвергнуто: начало окна = `IssuedAt` — выдача не означает работу на ТПА (задание выдают заранее).

### 2. Фильтры списка заданий

`GET /api/tasks` — три независимых диапазона, объединяются через **И**:

| Параметры | Правило | Задания без значения |
|---|---|---|
| `issuedFrom` / `issuedTo` (были `dateFrom` / `dateTo`) | `IssuedAt ∈ [from, to]` — поведение не меняется | исключаются |
| `plannedFrom` / `plannedTo` | `PlannedDate ∈ [from, to]` (`DateOnly`, даты завода) | — (поле обязательно) |
| `activeFrom` / `activeTo` | окно активности пересекается с `[from, to)` | без `SetupStartedAt` исключаются |

`DateTime`-параметры приводятся к UTC через `SpecifyKind` (правило CLAUDE.md).

**Статус по умолчанию.** Без `status` список исключает `Completed`/`Closed` («Активные»). Исключение:
если задан `activeFrom`/`activeTo`, а `status` нет — возвращаются все статусы (задание, завершённое в
периоде, в периоде было в работе; карточке ТПА нужно и оно). Для `issued*`/`planned*` умолчание
«Активные» остаётся. (Решено 2026-10-13; отвергнуто: отменять умолчание любым фильтром периода —
«Выдано за неделю» начал бы показывать архив; параметр `includeArchived` — лишний параметр.)

Фронт:
- **страница «Задания»** (`TaskFilters`): три поля периода — «Выдано», «Плановая дата», «В работе»
  (было одно «Период» = выдача); стор `tasks.js` передаёт соответствующие параметры;
- **карточка ТПА** (`ImmDetailModal`): `activeFrom/To` = границы текущей смены;
- **`ShiftTimeline.taskStyle`**: бар от `setupStartedAt` до `completedAt ?? closedAt ?? сейчас`
  (как у сегментов статусов; обрезается границами смены),
  отрезок `[setupStartedAt, startedAt ?? …)` — оттенком цвета задания.

### 3. Отчёт «Рабочий день»

Задания ТПА за период — все, чьё окно активности пересекается с периодом.

| Колонка | После |
|---|---|
| Пресс-форма | ПФ всех заданий периода через запятую, по порядку `SetupStartedAt` |
| План | **нормативный план за период**, сумма по заданиям (формула ниже) |
| Факт, смыкания, работа/наладка/простой, ср. цикл, простои по причинам | без изменений |
| Расход сырья | по ПФ **каждого цикла**: `Σ (Mold(c.MoldId).PartWeightGrams × c.Cavities + Mold(c.MoldId).RunnerWeightGrams)`; циклы без `MoldId` — 0 |

Факт — по снапшоту `ImmCycle.Cavities`; fallback на ПФ задания убирается (legacy-данных нет).
DTO: `MoldName` остаётся строкой (через запятую) — контракт для фронта не меняется.

**Нормативный план за период** (`Core/Policies`, рядом с `TaskPlanCalculator`). Для задания с
окном выпуска `[S, E)`, `E = CompletedAt ?? ClosedAt ?? now`, планом `P = PlanQuantity`, эталоном
`C = PlannedFullCycleSeconds`, гнёздами `K = Mold.Cavities` (текущие — это прогноз, как в PZP-14):

```
N(t)  = t ≤ S ? 0 : ⌊(min(t, E) − S) / C⌋ × K        // накопленный норматив к моменту t
План[a, b) = min(P, N(b)) − min(P, N(a))
```

Для текущего периода `b` ограничивается «сейчас». `C` не задан или ≤ 0 → план 0. Свойства:
сумма по дням = плану задания (не больше `P`); простои внутри выпуска не вычитаются — это потери,
видные как разрыв план/факт (тот же якорь, что у BL-12); план не зависит от гранулярности периода.

- Отвергнуто: план всей партии + накопленный факт — несопоставимо с фактом за сутки, ломается при
  двух заданиях за сутки.
- Отвергнуто: убрать план из суточного отчёта.

### 4. Отчёты по наладчикам («Наладчики», «Наладчики по ТПА»)

| Колонка | После |
|---|---|
| Выполнено заданий | `Status == Completed` и `CompletedAt ∈ период` |
| **Выполнено наладок** (новая, `CompletedSetups`) | задания наладчика с `StartedAt ∈ период` |
| Время наладки | `Σ (StartedAt − SetupStartedAt)` по тем же наладкам |
| Ср. время наладки | время наладки / выполнено наладок (0 при нуле наладок) |
| Отработано смен | **удаляется** |
| Время работы | **удаляется** |

- Наладка, идущая через границу периода, целиком относится к периоду своего **завершения** —
  количество, сумма и среднее согласованы.
- Наладчик = `ShiftTask.PersonnelId`: переназначение возможно только в `Issued`, до начала наладки.
- Отменённая наладка не считается: `CancelSetup` сбрасывает `SetupStartedAt`.
- Статусы — только явным равенством, не `>=`.
- Учёт рабочего времени персонала — задача СКУД, не Control. Честная атрибуция присутствия
  наладчика в сменах — BL-26 (журнал входов).
- Отвергнуто: засчитывать все смены, которые пересекает задание, — приписывает наладчику смены,
  когда его не было.
- Отвергнуто: оставить смену начала задания — метрика занижена и не имеет смысла для длинных прогонов.

### 5. Уборка

- Удаляются `ShiftWorkCalculator`, `ShiftInstance`, `ShiftWorkCalculatorTests`.
- Из `AssetsPersonnelItemDto`, `AssetsPersonnelByImmItemDto`, `AssetsPersonnelImmBreakdownDto`
  удаляются `WorkedShifts`, `TotalWorkSeconds`; добавляется `CompletedSetups`. Колонки — в
  `AssetsReportView.vue` и в Excel-экспорте.
- `EventType`: удаляются `Alarm`, `Setup`, `CycleComplete`, `CycleAborted`; остаётся `Downtime = 0`.
  Колонка `int`, значение не меняется — миграция не нужна. Поле `Event.EventType` остаётся.
- Комментарий `ShiftTask.Close` — без «в конце дня»; устаревшие формулировки «задание короче смены»
  в `docs/domain`, если найдутся.

## Тестирование

- **xUnit unit:** `TaskActivityWindow` (открытое/закрытое окно, `Closed` без `Completed`, нет
  `SetupStartedAt`); нормативный план (задание внутри суток; трое суток — сумма по дням = `P`;
  норматив исчерпан раньше `E`; текущий день; `Closed` без завершения; `C` не задан).
- **xUnit integration:** фильтры `issued*`/`planned*`/`active*` и их комбинация; «Рабочий день» —
  задание через трое суток, два задания за сутки, циклы без задания; наладчики — наладка через
  полночь, задание начато до периода и завершено в нём, отменённая наладка.
- **Vitest:** `ShiftTimeline.taskStyle` (бар от `setupStartedAt`, отрезок наладки), `TaskFilters`
  (три поля → параметры запроса).
