# PZP-27 — Автоподстановка артикула нового изделия

- **Дата:** 2026-11-05
- **Задача:** PZP-27, блок В фидбека пилота ПЗП
- **Статус:** реализовано 2026-11-05
- **ADR:** не нужен — клиентское удобство заполнения существующей формы без изменения схемы БД, API и доменных инвариантов

## Цель

При добавлении изделия подставлять следующую свободную числовую часть артикула, чтобы менеджеру или
администратору не приходилось вручную просматривать существующие изделия типа. Подставленное значение остаётся
обычным редактируемым текстом: пользователь может заменить его на другое число или буквенный артикул.

## Акторы и сценарии (use cases)

| Актор | Сценарий | Изменяемый код | Тест |
|---|---|---|---|
| Менеджер / админ | **UC-1.** Открывает «Новое изделие» для типа, у которого уже есть изделие `0`. Поле артикула заполнено значением `1`; полный артикул сразу показывается как `<тип>.1`. | `ProductTypeDictionary.vue` | Vitest формы изделия |
| Менеджер / админ | **UC-2.** У типа есть числовые артикулы `0`, `1`, `4` и буквенный `BLK`. Новая форма предлагает `5`, а не первый пропуск `2`; буквенные значения не участвуют в вычислении. | `utils/productArticle.js` | `nextProductArticle` |
| Менеджер / админ | **UC-3.** Среди изделий есть архивные. Их числовые артикулы также учитываются: архивирование не освобождает номер для автоподстановки. | `utils/productArticle.js` | `nextProductArticle` |
| Менеджер / админ | **UC-4.** В типе нет числовых артикулов. Предлагается `0`. При штатном создании типа это встречаться не должно, поскольку сервер сразу создаёт изделие `0`, но правило делает помощник полным. | `utils/productArticle.js` | `nextProductArticle` |
| Менеджер / админ | **UC-5.** Заменяет подставленное значение вручную, например на `BLK` или `10`. Сохраняется именно введённое значение с существующей нормализацией Trim + верхний регистр; автоподстановка больше не перезаписывает поле. | `ProductTypeDictionary.vue` | Vitest формы изделия |
| Менеджер / админ | **UC-6.** Открывает редактирование существующего изделия. Артикул остаётся прежним и не пересчитывается. | `ProductTypeDictionary.vue` | Vitest формы изделия |

Права не меняются: форму используют те же роли, что и раньше. Наладчик и наблюдатель новых возможностей не получают.

## Решения

1. **Только форма создания.** Автоподстановка выполняется в `showProductModal` при открытии нового изделия.
   `editProduct` и существующие записи не затрагиваются.
2. **Источник — уже загруженный `editing.products`.** Дополнительный GET и новый endpoint не нужны. Учитываются
   все изделия текущего типа, включая архивные.
3. **Числовой артикул — непустая строка только из ASCII-цифр `0–9`.** Значения с буквами, знаком, десятичной
   точкой или другими символами не участвуют. Пробелы по краям игнорируются при разборе; сохранённые артикулы уже
   нормализуются сервером.
4. **Следующее значение — `max(числовые артикулы) + 1`; без числовых — `0`.** Пропуски не заполняются. Например:
   - `[]` или только `BLK` → `0`;
   - `0`, `BLK` → `1`;
   - `0`, `1`, `4` → `5`;
   - `0`, `02`, `10` → `11`.
5. **Результат — десятичная строка без ведущих нулей.** Вычисление использует `BigInt`, чтобы длинный числовой
   артикул не потерял точность в JavaScript `Number`. Поскольку кандидат больше каждого существующего числового
   артикула, отдельный цикл «занято — ещё +1» не требуется: условие выполняется самим выбором максимума.
6. **Поле остаётся редактируемым.** Повторное открытие формы вычисляет подсказку заново по актуальным данным типа;
   ввод пользователя в уже открытой форме не отслеживается и не перезаписывается.
7. **Серверная уникальность остаётся окончательной проверкой.** Локальный список может устареть, а полный артикул
   может конфликтовать не только внутри типа, но и с артикулом другого типа. Автоподстановка не обещает глобальную
   уникальность и не заменяет API-валидацию.
8. **API, импорт и БД не меняются.** Через API и будущий импорт PZP-20 артикул по-прежнему передаётся явно.

## API и данные

Изменений нет:

- используется существующий `POST /api/producttypes/{typeId}/products` с явно переданным `article`;
- DTO типа уже содержит `products[].article` и `products[].isActive`;
- миграция, новые поля, параметры и статусы ответов не требуются;
- доменные правила `ProductArticle` и уникальность `FullArticle` остаются единственным источником правды при
  сохранении.

## UI

В `Справочники → Типы изделий → Редактировать → Добавить изделие`:

- поле **«Артикул»** заполнено предложенным следующим номером сразу при открытии;
- подсказка **«Полный артикул»** использует это значение через существующий `fullArticlePreview`;
- пользователь может изменить или очистить поле; пустое значение по-прежнему не проходит клиентскую проверку при
  сохранении;
- остальные поля формы и порядок сохранения не меняются.

Новых кнопок, отдельного режима «авто» и сохранения признака автоподстановки нет.

## Тесты

### Vitest — помощник `nextProductArticle`

- пустой список и список только с буквенными артикулами → `0`;
- стандартное изделие `0` → `1`;
- максимум и пропуски: `0`, `1`, `4`, `BLK` → `5`;
- архивное числовое изделие участвует в максимуме;
- ведущие нули сравниваются по числовому значению;
- значения со знаком, точкой и смешанным содержимым не считаются числовыми;
- длинный числовой артикул увеличивается без потери точности.

### Vitest — `ProductTypeDictionary`

- открытие нового изделия подставляет следующий номер и обновляет предпросмотр полного артикула;
- ручная замена подставленного значения отправляется в `addProduct` без повторного автопересчёта;
- редактирование сохраняет исходный артикул;
- существующий сценарий ошибки уникальности продолжает показывать текст сервера.

## Вне задачи

- Автоподстановка на сервере, в API или импорте Excel.
- Заполнение пропусков вместо увеличения максимума.
- Автоматический повтор сохранения с другим артикулом после конфликта уникальности.
- Перенумерация существующих изделий и изменение буквенных артикулов.
- Глобальная проверка доступности полного артикула до сохранения.
