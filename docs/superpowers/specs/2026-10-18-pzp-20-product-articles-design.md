# PZP-20 — Типы изделий и изделия (артикулы)

- **Дата:** 2026-10-18
- **Задача:** PZP-20 (выявлено на пилоте ПЗП)
- **Статус:** дизайн утверждён, ждёт ревью спеки
- **ADR:** ADR-0020 «Типы изделий и изделия (артикулы)». Заменяет ADR-0007, частично ADR-0009 (п.1 и п.8)

## Проблема

Сейчас пресс-форма привязана к одному «изделию» (`ProductType`), и задание с заказом определяют, что
выпускается, только через ПФ (`task.Mold.ProductTypeId`). На практике одна форма выпускает
несколько товарных позиций, например одну деталь в разных цветах. У каждой позиции свой артикул
(в 1С/CRM), а форма одна. Сейчас различить позиции в заказе и задании нельзя: наладчик не видит,
какой цвет загружать, прогресс заказа не отделяет «чёрный» от «белого».

Одному изделию может соответствовать и несколько ПФ: форма ломается или вырабатывает ресурс, и её
заменяют новой. Эта связь (`ProductType → Mold = 1:N`) сохраняется.

## Решения (зафиксированы при брейнсторминге 2026-10-18)

1. **Двухуровневый каталог.** «Тип изделия» (`ProductType`, бывшее «Изделие» в UI) содержит список
   «изделий» (`Product`). ПФ по-прежнему привязана к **типу**. Заказ и задание ссылаются на **изделие**.
   - Отвергнуто: связь ПФ ↔ изделие многие-ко-многим. Ломает все проверки на ПФ и заставляет
     хранить тип в задании отдельно. Двухуровневая схема оставляет `Mold → ProductType` без изменений.
   - Отвергнуто: заводить отдельную ПФ на каждый цвет. Ресурс, ТО и QR одной физической формы
     разъедутся по нескольким записям.
2. **У типа всегда есть хотя бы одно изделие.** При создании типа автоматически создаётся изделие
   по умолчанию: часть артикула `0`, наименование «По умолчанию». У изделия одно собственное поле
   кроме артикула — наименование.
3. **Полный артикул изделия = `артикул типа + "." + часть артикула изделия`**, например `A123.BLK`,
   `A123.0`. Буквы и точки внутри частей разрешены. Полный артикул — уникальный идентификатор
   изделия в БД.
   - Отвергнуто: запретить точку внутри частей. Склейка стала бы однозначной, но артикулы вида
     `123.А` из 1С было бы не завести.
   - Отвергнуто: склейка без разделителя. Больше коллизий, хуже читается.
4. **Единое пространство артикулов.** Полный артикул изделия не совпадает ни с другим полным
   артикулом, ни с артикулом какого-либо типа (и наоборот). Пример запрещённой ситуации: тип `123.А`
   с изделием `0` и тип `123` с изделием `А.0` дают один полный артикул `123.А.0`. Строка из 1С
   «123.А» должна однозначно указывать на одну сущность.
5. **Артикулы можно править всегда.** При правке артикула типа полные артикулы всех его изделий
   пересчитываются в той же транзакции; при конфликте сохранение откатывается целиком.
   - Отвергнуто: «заморозка» артикула после первого использования. Пользователь выбрал свободную
     правку; история заказов и заданий показывает актуальный артикул.
6. **Архив и удаление.**
   - Архивное изделие нельзя выбрать в новом заказе и задании. Ссылки на него сохраняются.
   - Последнее **активное** изделие активного типа в архив отправить нельзя. Чтобы вывести тип из
     оборота, в архив отправляют сам тип.
   - Изделие, которого нет ни в одном заказе и задании, можно **удалить физически**. Это сознательное
     исключение из правила «никогда не удалять»: у такой записи нет истории. Последнее изделие типа
     удалить нельзя.
   - Добавлять изделия можно в любой момент.
7. **Хранимый `Product.FullArticle` с unique-индексом.** Уникальность полных артикулов гарантирует
   БД. Пересечение с артикулами типов (п.4) проверяет приложение.
   - Отвергнуто: вычислять полный артикул на лету. Уникальность была бы только в приложении,
     поиск по полному артикулу — без индекса.
   - Отвергнуто: единый реестр артикулов (таблица `Articles`). Гарантирует п.4 на уровне БД, но
     требует синхронизации реестра при каждой правке; для справочника на сотни записей избыточно.
8. **В заказе хранится только `Order.ProductId`.** `Order.ProductTypeId` удаляется: тип берётся
   через изделие, иначе два источника правды. Legacy-данных нет — поле убираем без fallback.
9. **Автоподстановка.** Если у типа ровно одно активное изделие, оно подставляется само: в форме
   заказа при выборе типа, в форме задания при выборе ПФ (если задание не привязано к заказу).
10. **Смена цвета на той же ПФ — обычное новое задание.** Норматив наладки и буфер выпуска (PZP-14)
    — инструмент планировщика. Он сам снижает наладку во втором задании, если ПФ не меняется.
    Отдельной логики не нужно.
11. **Рецепты (BL-36) привязываются к изделию.** Каждое изделие — по сути отдельный рецепт. Это
    учитывается при реализации BL-36, в эту задачу не входит.

## Термины

| Термин в UI | Сущность | Пример |
|---|---|---|
| Тип изделия | `ProductType` | `A123` «Крышка 48мм» |
| Изделие | `Product` | часть `BLK` «Чёрный» |
| Полный артикул изделия | `Product.FullArticle` | `A123.BLK` |
| Изделие по умолчанию | `Product` с частью `0` | `A123.0` «По умолчанию» |

## Акторы и сценарии (use cases)

**Акторы:** технолог / руководитель (Manager, Admin) — ведёт справочник; планировщик (Manager,
Admin) — создаёт заказы и задания; наладчик (Adjuster) — видит изделие задания; внешний клиент API.

### UC-1. Создать тип изделия
- **Актор:** технолог.
- **Поток:** Справочники → Типы изделий → «Добавить тип изделия» → артикул и наименование →
  «Сохранить». Тип создаётся вместе с изделием `0` «По умолчанию», окно переходит в режим
  редактирования с блоком «Изделия».
- **Исключения:** артикул пустой → 400; артикул совпадает с артикулом другого типа или с полным
  артикулом любого изделия → 409; полный артикул изделия по умолчанию (`<артикул>.0`) уже занят → 409.
- **Endpoint:** `POST /api/producttypes`. **Тест:** `ProductTypesControllerTests.Create_*`.

### UC-2. Добавить изделие в тип
- **Актор:** технолог.
- **Поток:** в окне типа → «Добавить изделие» → часть артикула и наименование (полный артикул виден
  вживую) → «Сохранить». Доступно в любой момент, в том числе когда по типу уже есть заказы и задания.
- **Исключения:** часть или наименование пустые → 400; полный артикул занят другим изделием или
  совпадает с артикулом типа → 409 с указанием владельца; тип не найден → 404.
- **Endpoint:** `POST /api/producttypes/{id}/products`. **Тест:** `ProductsApiTests.Add_*`,
  в том числе коллизия `123.А`+`0` против `123`+`А.0`.

### UC-3. Переименовать артикул типа или изделия
- **Актор:** технолог.
- **Поток:** правит артикул типа → все полные артикулы его изделий пересчитываются. Или правит часть
  артикула изделия → пересчитывается его полный артикул. Наименования правятся без ограничений.
- **Исключения:** любой пересчитанный полный артикул конфликтует (п.4) → 409, ничего не сохраняется.
- **Endpoint:** `PUT /api/producttypes/{id}`, `PUT /api/producttypes/{id}/products/{pid}`.
  **Тест:** `ProductsApiTests.RenameType_RecomputesFullArticles`, `RenameType_Conflict_RollsBack`.

### UC-4. Отправить изделие в архив / вернуть
- **Актор:** технолог.
- **Поток:** «В архив» в строке изделия. Изделие пропадает из выбора в формах заказа и задания.
  Существующие заказы и задания ссылку сохраняют. «Вернуть» возвращает его в выбор.
- **Исключения:** последнее активное изделие активного типа → 409 «Это последнее активное изделие
  типа. Чтобы вывести тип из оборота, переведите в архив сам тип».
- **Альтернатива:** у архивного типа изделия архивируются и возвращаются без ограничений. Вернуть
  из архива тип, у которого нет ни одного активного изделия, нельзя → 409 «Сначала верните из
  архива хотя бы одно изделие типа».
- **Endpoint:** `PUT /api/producttypes/{id}/products/{pid}` (`isActive`),
  `PUT /api/producttypes/{id}` (`isActive`). **Тест:** `ProductsApiTests.Archive_*`,
  `ProductTypesControllerTests.Restore_WithoutActiveProducts_Conflict`.

### UC-5. Удалить изделие
- **Актор:** технолог.
- **Поток:** «Удалить» (кнопка видна только у неиспользованного изделия) → подтверждение → изделие
  удаляется физически.
- **Исключения:** изделие есть в заказе или задании → 409 «Изделие используется в заказах или
  заданиях — его можно только отправить в архив»; изделие последнее у типа → 409.
- **Endpoint:** `DELETE /api/producttypes/{id}/products/{pid}`. **Тест:** `ProductsApiTests.Delete_*`.

### UC-6. Создать или изменить заказ
- **Актор:** планировщик.
- **Поток:** «Создать заказ» → тип изделия → изделие (если активное одно — подставлено) → номер,
  срок, количество → «Сохранить».
- **Альтернатива:** правка заказа без привязанных заданий — изделие можно сменить.
- **Исключения:** изделие архивное или его тип архивный → 400; смена изделия при привязанных
  заданиях → 409.
- **Endpoint:** `POST /api/orders`, `PUT /api/orders/{id}`. **Тест:** `OrdersCrudTests.*Product*`.

### UC-7. Создать задание
- **Актор:** планировщик.
- **Поток:** ТПА → ПФ → изделие (из изделий типа ПФ; одно активное — подставлено) → заказ (активные
  заказы на это изделие, необязательно) → остальные поля → «Сохранить».
- **Альтернатива:** «Создать задание» из карточки заказа — изделие взято из заказа и заблокировано,
  ПФ отфильтрованы по типу изделия заказа.
- **Исключения:** изделие не указано → 400; изделие не принадлежит типу ПФ → 400; изделие или его
  тип в архиве → 400; у ПФ не задан тип → 400 «У пресс-формы не задан тип изделия»; изделие заказа
  не совпадает с изделием задания → 400.
- **Endpoint:** `POST /api/tasks`. **Тест:** `TaskProductGuardTests.*`.

### UC-8. Сменить изделие в задании
- **Актор:** планировщик.
- **Поток:** «Ред.» у задания в статусе «Планируется» без заказа → выбирает другое изделие типа ПФ.
- **Исключения:** статус не «Планируется» → 400; задание привязано к заказу → 400 (изделие диктует
  заказ); изделие чужого типа или архивное → 400.
- **Endpoint:** `PUT /api/tasks/{id}`. **Тест:** `TaskProductGuardTests.Update_*`,
  unit `ShiftTaskSetProductTests`.

### UC-9. Привязать задание к заказу
- **Актор:** планировщик.
- **Поток:** из формы задания (`set-order`) или из карточки заказа («Привязать существующее» —
  в списке незавершённые задания без заказа с тем же изделием).
- **Исключения:** изделие задания ≠ изделию заказа → 400 «Изделие задания не совпадает с изделием
  заказа»; заказ не активен → 400.
- **Endpoint:** `POST /api/tasks/{id}/set-order`, `POST /api/orders/{id}/tasks`.
  **Тест:** `TaskOrderBindingApiTests.*`, `OrderTaskBindingApiTests.*`, unit `OrderTaskBindingTests`.

### UC-10. Наладчик видит изделие задания
- **Актор:** наладчик.
- **Поток:** в мобильной карточке задания и в деталях задания видит полный артикул и наименование
  изделия рядом с ПФ — понимает, какой материал или краситель загружать.
- **Endpoint:** `GET /api/tasks/my` и др. (поля `TaskDto`). **Тест:** Vitest `MobileTaskCard.spec`.

### UC-11. Внешний клиент API
- `POST /api/tasks` и `POST /api/orders` без `productId` или с чужим/архивным изделием → 400.

## Модель данных

```csharp
public class ProductType : BaseEntity        // «Тип изделия»
{
    public string Article { get; set; }       // уникален; не совпадает ни с одним Product.FullArticle
    public string Name { get; set; }
    public bool IsActive { get; set; } = true;
    public ICollection<Mold> Molds { get; set; }
    public ICollection<Product> Products { get; set; }   // всегда ≥ 1
}

public class Product : BaseEntity            // «Изделие»
{
    public Guid ProductTypeId { get; set; }   // обязателен, FK Restrict
    public ProductType? ProductType { get; set; }
    public string Article { get; set; }       // часть артикула, заглавными
    public string Name { get; set; }          // обязательно
    public string FullArticle { get; set; }   // ProductType.Article + "." + Article; unique-индекс
    public bool IsActive { get; set; } = true;
}

// Mold.ProductTypeId — без изменений.
// Order:     - ProductTypeId,  + Guid ProductId (обязателен)
// ShiftTask: + Guid ProductId (обязателен)
```

**Нормализация.** Сервер делает `Trim()` и `ToUpperInvariant()` для артикула типа и части
артикула изделия (сейчас заглавные обеспечивает только фронт). Поэтому unique-индекс по
`FullArticle` — обычный, без `lower()`. Склейка и нормализация — чистая функция
`ProductArticle.Compose(typeArticle, part)` в `Core/Policies`.

## Инварианты (нарушение = баг)

1. `FullArticle` уникален в БД и не совпадает ни с одним `ProductType.Article`; артикул типа не
   совпадает ни с одним `FullArticle`.
2. У типа всегда ≥ 1 изделия; у активного типа — ≥ 1 активного изделия (держат два запрета:
   архивировать последнее активное изделие активного типа и вернуть из архива тип без активных
   изделий).
3. Архивное изделие и изделия архивного типа нельзя выбрать в новом заказе или задании; ссылки
   сохраняются.
4. Физически удаляется только изделие без заказов и заданий и не последнее у типа.
5. Правка артикула типа пересчитывает `FullArticle` всех его изделий в той же транзакции.
6. `task.Product.ProductTypeId == task.Mold.ProductTypeId`.
7. Привязка задания к заказу — только при `task.ProductId == order.ProductId`.
8. Изделие задания меняется только в `Planned` и только без заказа. Изделие заказа не меняется при
   привязанных заданиях.
9. Тип ПФ нельзя сменить, если по ней есть задания (правило ADR-0007 сохраняется) — оно держит
   инвариант 6.

## API

### Справочник типов изделий (`ProductTypesController`)

Роли: запись — Admin, Manager; чтение — ещё и Adjuster.

| Endpoint | Поведение |
|---|---|
| `POST /api/producttypes` | Создаёт тип + изделие `0` «По умолчанию» в одной транзакции |
| `PUT /api/producttypes/{id}` | При смене `Article` пересчитывает `FullArticle` изделий типа |
| `GET /api/producttypes`, `GET /api/producttypes/{id}` | `ProductTypeDto` + `Products[]`. Поиск — по артикулу и наименованию типа, полному артикулу и наименованию изделия |
| `POST /api/producttypes/{id}/products` | Добавить изделие |
| `PUT /api/producttypes/{id}/products/{pid}` | Правка `article`, `name`, `isActive` |
| `DELETE /api/producttypes/{id}/products/{pid}` | Удалить неиспользованное изделие |

```csharp
public class ProductDto
{
    public Guid Id { get; set; }
    public string Article { get; set; }       // часть
    public string FullArticle { get; set; }
    public string Name { get; set; }
    public bool IsActive { get; set; }
    public bool IsUsed { get; set; }           // есть в заказах или заданиях — UI скрывает «Удалить»
}
// ProductTypeDto: + List<ProductDto> Products
// CreateProductRequestDto { Article, Name }; UpdateProductRequestDto { Article?, Name?, IsActive? }
```

**Проверка уникальности** — приватный помощник контроллера (все изменения артикулов идут через
него):
- кандидат на артикул типа сверяется с `FullArticle` всех изделий;
- каждый кандидат на `FullArticle` сверяется с `FullArticle` других изделий и с артикулами всех
  типов;
- unique-индекс — подстраховка от гонки: `DbUpdateException` по нарушению уникальности
  превращается в тот же 409.

Сообщение называет конфликт и владельца: «Полный артикул 123.А.0 уже есть у изделия «По умолчанию»
(тип 123.А)», «Артикул 123.А совпадает с полным артикулом изделия «Чёрный» (тип 123)».

### Политики (`Core/Policies`)

- `ProductArticle.Compose(typeArticle, part)` и `Normalize(article)`.
- `ProductSelection.EnsureSelectable(Product product)` — изделие и его тип активны, иначе
  `DomainException`.
- `OrderTaskBinding.EnsureCanBind(Order order, Guid taskProductId)` — заказ активен и
  `order.ProductId == taskProductId`. Проверка «у ПФ не задан тип» отсюда уходит.

### Сущность `ShiftTask` (ADR-0002)

`SetProduct(Guid productId)` — `DomainException`, если `Status != Planned` или `OrderId != null`.
Принадлежность изделия типу ПФ и выбираемость проверяет контроллер.

### Задания (`TasksController`)

- `CreateTaskRequestDto`: + `Guid? ProductId` (обязателен, `null` → 400). Проверки: изделие
  существует, `EnsureSelectable`, `product.ProductTypeId == mold.ProductTypeId`. Если у ПФ нет
  типа — прежнее сообщение «У пресс-формы не задан тип изделия». При `OrderId` —
  `EnsureCanBind(order, request.ProductId)`.
- `UpdateTaskRequestDto`: + `Guid? ProductId` → `task.SetProduct` + те же проверки изделия.
- `SetOrder`: `EnsureCanBind(order, task.ProductId)`.
- `TaskDto`: + `ProductId`, `ProductFullArticle`, `ProductName`, `ProductTypeName`.
- Поиск заданий (`TasksController.cs:138`): + `Product.FullArticle`, `Product.Name`.

### Заказы (`OrdersController`)

- `CreateOrderRequestDto`: `ProductTypeId` → `ProductId`. `UpdateOrderRequestDto`: `ProductTypeId?` →
  `ProductId?`; смена при привязанных заданиях → 409 «Нельзя сменить изделие заказа: к нему
  привязаны задания».
- `OrderDto`: `ProductId`, `ProductFullArticle`, `ProductName`, `ProductTypeId`, `ProductTypeName`
  (тип — вычисляемый через изделие). `ProductTypeArticle` уходит.
- `GET /api/orders`: фильтры `productTypeId` (через `Product.ProductTypeId`) и новый `productId`.
- `AttachTask`: `EnsureCanBind(order, task.ProductId)`.
- `OrderTaskSummaryDto`: + `ProductFullArticle`.

### Прочее

- `UnplannedRunController.Assign`: проверка `task.Mold.ProductTypeId == null` (`:167`) удаляется.
  В метках эпизода (`:71`) и кандидатов (`:145`) — полный артикул изделия.
- `ImmDto`: + `CurrentProductArticle` (полный артикул изделия текущего задания).

## UI

## Миграция `AddProducts`

Одна миграция, данные переносятся SQL внутри неё:

1. `UPDATE "ProductTypes" SET "Article" = upper(trim("Article"))`.
2. Таблица `Products` (FK на `ProductTypes` `Restrict`, unique-индекс `FullArticle`).
3. Каждому типу — изделие `0` «По умолчанию», `FullArticle = "Article" || '.0'`.
4. `ShiftTasks.ProductId` (nullable) ← изделие по умолчанию типа ПФ задания. Если у задания ПФ без
   типа — `RAISE EXCEPTION` с понятным сообщением (присвоить тип ПФ до обновления). Затем NOT NULL
   + FK `Restrict`.
5. `Orders.ProductId` (nullable) ← изделие по умолчанию `Orders.ProductTypeId`. NOT NULL + FK
   `Restrict`. Удалить `Orders.ProductTypeId` и его индекс/FK.

Перед выкаткой на ПЗП миграция прогоняется на копии их БД. `Mold.ProductTypeId` NOT NULL (BL-35) —
отдельная задача.
