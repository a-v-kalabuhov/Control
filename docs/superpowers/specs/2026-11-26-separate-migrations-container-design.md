# TD-06: отдельный one-shot контейнер EF Core-миграций

- **Дата:** 2026-11-26
- **Статус:** дизайн согласован в brainstorming; спека ожидает пользовательского ревью
- **Основная цель:** надёжный и явный порядок применения миграций перед запуском API

## 1. Контекст и проблема

Сейчас `Wintime.Control.API` при старте синхронно вызывает `ControlDbContext.Database.Migrate()` в `Program.cs`. В том же блоке выполняются создание демо-пользователей, первого production-администратора и смены по умолчанию.

Из-за этого изменение схемы БД является побочным эффектом запуска web-приложения. Порядок обновления и причина сбоя видны только через жизненный цикл и логи API. При нескольких экземплярах API автоматическая миграция также создавала бы гонку за изменение схемы.

Для текущих одиночных Docker Compose-установок нужен более простой и явный процесс: PostgreSQL готов → отдельный migrator применил миграции и завершился успешно → запустился API.

## 2. Цели и нецели

### Цели

1. Убрать применение миграций из API во всех средах.
2. Создать отдельное консольное приложение `Wintime.Control.Migrations` на .NET 9.
3. Использовать одно и то же приложение для локальной разработки и Docker Compose.
4. Гарантировать при `docker compose up`, что API запускается только после успешного завершения миграций.
5. При штатном обновлении останавливать старый API до миграций и не запускать новый API после их сбоя.
6. Выпускать образы API и migrator одной версией.
7. Сохранить существующую прикладную инициализацию API и прохождение интеграционных тестов.
8. Охватить dev, demo, PZP и все smoke Compose-конфигурации, включая восстановление report-дампа и сброс демо-БД.

### Нецели

- Отдельные пользователи/роли PostgreSQL и разграничение DDL/DML-прав.
- Retry-политика, автоматический rollback БД и автоматическое резервное копирование.
- Zero-downtime deployment и поддержка одновременной работы старой и новой версий API.
- Запуск миграций при каждом `docker restart api`, автоматическом restart после сбоя или перезагрузке хоста.
- Kubernetes/Docker Swarm job или общий deployment supervisor.
- Перенос доменных сидов в migrator.
- Новые EF-миграции, изменения схемы, HTTP API и доменных инвариантов.

## 3. Акторы и сценарии (use cases)

### Акторы

- **Разработчик** — подготавливает локальную БД и запускает API через `dotnet run`.
- **Инженер развёртывания / deploy-скрипт** — обновляет установку и анализирует результат миграций.
- **Docker Compose** — упорядочивает запуск сервисов по healthcheck и коду завершения.
- **Migrator** — единственный компонент, который применяет EF Core-миграции.
- **API** — выполняет прикладную инициализацию и обслуживает запросы только на подготовленной схеме.
- **PostgreSQL** — принимает миграции и хранит `__EFMigrationsHistory`.
- **Тестовый runner** — проверяет migrator и API на изолированной Testcontainers-БД.

### UC-1. Локальный запуск на пустой БД

1. Разработчик запускает PostgreSQL.
2. Выполняет `dotnet run --project Wintime.Control.Migrations`.
3. Migrator применяет все миграции и возвращает `0`.
4. Разработчик запускает `Wintime.Control.API`.
5. API не меняет схему, выполняет существующий прикладной сид и начинает обслуживать запросы.

Если шаг 2 завершился ошибкой, API разработчик не запускает; повторный запуск migrator после исправления причины продолжает с фактически применённого состояния `__EFMigrationsHistory`.

### UC-2. Чистая установка через Compose

1. Compose дожидается healthy PostgreSQL.
2. One-shot контейнер `migrations` применяет миграции и завершается с кодом `0`.
3. Compose запускает API благодаря `service_completed_successfully`.
4. API создаёт положенные демо-/bootstrap-данные и смену по умолчанию.
5. `/health` подтверждает доступность API.

### UC-3. Успешное обновление

1. Deploy-скрипт получает образы API и migrator одной версии.
2. Останавливает старый API.
3. Явно пересоздаёт one-shot service миграций, чтобы новый запуск не зависел от результата предыдущего контейнера.
4. После успешного migrator запускает новый API.
5. Скрипт проверяет `/health` и версии обоих образов.

Повторное применение уже установленной версии является успешным no-op, если новых миграций нет.

### UC-4. Ошибка миграции при обновлении

1. Старый API уже остановлен.
2. Migrator возвращает ненулевой код и пишет ошибку без секретов.
3. Compose не запускает API; deploy-скрипт завершается ошибкой и показывает лог миграций.
4. Система остаётся недоступной до исправления причины и успешного повторного запуска.

Уже применённые миграции не откатываются автоматически. Старый API не возобновляет работу, поскольку схема могла частично обновиться.

### UC-5. Сброс демо-БД

1. `reset-db.sh` останавливает API, пересоздаёт PostgreSQL volume и дожидается healthy PostgreSQL.
2. Migrator создаёт актуальную схему.
3. API запускается и создаёт демо-аккаунты.
4. API останавливается на время загрузки большого SQL-сида.
5. После загрузки повторный migrator выполняет no-op, затем API запускается.

### UC-6. Smoke-стенд с готовым report-дампом

1. PostgreSQL восстанавливает дамп, содержащий схему, данные и историю миграций.
2. Healthcheck с достаточным `start_period` не пропускает запуск во время восстановления.
3. Migrator применяет только более новые миграции.
4. API запускается на полностью восстановленной и актуальной БД.

### UC-7. Интеграционные тесты API

1. `IntegrationTestFactory` запускает Testcontainers-PostgreSQL.
2. До первого обращения к `WebApplicationFactory.Services` fixture вызывает runner нового migrator.
3. Запуск хоста выполняет только прикладной сид.
4. Тесты добавляют свои данные и выполняются на подготовленной схеме.

## 4. Архитектура приложения

### 4.1. `Wintime.Control.Migrations`

Новый консольный проект добавляется в `Wintime.Control.sln` и ссылается на `Wintime.Control.Infrastructure`. Используется существующий `ControlDbContext`; отдельная модель и копии миграций не создаются.

Обязанности приложения:

1. Построить конфигурацию из `appsettings.json` и переменных окружения.
2. Проверить наличие `ConnectionStrings:DefaultConnection`.
3. Зарегистрировать `ControlDbContext` с Npgsql.
4. Вызвать `await Database.MigrateAsync()`.
5. Вернуть `0` при успехе и ненулевой код при любой ошибке.

Логика оформляется как небольшой тестируемый runner, принимающий конфигурацию и возвращающий код результата. Точка входа консольного проекта только собирает конфигурацию, настраивает console logging и возвращает код runner. Это позволяет integration-тестам вызывать тот же код без глобального изменения environment variables тестового процесса.

Migrator не регистрирует Identity, MQTT, hosted services, controllers, Serilog-пайплайн API и доменные сиды. EF CLI и `dotnet ef` в runtime-образ не входят.

### 4.2. Изменение API

Из блока инициализации в `Wintime.Control.API/Program.cs` удаляется только:

```csharp
db.Database.Migrate();
```

Остаются без изменения по смыслу:

- демо-пользователи при `DemoMode=true`;
- первый production-администратор из `Bootstrap:AdminPassword`;
- смена по умолчанию при отсутствии смен.

В Development, Test и Production не появляется конфигурационный fallback с автоматической миграцией. API больше не является способом изменения схемы.

### 4.3. Локальная конфигурация

`Wintime.Control.Migrations/appsettings.json` содержит тот же локальный connection string по умолчанию, что API:

```text
Host=localhost;Database=WintimeControlDb;Username=postgres;Password=password;
```

Переменная `ConnectionStrings__DefaultConnection` переопределяет его в Docker и других средах. Пароль в лог не выводится.

Нормальная локальная последовательность:

```powershell
dotnet run --project Wintime.Control.Migrations
dotnet run --project Wintime.Control.API
```

Команда `dotnet ef migrations add` остаётся способом создавать новые миграции. `dotnet ef database update` убирается из документированного штатного процесса: применение выполняет новый migrator.

## 5. Docker-образы и версионирование

Для migrator добавляются два Dockerfile по существующим паттернам репозитория:

- `Wintime.Control.Migrations/Dockerfile.prod` — `dotnet/runtime:9.0`, копирует локально собранное `publish/migrations`, запускается под непривилегированным пользователем;
- `Wintime.Control.Migrations/Dockerfile.dev` — SDK stage для restore/publish и runtime stage, frontend не собирает.

Версии образов не различаются:

- demo: `ghcr.io/a-v-kalabuhov/control/api` и `ghcr.io/a-v-kalabuhov/control/migrations` получают одинаковый тег из файла `VERSION`; при публикации `latest` обновляется у обоих;
- PZP: `wintime/api:pilot` и `wintime/migrations:pilot`;
- smoke: `wintime/api:smoke-test` и `wintime/migrations:smoke-test`.

В demo Compose и deploy-скрипте `API_TAG` заменяется на `APP_VERSION`, поскольку одна переменная теперь относится к двум образам. PZP/smoke сборки и offline-пакеты дополнительно включают publish, build, save/load образа миграций.

## 6. Контракт Docker Compose

В каждый Compose-файл с API добавляется однотипный сервис с окружением конкретной БД:

```yaml
services:
  migrations:
    image: ghcr.io/a-v-kalabuhov/control/migrations:${APP_VERSION}
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      ConnectionStrings__DefaultConnection: "Host=postgres;Database=WintimeControlDb;Username=postgres;Password=${DB_PASSWORD};"
    restart: "no"
    networks: [wtctrl]

  api:
    image: ghcr.io/a-v-kalabuhov/control/api:${APP_VERSION}
    depends_on:
      migrations:
        condition: service_completed_successfully
      mosquitto:
        condition: service_started
    # Остальные environment, ports, volumes, restart и limits сохраняются.
```

Для dev/PZP/smoke меняются image, имя БД, сеть, logging и limits согласно конкретному файлу; семантика зависимости одинаковая. API больше не полагается непосредственно на `postgres: service_healthy`: эта часть цепочки инкапсулирована в зависимости migrator. Прямая зависимость API от Mosquitto сохраняется.

`migrations` не получает `restart: unless-stopped`. Завершённый контейнер остаётся доступен для `docker compose ps -a` и `docker compose logs migrations` до следующего явного пересоздания.

Гарантия относится к запуску через `docker compose up`. `docker restart api` и Docker restart policy не обязаны запускать миграции и не расширяют согласованный инвариант.

Охватываются:

- `docker-compose.dev.yml`;
- `deploy/demo/package/docker-compose.yml`;
- `deploy/pzp/package/docker-compose.prod.yml`;
- `deploy/smoke-test/package/docker-compose.test.yml`;
- `deploy/smoke-test/package/docker-compose.pzp.yml`;
- `deploy/smoke-test/package/docker-compose.test-report.yml`.

## 7. Потоки запуска и обновления

### 7.1. Обычный Compose-запуск

`docker compose up -d` использует декларативную цепочку зависимостей. API не стартует при ненулевом завершении миграций.

### 7.2. Штатный deploy

Deploy-скрипты не полагаются на неявное повторное использование старого exited-контейнера. Нормативный поток demo:

1. `docker compose pull api migrations`;
2. записать общую `APP_VERSION`;
3. `docker compose stop api`;
4. `docker compose up -d --force-recreate migrations api`.

Явное пересоздание гарантирует новый запуск миграций, а Compose упорядочивает запуск перечисленных сервисов по `depends_on`. PZP/smoke используют тот же поток с соответствующим Compose-файлом.

При ошибке скрипт показывает `logs migrations` и `logs api` (если API успел запуститься на последующем этапе проверки), завершается ненулевым кодом и не выполняет проверку успешного релиза. Старый API повторно не запускается.

### 7.3. Сброс демо-БД

В `reset-db.sh` оба запуска API заменяются потоком «пересоздать migrations и api». Первый запуск создаёт схему и демо-аккаунты до загрузки большого сида. Второй после сида повторно проверяет отсутствие новых миграций и запускает API.

### 7.4. Report-дамп

Сервис миграций запускается только после существующего healthcheck PostgreSQL с `start_period: 15m`. Комментарии и документация обновляются: более новые миграции после восстановления применяет migrator, не API.

## 8. Ошибки и эксплуатационные последствия

| Ситуация | Поведение |
|---|---|
| Нет connection string | Понятная ошибка конфигурации, ненулевой exit code |
| PostgreSQL недоступен | Ошибка подключения, ненулевой exit code; retry не выполняется |
| Миграция выбросила исключение | Исключение логируется без строки подключения/пароля, ненулевой exit code |
| Новых миграций нет | Успешный no-op, exit code `0` |
| Повторный запуск после частичного прогресса | EF использует фактическое содержимое `__EFMigrationsHistory`; автоматический rollback не выполняется |
| Сбой во время обновления | API остаётся остановленным, deploy неуспешен |
| Разные версии образов | Штатные скрипты не допускают этого через общий `VERSION`/тег и проверяют обе версии |

Ограничение доступности сознательно принято: старый код не должен работать со схемой, которая могла частично обновиться. Резервное копирование перед реальным обновлением остаётся отдельной эксплуатационной процедурой и не расширяет TD-06.

## 9. Тестирование и критерии приёмки

### 9.1. Автоматические .NET-тесты

В существующий integration-проект добавляются xUnit-тесты runner миграций против Testcontainers-PostgreSQL:

1. **Пустая БД:** результат `0`; список строк `__EFMigrationsHistory` совпадает со списком миграций текущей сборки.
2. **Повторный запуск:** результат `0`; набор применённых миграций не изменился.
3. **Ошибка конфигурации/подключения:** ненулевой результат; API в этом тесте не участвует. Для недоступного адреса используется короткий Npgsql timeout, чтобы тест не зависал.

`IntegrationTestFactory` вызывает тот же runner миграций до запуска хоста, не создавая отдельный тестовый способ применения схемы. Все существующие unit- и integration-тесты должны пройти без возврата `Migrate()` в API.

### 9.2. Сборка

- `Wintime.Control.sln` собирается с новым проектом.
- Production publish migrator не требует frontend.
- Локально собираются production-образы API и migrator.
- Demo push, PZP save и smoke save включают образ миграций; offline-пакет содержит всё необходимое для его загрузки.

### 9.3. Compose smoke

Минимальные проверки выполняются на smoke/dev-окружении без полного демо-сида:

1. **Чистая БД:** migrator завершается раньше старта API; `/health` возвращает успех; bootstrap/смена по умолчанию созданы.
2. **Повторный `compose up`:** успешный no-op миграций, отсутствие ошибок и гонок.
3. **Намеренный сбой:** неверная конфигурация только migrator приводит к ненулевому завершению, API не запускается.
4. **Обновление:** старый API останавливается до миграций; после успеха запускаются образы одной новой версии.
5. **Сбой обновления:** после ошибки migrator API остаётся остановленным, deploy сообщает ошибку и выводит лог миграций.
6. **Report-дамп:** migrator ждёт завершения восстановления и применяет только отсутствующие миграции.

Сценарий `reset-db.sh` проверяется на тестовом окружении по тем же переходам состояний. Полный 45–60-минутный демо-сид не требуется для проверки механизма миграций; окончательная проверка полного сброса выполняется при ближайшем реальном демо-деплое и не блокирует автоматические тесты TD-06.

### 9.4. Итоговые критерии

- В API отсутствуют `Database.Migrate()` и `MigrateAsync()` как стартовая инициализация.
- Во всех перечисленных Compose-файлах API зависит от `service_completed_successfully` migrator.
- Один и тот же код migrator работает локально и в контейнере.
- При ошибке миграции штатный deploy не оставляет работающий API.
- Прикладные сиды остаются идемпотентными: повторный запуск API не дублирует записи.
- Существующие и новые тесты зелёные; собраны оба образа; задокументированы запуск и диагностика.

## 10. Документация и ADR

В фазе реализации:

1. Создаётся **ADR-0033** о выделении EF Core-миграций в one-shot application/container, с альтернативами и последствиями.
2. В `CLAUDE.md` обновляются команды локального запуска и добавляется правило: схему применяет `Wintime.Control.Migrations`, API миграции не выполняет.
3. Обновляются demo/PZP/smoke инструкции, комментарии Compose и `reset-db.sh`.
4. В описание TD-06 после выполнения добавляются PR и ADR; задача переносится в архив беклога по обычному процессу.

## 11. Рассмотренные альтернативы

### 11.1. Режим `--migrate-only` в API

Плюс: один образ и меньше изменений сборки. Минусы: migrator сохраняет все зависимости web-приложения, конфигурацию и риск лишней инициализации; граница ответственности остаётся размытой. Отклонено.

### 11.2. `dotnet ef database update` в SDK-контейнере

Плюс: не нужен новый .NET-проект. Минусы: SDK/EF tooling в deployment, дополнительные `--project`/`--startup-project`, более тяжёлый и хрупкий запуск. Отклонено.

### 11.3. Оставить автомиграции в Development

Плюс: короче локальный запуск. Минусы: два механизма применения схемы, различие сред и риск случайного включения вне разработки. Отклонено; локально используется тот же migrator.

### 11.4. Оставлять старый API работающим при сбое

Плюс: меньше downtime. Минус: старый код может работать с уже изменённой схемой; корректность потребовала бы backward-compatible expand/contract-процесса. Для текущего одиночного развёртывания отклонено.

## 12. Оценка и сложность

Предварительная оценка реализации: **1–2 дня**.

Признаки сложности: новый исполняемый проект, два новых Dockerfile, изменение контракта запуска и нескольких независимых deployment-пакетов, явная подготовка БД в интеграционных тестах. Новых EF-миграций, endpoint’ов и доменных инвариантов нет. Нужен ADR, поскольку решение задаёт постоянный паттерн развёртывания.
