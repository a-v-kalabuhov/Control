# Создание задания из карточки заказа

**Дата:** 2026-07-27
**Статус:** согласовано
**Контекст:** продолжение PZP-05 (модуль заказов), см. `2026-07-26-pzp-05-orders-module-design.md`

## 1. Проблема

Заказ и задание сейчас связываются только со стороны задания. Чтобы выдать задание по
заказу, менеджер обязан:

1. уйти в раздел «Задания», нажать «Выдать задание»;
2. выбрать ТПА и пресс-форму — и только после выбора ПФ разблокируется поле «Заказ»,
   куда подгружаются активные заказы с тем же типом изделия;
3. либо, если заказ не указали сразу, вернуться в карточку заказа и нажать
   «Привязать существующее».

Зависимость односторонняя: ПФ определяет список заказов. Обратного пути — «я в заказе,
хочу задание по нему» — нет, хотя это основной сценарий менеджера, работающего от плана
продаж.

Второй дефект: кнопка «Привязать существующее» показывается в карточке заказа любого
статуса, но привязка к неактивному заказу запрещена политикой и возвращает 400.

## 2. Акторы и сценарии (use cases)

**Актор:** Менеджер или Администратор (`POST /tasks` — `[Authorize(Roles = Admin,Manager)]`).

### UC-1. Выдать задание по активному заказу (основной)

1. Менеджер открывает Заказы → «Открыть» на нужном заказе.
2. В блоке «Задания» нажимает **«Создать задание»**.
3. Открывается форма задания. Поле «Заказ» заполнено этим заказом и заблокировано.
4. Список пресс-форм содержит только ПФ типа изделия заказа.
5. Менеджер выбирает ТПА, ПФ, наладчика, план и дату, сохраняет.
6. Задание создано в статусе `Draft` и сразу привязано к заказу; таблица заданий в
   карточке и прогресс заказа в списке обновляются.

### UC-2. Попытка создать задание по неактивному заказу

1. Менеджер открывает карточку завершённого или отменённого заказа.
2. Кнопки «Создать задание» и «Привязать существующее» видны, но заблокированы;
   подсказка объясняет причину.
3. Действие невозможно — до возобновления заказа («Возобновить» в списке заказов).

### UC-3. Выдача задания вне заказа (регресс, поведение не меняется)

Менеджер идёт в «Задания» → «Выдать задание». Форма работает как раньше: поле «Заказ»
активно, заполняется после выбора ПФ, список ПФ полный.

## 3. Решение

Правка чисто фронтовая. Бэкенд уже поддерживает сценарий: `POST /tasks` принимает
`OrderId` и валидирует привязку общей политикой
`Core/Policies/OrderTaskBinding.EnsureCanBind` (заказ `Active` + у ПФ задан тип +
тип ПФ == тип изделия заказа). См. `TasksController.CreateTask`.

### 3.1. `components/orders/OrderDetailModal.vue`

В шапке блока «Задания» — вторая кнопка слева от существующей:

```
Задания          [Создать задание] [Привязать существующее]
```

- Обе кнопки `:disabled="order?.status !== 'Active'"`, обёрнуты в `el-tooltip`
  с текстом «Задание можно создать только для активного заказа».
  Дизейбл «Привязать существующее» — попутное исправление дефекта из §1.
- Клик по «Создать задание» открывает `TaskFormModal` (`append-to-body`, поверх карточки)
  с пропом `locked-order`.
- По `@success` → `loadOrder()` + `emit('updated')` — обновляются и таблица заданий
  в карточке, и прогресс в списке заказов.

### 3.2. `views/tasks/TaskFormModal.vue` — новый опциональный проп `lockedOrder`

Объект `{ id, number, productTypeId, productTypeArticle }` — берётся из уже загруженного
в карточке `order`, дополнительных запросов не требует. Поведение при заданном пропе:

| Аспект | Без `lockedOrder` (как сейчас) | С `lockedOrder` |
|---|---|---|
| Поле «Заказ» | активно после выбора ПФ | `disabled`, значение = `lockedOrder.id` |
| `orderOptions` | `GET /orders?status=Active&productTypeId=…` | единственный элемент — сам `lockedOrder`, запрос не делается |
| Список ПФ | все активные | только `m.productTypeId === lockedOrder.productTypeId` |
| watch `selectedProductTypeId` | вызывает `loadOrdersForProductType` | не вызывает (иначе затрёт `form.orderId`) |
| `resetForm` | `orderId = null` | `orderId = lockedOrder.id` |

Фильтр ПФ — клиентский computed `availableMolds`: `GET /molds` не поддерживает параметр
`productTypeId`, но `MoldDto` его отдаёт. Тот же приём уже применён в
`OrderDetailModal.openAttachDialog`. Расширять контроллер ради этого не нужно —
список ПФ невелик и уже грузится целиком.

Клиентский фильтр — это UX, а не контроль доступа: правило привязки по-прежнему
enforced на сервере той же политикой.

Без пропа поведение формы не меняется — существующий вызов из раздела «Задания»
не затрагивается.

### 3.3. Бэкенд

Изменений нет.

## 4. Тесты (Vitest)

`views/__tests__/` и `components/orders/__tests__/` — по существующим паттернам.

**`OrderDetailModal.spec.js`**
- кнопка «Создать задание» активна при `status === 'Active'`;
- обе кнопки заблокированы при `Completed` и при `Cancelled`;
- клик открывает `TaskFormModal` с `lockedOrder`, собранным из текущего заказа;
- `@success` от формы вызывает перезагрузку заказа и эмитит `updated`.

**`TaskFormModal.spec.js`**
- с `lockedOrder`: селект заказа `disabled` и отображает номер заказа;
- с `lockedOrder`: в списке ПФ только ПФ с типом изделия заказа;
- с `lockedOrder`: смена ПФ не сбрасывает `form.orderId`;
- с `lockedOrder`: в теле `POST /tasks` уходит `orderId` заказа;
- регресс без пропа: поле «Заказ» активно, список ПФ полный, заказы грузятся по типу ПФ.

## 5. Что осознанно не делаем

- **Кнопки «Создать задание» в строке списка заказов.** Список уже несёт пять действий
  в колонке; вход через «Открыть» → карточка достаточен.
- **Параметра `productTypeId` в `GET /molds`.** Клиентского фильтра хватает; серверный
  фильтр — отдельная задача, если список ПФ вырастет.
- **Смены заказа у созданного задания через эту форму.** Заказ у существующего задания
  меняется только через `POST /tasks/{id}/set-order` — единая точка привязки, как и было.
