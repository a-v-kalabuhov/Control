# Нормализация хранения телеметрии

- **Дата:** 2026-11-25
- **Задача:** уменьшение объёма БД ПЗП и накладных расходов на хранение телеметрии
- **Статус:** проект дизайна; требуется ADR и план реализации
- **Оценка реализации:** 3–5 дней с тестами и репетицией миграции на дампе ПЗП, плюс технологическое окно на площадке
- **ADR:** требуется — изменяются схема большой таблицы, внутренние ключи и паттерн доступа к телеметрии

## Цель

Уменьшить размер таблицы `Telemetry` и её индексов без изменения внешних API, MQTT-контракта, COV-фильтрации и пользовательских сценариев просмотра телеметрии:

1. удалить неиспользуемый индекс по `ParameterName`;
2. заменить UUID ТПА в `Telemetry` на внутренний целочисленный ключ справочника `Imms`;
3. заменить строковое `ParameterName` на целочисленный FK к новому справочнику параметров;
4. оставить один составной индекс `(ImmId, Timestamp, ParameterId)` с целочисленными ключами.

Нормализация не является заменой политики хранения, сжатия TimescaleDB или уменьшения частоты записи. Она уменьшает размер каждой строки, но не количество строк.

## Акторы и сценарии (use cases)

| Актор | Сценарий | Результат |
|---|---|---|
| Система | **UC-1.** Принимает MQTT-сообщение с полным набором параметров ТПА. | Для каждого валидного параметра создаётся строка `Telemetry` с целочисленными `ImmId` и `ParameterId`. COV, валидация, обработка циклов и статусов не меняются. |
| Система | **UC-2.** Получает параметр, отсутствующий в шаблоне ТПА. | Действует текущее правило валидации: неизвестный параметр не сохраняется и не создаёт новую запись в справочнике параметров. |
| Manager / Admin | **UC-3.** Открывает живую или историческую телеметрию, выбирает ТПА и сигналы. | В URL и API по-прежнему используются GUID ТПА и строковые имена параметров. Сервер преобразует их во внутренние ключи и возвращает прежний DTO. |
| Система | **UC-4.** Выполняет live-дельту с `pointsFrom`. | Поведение не меняется: точки догружаются от `pointsFrom`, seed-запросы не выполняются, клиентский кеш продолжает работать. |
| Система | **UC-5.** Выполняет полный запрос окна и seed-запросы. | Основной запрос и seed используют один составной индекс `(ImmId, Timestamp, ParameterId)`; последовательный scan всей таблицы не допускается. |
| Admin | **UC-6.** Создаёт или изменяет шаблон с новым именем параметра. | Новое имя получает запись в справочнике параметров и попадает в кеш. Удалённые из шаблона имена не удаляются из справочника, поскольку на них могут ссылаться исторические строки. |
| Система | **UC-7.** Перезапускается после миграции. | Справочники и кеши загружаются до начала обработки MQTT; на горячем пути записи нет отдельного SQL-запроса за ключом каждого параметра. |
| Admin / разработчик | **UC-8.** Выполняет миграцию существующей базы ПЗП. | Все исторические строки сохраняют `Id`, время и значения, получают корректные целочисленные ключи; внешние GUID ТПА и имена параметров остаются доступными через справочники. |

## Основные решения

1. **Внешний `Imm.Id Guid` сохраняется.** Он остаётся ключом API, MQTT-конфигурации, коннектора и всех остальных таблиц. Целочисленный ключ предназначен только для компактного хранения `Telemetry`.
2. **Справочник параметров глобальный.** Одно имя параметра имеет один `Id` независимо от шаблона и ТПА. Имена не нормализуются по регистру и не объединяются: текущие сравнения `ParameterName` являются регистрозависимыми.
3. **После миграции у `Telemetry` только два индекса:** первичный ключ и `(ImmId, Timestamp, ParameterId)`. Отдельные индексы по `ParameterName`, `(ImmId, Timestamp)` со старыми типами и `(ImmId, ParameterName, Timestamp)` отсутствуют.
4. **Внешние контракты не меняются.** Новые числовые ключи не появляются в API, DTO, URL, JSON шаблонов или сообщениях MQTT.
5. **Разрешение имён в ключи кешируется.** Допустимы единичные обращения к БД при пополнении кеша, но не запрос к справочнику для каждой строки MQTT-сообщения.
6. **Перенос большой истории выполняется в новую таблицу.** In-place update 172 млн строк создал бы вторую версию каждой строки, а удаление старых колонок само по себе не вернуло бы место без полной перезаписи таблицы.

## Модель данных

### Изменение `Imms`

В существующую таблицу добавляется внутренний ключ:

| Поле | Тип | Правило |
|---|---|---|
| `Id` | `uuid` | Существующий первичный и внешний ключ, не меняется |
| `InternalId` | `integer` | `GENERATED ... AS IDENTITY`, уникален, неизменяем, не выдаётся наружу |

- `InternalId` заполняется PostgreSQL автоматически, включая существующие строки.
- На `InternalId` создаётся уникальное ограничение/индекс, поскольку оно будет целью FK.
- Архивация ТПА не меняет `InternalId`.
- Остальные таблицы продолжают ссылаться на `Imms.Id uuid`; массовая замена их FK не входит в задачу.

### Новая сущность `TelemetryParameter`

Таблица `TelemetryParameters`:

| Поле | Тип | Правило |
|---|---|---|
| `Id` | `integer` | Первичный ключ, `GENERATED ... AS IDENTITY` |
| `Name` | `text` | Обязательное точное имя параметра, уникально |

Ограничения и правила:

- уникальность `Name` соответствует текущему точному сравнению имён; `Temp` и `temp` остаются разными параметрами;
- отдельного `IsActive` нет: справочная строка нужна, пока существует хотя бы одна историческая ссылка;
- автоматического удаления и переименования записей при правке шаблона нет;
- ограничение «около 100 параметров» является ожидаемой нагрузкой, а не ограничением БД.

### Новая структура `Telemetry`

| Поле | Тип | Правило |
|---|---|---|
| `Id` | `bigint` | Существующий первичный ключ; значения и identity-последовательность сохраняются |
| `ImmId` | `integer` | FK → `Imms.InternalId`, `Restrict` |
| `Timestamp` | `timestamptz` | Существующее значение UTC, без изменений |
| `ParameterId` | `integer` | FK → `TelemetryParameters.Id`, `Restrict` |
| `ValueNumeric` | `numeric?` | Без изменения типа и значения |
| `ValueText` | `text?` | Без изменения типа и значения |

Старые колонки `Telemetry.ImmId uuid` и `Telemetry.ParameterName text` в целевой схеме отсутствуют. В EF добавляется навигация `Telemetry.Parameter`; связь `Telemetry.Imm` использует `HasPrincipalKey(Imm.InternalId)`.

### Целевые индексы

```text
PK_Telemetry                       (Id)
IX_Telemetry_Imm_Time_Parameter    (ImmId, Timestamp, ParameterId)
```

Удаляются и больше не объявляются в модели EF:

```text
IX_Telemetry_ParameterName
IX_Telemetry_ImmId_Timestamp
IX_Telemetry_Imm_Param_Time
```

Порядок `(ImmId, Timestamp, ParameterId)` выбран намеренно:

- основной запрос использует левый префикс `(ImmId, Timestamp)` и естественный порядок по времени;
- seed-запрос идёт по нему назад и фильтрует `ParameterId` внутри записей полного набора параметров;
- отдельный индекс `(ImmId, Timestamp)` не нужен, поскольку его левый префикс уже покрыт целевым индексом;
- индекс `(ImmId, ParameterId, Timestamp)` ради отдельной оптимизации seed не создаётся.

На ПЗП два удаляемых индекса уже отсутствуют из-за ручных операций. Миграция обязана использовать идемпотентные удаления `IF EXISTS` и привести модель EF, migration history и фактическую БД к одному состоянию.

## Запись телеметрии

Последовательность обработки MQTT остаётся прежней до этапа сохранения:

1. ТПА определяется по существующему внешнему GUID; сущность `Imm` дополнительно содержит `InternalId`.
2. Валидация и COV выполняются без изменений и используют строковые имена из шаблона.
3. Обработчики циклов и статусов продолжают получать полный набор сигналов текущего сообщения.
4. `StoreTelemetryDataHandler` записывает `context.Device.InternalId` в `Telemetry.ImmId`.
5. Для каждого валидного `ParameterName` `ITelemetryParameterResolver` возвращает `ParameterId` из потокобезопасного кеша.
6. В `Telemetry` сохраняются только числовые ключи и прежние время/значения.

Если валидное имя из актуального шаблона отсутствует в кеше, resolver один раз синхронно разрешает его через БД и пополняет кеш. Параллельное создание одного имени разрешается уникальным ограничением и повторным чтением записи. Неизвестные шаблону имена не попадают в resolver благодаря существующей валидации.

## Пополнение справочника параметров

Справочник наполняется из двух источников:

- при миграции — всеми различными `Telemetry.ParameterName`, чтобы сохранить историю, включая параметры удалённых шаблонов;
- при старте и создании/правке шаблона — всеми `SensorTemplate.ParameterName`, включая параметры, для которых ещё нет истории.

Создание недостающих записей для нового шаблона выполняется в той же транзакции БД, что сохранение шаблона. Кеш обновляется после успешного коммита. При старте приложения кеши шаблонов и параметров полностью инициализируются до запуска MQTT-обработки.

## Чтение телеметрии и API

Endpoint `GET /api/imm/{id:guid}/telemetry-dashboard` и его query-параметры не меняются:

- `id` остаётся GUID ТПА;
- `parameters` остаётся списком строк;
- `from`, `to`, `pointsFrom` сохраняют текущий смысл;
- DTO сигналов и точек остаётся прежним.

Для каждого запроса сервер:

1. читает `Imm` по внешнему GUID и получает `InternalId`;
2. преобразует известные имена параметров в `ParameterId`;
3. выполняет основной запрос по `(InternalId, Timestamp, ParameterId)`;
4. для полного окна выполняет seed-запросы по тем же ключам;
5. преобразует числовые ключи строк обратно в имена и заполняет текущий DTO.

Неизвестное имя параметра не должно вызывать ошибку: как и раньше, соответствующий сигнал возвращается без точек. Live-запрос с `pointsFrom` по-прежнему не выполняет seed-запросы.

Двухзапросная схема seed через отдельный `MAX(Timestamp)` не вводится: текущий `ORDER BY Timestamp DESC LIMIT 1` уже находит максимум и строку за одно обращение.

## Миграция существующих данных

### Подготовка

1. Снять полный дамп БД ПЗП и проверить восстановление на отдельной копии.
2. Зафиксировать исходные размеры таблицы и индексов, количество строк и планы основного/seed-запросов.
3. Измерить длительность и потребное место на репетиции. На диске должно хватить места одновременно на старую и новую таблицы, новые индексы, WAL и запас для завершения операции.
4. Согласовать технологическое окно. На время переноса останавливаются коннектор и старый API; сбор телеметрии за это время приостанавливается, буферизация сообщений не предусмотрена.

### Перенос

1. Добавить `Imms.InternalId` и создать `TelemetryParameters`.
2. Заполнить справочник параметров из `SELECT DISTINCT ParameterName FROM Telemetry`.
3. Создать временную `TelemetryNormalized` с целевыми типами и FK, но без тяжёлого составного индекса.
4. Копировать строки пакетами по возрастанию `Id` с сохранением контрольной точки после каждого закоммиченного пакета. Один непрерывный `UPDATE`/`INSERT` всей истории в одну гигантскую транзакцию не допускается.
5. При копировании заменить GUID на `Imms.InternalId`, а имя — на `TelemetryParameters.Id`. Строки, для которых не нашёлся справочный ключ, являются блокирующей ошибкой миграции.
6. Сохранить все `Id`; после копирования установить identity-последовательность так, чтобы следующий `Id` был больше максимального перенесённого.
7. Проверить количество строк, отсутствие неприкреплённых ключей, совпадение времени и значений по контрольным выборкам для каждого ТПА и параметра.
8. Создать целевой составной индекс после основной загрузки, выполнить `ANALYZE` и проверить планы запросов.
9. В короткой финальной транзакции переименовать исходную таблицу в `TelemetryLegacy`, новую — в `Telemetry`, согласовать имена ограничений и индексов с моделью EF.
10. После контрольной проверки удалить `TelemetryLegacy` для освобождения места. До этого удаления откат выполняется обратным переименованием; после удаления — только восстановлением из дампа.
11. Запустить новый API, проверить чтение и запись, затем запустить коннектор.

Пакетный перенос не должен незаметно запускаться обычным `Database.Migrate()` при старте боевого API. Необходим управляемый сценарий миграции с контрольной точкой и согласованной migration history; разовые ручные изменения схемы вне этого сценария не считаются завершённой миграцией.

## Что не входит в задачу

- переход на TimescaleDB, сжатие или секционирование;
- изменение COV и пропуск неизменённых значений;
- удаление или агрегирование старой телеметрии;
- удаление `Telemetry.Id` или первичного ключа;
- замена GUID во всех остальных таблицах;
- изменение `ValueNumeric`/`ValueText`;
- изменение внешних API, MQTT, шаблонов и frontend-компонентов;
- кеширование seed-точек или изменение механизма `pointsFrom`.

## Тестирование

### Unit

- resolver возвращает стабильные `Id`, различает имена по регистру и не обращается к БД при повторном вызове;
- параллельное добавление одного имени не создаёт дублей;
- запись использует `Imm.InternalId` и `ParameterId`;
- неизвестный шаблону параметр не создаёт справочную запись;
- чтение формирует прежний DTO и корректно обрабатывает неизвестное имя.

### Integration

- создание/правка шаблона пополняет справочник в одной транзакции;
- после перезапуска кеш восстанавливается без обращений к справочнику на каждую строку;
- MQTT-сообщение создаёт строки с правильными FK, а циклы и статусы обрабатываются как раньше;
- основной запрос, полный seed и live `pointsFrom` возвращают те же результаты, что до нормализации;
- `EXPLAIN` показывает использование `IX_Telemetry_Imm_Time_Parameter`, отсутствует sequential scan по `Telemetry`;
- FK не позволяют удалить ТПА или параметр с историей.

### Репетиция миграции на дампе

- пакетная миграция возобновляется с контрольной точки без дублей;
- итоговые количества и контрольные значения совпадают с источником;
- identity продолжается с корректного значения;
- целевая схема совпадает с моделью EF;
- измерены итоговый размер, длительность окна и время основного/seed-запросов;
- откат до удаления `TelemetryLegacy` проверен отдельно.

## Критерии приёмки

1. В `Telemetry` отсутствуют UUID ТПА и строковое имя параметра; используются два `integer` FK.
2. Все исторические строки и значения сохранены, внешние GUID и имена доступны через справочники.
3. У `Telemetry` остаются только PK и `(ImmId, Timestamp, ParameterId)`.
4. Индекс по имени параметра удалён и из фактической БД, и из модели EF.
5. Запись телеметрии не выполняет SQL-запрос к справочнику для каждой строки.
6. API и DTO не изменились; frontend не требует доработки.
7. COV, циклы, статусы, live-дельта и seed работают без изменения семантики.
8. Репетиция на дампе ПЗП завершена с измеренными размером, временем и успешными проверками целостности.
9. Для ПЗП подготовлены проверенные сценарии миграции и отката, а технологическое окно согласовано по результатам репетиции.
