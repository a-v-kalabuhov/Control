# Рабочий режим ТПА и двухуровневый цикл литья

**Дата:** 2026-08-01
**Статус:** дизайн согласован, ждёт плана реализации

## Проблема

ТПА работают в трёх рабочих режимах: ручном, полуавтоматическом и автоматическом.
Ручной используется только для наладки. Партия изделий выпускается в автоматическом
или полуавтоматическом режиме.

- **Автоматический** — изделие извлекается из пресс-формы самим ТПА (толкателем либо
  воздушным клапаном). Пауза между циклами литья короткая; длинная пауза означает
  проблему с ПФ, например залипание изделия.
- **Полуавтоматический** — после раскрытия ПФ ТПА открывает защитную дверь, оператор
  извлекает изделие и закрывает дверь; закрытие двери запускает следующий цикл.
  Длительность паузы зависит от человека и принципиально нестабильна.

Коннектор не знает, в каком рабочем режиме находится ТПА, и не может это определить.
Отсюда два дефекта:

1. **Приложение не различает два вложенных цикла.** Сейчас `ImmCycle` пишется по
   инкременту `cycleCounter` и хранит только длительность полного цикла. Цикл литья и
   пауза не разделены, поэтому нельзя ни оценить стабильность процесса, ни отличить
   «форма работает медленно» от «оператор задержался».
2. **Детект простоя не учитывает режим.** Порог 120 секунд не-`auto` разумен для
   автомата, но в полуавтомате даёт ложные простои на каждой паузе оператора.

## Решения (принято при обсуждении)

### Р1. Двухуровневая модель цикла

Раскладка по времени одного полного цикла:

```text
смыкание → Injection↑ (якорь, счётчик++) → выдержка/охлаждение → полное раскрытие
   └───────────────────── цикл литья ─────────────────────────┘
полное раскрытие → (извлечение изделия) → смыкание
        └──────────── пауза ────────────┘
```

- **Цикл литья** — от полного смыкания ПФ до её полного раскрытия.
- **Пауза** — от полного раскрытия до следующего смыкания.
- **Полный цикл** — цикл литья + пауза. Не хранится, считается на лету.

Якорь цикла в коннекторе остаётся прежним — фронт `Injection ↑` (он же инкрементирует
счётчик износа формы). Меняется **признак завершения** цикла: вместо `EjectorFwdReached`
им становится полное раскрытие формы.

### Р2. Длительности считает коннектор, полный цикл — приложение

Коннектор публикует две измеренные величины: длительность цикла литья и длительность
паузы. Полный цикл вычисляет Control.

Причина разделения: решение «это пауза или это простой» требует знания рабочего режима,
а коннектор о режиме ничего не знает. Коннектор при длительной паузе решит, что ТПА ушёл
в простой (`mode = idle`), — приложение при этом видит, что это именно пауза.

### Р3. Рабочий режим — параметр задания

Значения: **автомат** и **полуавтомат**. Ручной режим — это наладка, а не выпуск партии,
поэтому в задании его нет. Поле обязательное, по умолчанию автомат. В будущем переезжает
в технологическую карту.

### Р4. Эталонные длительности — параметры задания

- **Полный цикл — обязателен.** Менеджер вычисляет его при планировании, потому что
  должен хотя бы примерно знать, когда задание будет закончено.
- **Цикл литья — необязателен.** Технологический параметр, нужен только для анализа
  стабильности; не задан — анализ просто не строится.

### Р5. Простой — единый высокий порог, без учёта режима

Порог один для обоих режимов, из конфига приложения, 900 секунд (15 минут).
Отсчёт начинается при любом не-`auto` статусе и сбрасывается только возвратом в `auto`;
`alarm` и `manual` отсчёт продолжают.

Обоснование — журнал простоев есть очередь работы для наладчика и материал для разбора
у начальника. Записи ценой в минуту простоя обесценивают обе роли: наладчик заполняет их
формально, начальник перестаёт читать. Крупные простои (серьёзная поломка, длительное
отсутствие на рабочем месте) интересны начальнику и не требуют большого труда по
заполнению. Короткие остановы при этом не теряются: длительность каждой паузы пишется в
`ImmCycle`, и «ТПА встал на 4 минуты» будет видно из данных о циклах как потеря темпа,
посчитанная без единого действия человека.

**Следствие, зафиксировано осознанно:** рабочий режим и эталоны **не влияют на детект
простоя**. Они хранятся ради планирования и будущей аналитики отклонений.

### Р6. Учёт выпуска в полуавтомате

При `WorkMode.SemiAuto` условие `mode == auto` в `CycleProcessingPolicy.ShouldCountOutput`
снимается. Иначе коннектор по своему таймауту успеет уйти в `idle` до того, как оператор
закроет дверь и цикл завершится, и выпуск не зачтётся.

## Акторы и сценарии (use cases)

| Актор | Сценарий | Результат |
|---|---|---|
| Менеджер / технолог | Создаёт задание: выбирает рабочий режим, вводит эталон полного цикла и (опционально) эталон цикла литья | Задание содержит режим и нормы; без эталона полного цикла создать нельзя |
| Менеджер | Планирует срок завершения задания | Опирается на введённый эталон полного цикла и план выпуска |
| Наладчик | Работает по заданию в полуавтомате, ТПА ждёт его действий между циклами | ТПА остаётся в состоянии «Работа», записи простоя не создаются |
| Наладчик | Отошёл или чинит машину дольше 15 минут | Создана запись простоя с началом в момент перехода ТПА в не-`auto`, а не в момент обнаружения; наладчик указывает причину |
| Оператор в полуавтомате | Извлекает изделие и закрывает дверь | Цикл засчитан в выработку задания, несмотря на `mode = idle` от коннектора |
| Начальник производства | Разбирает журнал простоев | Видит только значимые простои, без шума из коротких остановов |
| Коннектор | Публикует телеметрию по завершении цикла | Отдаёт длительность цикла литья и длительность предшествующей паузы |

Сценарии, **не входящие** в эту спеку и вынесенные в отдельную работу по аналитике:
анализ стабильности цикла литья, анализ отклонений пауз от эталона, отображение потерь
темпа, дашборды и отчёты по этим данным.

## Модель данных

### Новый enum `WorkMode`

`Wintime.Control.Core/Enums/WorkMode.cs`:

```csharp
public enum WorkMode
{
    Auto = 0,      // изделие извлекает ТПА
    SemiAuto = 1   // изделие извлекает оператор
}
```

**Не путать с `ImmMode`** (`Core/Constants/ImmMode.cs`). `ImmMode` — состояние ТПА,
приходящее из телеметрии (`auto`/`manual`/`idle`/`alarm`). `WorkMode` — как технолог
назначил работать. Различие фиксируется в XML-doc обоих типов.

### `ShiftTask` — три новых поля

| Поле | Тип | Правило |
|---|---|---|
| `WorkMode` | `WorkMode` NOT NULL, default `Auto` | обязателен в UI; существующие задания мигрируют в `Auto` — поведение системы не меняется |
| `PlannedFullCycleSeconds` | `int?` | обязателен при создании нового задания (валидация в API), `> 0`. В БД nullable: у существующих заданий значения нет, и выдумывать его нельзя |
| `PlannedInjectionCycleSeconds` | `int?` | необязателен; если задан — `> 0` и `<= PlannedFullCycleSeconds` |

`null` в `PlannedFullCycleSeconds` означает legacy-задание, созданное до этой доработки.

### `ImmCycle` — два новых поля

| Поле | Тип | Смысл |
|---|---|---|
| `InjectionDurationMs` | `int?` | длительность цикла литья: смыкание↑ → полное раскрытие↑ |
| `PauseDurationMs` | `int?` | длительность паузы, предшествовавшей этому циклу: раскрытие↑ → смыкание↑ |

Полный цикл **не хранится** — равен сумме двух полей, считается на лету.

Существующий `DurationSeconds` не трогаем: он остаётся полным циклом, посчитанным по
инкременту счётчика, и служит fallback для машин без новых сигналов. Все текущие отчёты
и дашборд телеметрии продолжают работать без правок.

Оба поля nullable по той же причине, что и `Cavities`: данные появляются только там, где
коннектор умеет их отдавать.

## Контракт с коннектором

Два новых значения `ParameterType` в шаблоне ТПА — по образцу `cycleCounter`, который
уже несёт семантику, а не только тип:

| `ParameterType` | Значение | Единицы |
|---|---|---|
| `injectionDuration` | длительность цикла литья | миллисекунды, целое |
| `cyclePause` | длительность паузы **перед** текущим циклом | миллисекунды, целое |

Правила:

- Оба сенсора **не** `Required`. Машина без сигналов смыкания/раскрытия работает по-старому.
- Валидация типов — в `ValidateTelemetryDataHandler.TryValidateSensorValue`, рядом с
  `cycleCounter`, как целые.
- **COV-фильтрация для этих типов должна быть выключена** (`Threshold = 0`). Иначе фильтр
  подставит закешированное значение прошлого цикла, и вместо реальной вариации получится
  ровная линия — то есть потеряется ровно то, ради чего всё делается. Проверка
  «у сенсора этих типов `Threshold` обязан быть 0» ставится в валидацию шаблона, а не в
  комментарий.
- Коннектор публикует сообщение в момент полного раскрытия ПФ и отдаёт в нём обе
  величины: длительность только что завершившегося цикла литья и длительность паузы,
  ему предшествовавшей.

Чтение — в `CycleProcessingHandler`, в момент сборки `ImmCycle` после того, как цикл
признан завершённым: значения достаются из `data.Sensors` по `ParameterType` и кладутся
в новые поля. Сенсоров нет — поля остаются `null`, остальное работает как сейчас.

### Зависимость: доработка коннектора USR

Реализация на стороне коннектора — отдельная работа в приватном репозитории
`Sources/Connectors/Wintime.Connector.UsrModbus`, за границей этой спеки. Требуется:

- два новых дискретных сигнала: смыкание ПФ и полное раскрытие ПФ (две новые роли
  `SignalRole`, два входа USR на машине);
- признак завершения цикла в автомате состояния меняется с `EjectorFwdReached` на
  полное раскрытие;
- публикация `injectionDuration` и `cyclePause`.

Замечание: в `STATE_MACHINE.md` коннектора записано, что `Mould closed` неоднозначен —
форма смыкается и в наладке. Здесь это безопасно: счётчик циклов по-прежнему двигает
только `Injection ↑`, а наладка отсекается статусом задания на стороне Control.

## Изменения в логике

### Простой

`DowntimeSettings.IdleThresholdSeconds`: 120 → 900.

`DowntimeDecision.Evaluate` **не меняется**: он уже открывает простой при не-`auto`
дольше порога, закрывает при возврате в `auto`, и ставит начало в момент смены статуса
(`statusSinceUtc`), а не в момент обнаружения. То есть простой, записанный на 15-й
минуте, ложится в журнал началом «15 минут назад», и наладчик сразу видит корректную
длительность.

`DowntimeDetectionWorker` и `ImmController` не меняются — оба уже читают порог из
настроек.

### Эффективный статус

`ImmEffectiveStatus.Resolve` не меняется. В полуавтомате ТПА, ждущий оператора, остаётся
в состоянии **Работа**: `mode = idle` от коннектора не проходит порог и растворяется в
`Production` по существующей ветке «до порога Stopped растворён в Работу».

`EffectiveStatusTimeline` не меняется: он восстанавливает историю по уже записанным
событиям простоя, а не по порогу.

### Учёт выпуска

`CycleProcessingPolicy.ShouldCountOutput` получает параметр `WorkMode`:

- `Auto` — как сейчас: задание InProgress **и** `mode == auto` **и** нет открытого простоя;
- `SemiAuto` — задание InProgress **и** нет открытого простоя (условие `mode == auto` снято).

`ShouldProcessCycle` не меняется.

## API и UI

- `CreateShiftTaskRequest` / `UpdateShiftTaskRequest`: добавляются `workMode`,
  `plannedFullCycleSeconds`, `plannedInjectionCycleSeconds`. Валидация по правилам из
  раздела «Модель данных»; нарушение → `DomainException` → HTTP 400.
- `ShiftTaskDto`: три новых поля на выдачу.
- Форма создания/редактирования задания: селектор режима (по умолчанию «Автомат») и два
  числовых поля в секундах, у эталона цикла литья — пометка «необязательно».
- Карточка задания: режим и эталоны отображаются рядом с планом выпуска.

## Тесты

**xUnit:**

- `ShiftTask` — валидация трёх новых полей: обязательность полного цикла, границы
  значений, `PlannedInjectionCycleSeconds <= PlannedFullCycleSeconds`.
- `CycleProcessingHandler` — новые сенсоры попадают в `ImmCycle`; их отсутствие оставляет
  поля `null` и не ломает обработку.
- `CycleProcessingPolicy.ShouldCountOutput` — таблица по обоим режимам, включая
  ключевой случай «SemiAuto + `mode = idle` + InProgress + нет простоя → выпуск засчитан».
- Валидация шаблона — сенсор типа `injectionDuration`/`cyclePause` с ненулевым
  `Threshold` отклоняется.

**Vitest:** форма задания — обязательность полного цикла, необязательность цикла литья.

Существующие тесты простоя (`DowntimeDecisionTests`, `DowntimeDetectionWorkerTests`)
задают порог явно и от смены значения по умолчанию не страдают.

## Миграция

Одна миграция EF Core:

- `ShiftTasks`: `WorkMode` (int NOT NULL, default 0), `PlannedFullCycleSeconds` (int NULL),
  `PlannedInjectionCycleSeconds` (int NULL);
- `ImmCycles`: `InjectionDurationMs` (int NULL), `PauseDurationMs` (int NULL).

Существующие строки не переписываются: задания получают режим «автомат», что сохраняет
текущее поведение, эталоны остаются пустыми.

## ADR

Завести ADR на решение Р5 — «единый высокий порог простоя; короткие остановы уходят в
аналитику по циклам, а не в журнал». Это решение задаёт паттерн и через полгода без
записанного обоснования будет выглядеть опечаткой в конфиге.

## Границы и известные компромиссы

- **Авария в журнале с задержкой.** `alarm` не открывает простой немедленно и ждёт общий
  порог. Самосбрасывающаяся за минуту авария — шум, серьёзная переживёт 15 минут и
  попадёт в журнал с корректным началом.
- **Наладка посреди задания.** `manual` при задании InProgress отсчёт не сбрасывает:
  длительное вмешательство наладчика попадёт в журнал как простой. Короткое отсекается
  тем же порогом.
- **Режим и эталоны пока «спящие».** До реализации аналитики они только хранятся.
  Это осознанно, см. Р5.
- **Аналитика вне скоупа.** Анализ стабильности цикла литья, отклонений пауз от эталона и
  потерь темпа — отдельная спека, которая опирается на данные, начинающие копиться здесь.
