# Старший смены по умолчанию

- **Дата:** 2026-11-25
- **Зависимости:** PZP-32 (`ShiftLead`, план смен, интервалы литейщиков), PZP-31 (сменный рапорт и закрытие смены)
- **Статус:** черновик для согласования
- **ADR:** требуется ADR-0032, уточняющий позиционную модель ADR-0027 и неизменяемость старшего закрытого рапорта ADR-0030/0031

## Цель

Разрешить Manager/Admin задать старшего по умолчанию для каждой позиции справочника смен. Если на конкретную дату старший не назначен явно, система использует старшего из настройки не только для отображения, но и для всех серверных прав доступа.

Пример: для смены 1 выбран Иванов, для смены 2 — Петров. Даже если менеджер не заполняет старших в плане, Иванов получает свои смены 1, а Петров — свои смены 2. Явное назначение другого старшего на конкретную дату имеет приоритет над настройкой.

Если для позиции не задан старший по умолчанию, используется активный Manager, созданный раньше остальных активных менеджеров. Таким образом, полная цепочка: **явное назначение → настройка позиции → первый активный Manager → нет старшего, если активных менеджеров нет**.

## Термины

- **Явный старший** — пользователь, сохранённый в `ShiftPlanItem.ShiftLeadId` через назначение на конкретную дату либо зафиксированный там при закрытии рапорта.
- **Старший по умолчанию** — пользователь, выбранный для позиции справочника смен в отдельной панели настроек.
- **Резервный менеджер** — активный пользователь с ролью `Manager`, имеющий минимальные `CreatedAt`, затем `Id` при равенстве времени. Это автоматический fallback, когда нет ни явного старшего, ни настройки позиции.
- **Эффективный старший** — результат разрешения ответственности для конкретной позиции и даты:

```text
EffectiveShiftLeadId = ShiftPlanItem.ShiftLeadId
                       ?? ShiftDefaultLead[Position].ShiftLeadId
                       ?? FirstActiveManager.Id
```

- **Источник старшего** — `Explicit`, если использовано явное назначение; `Default`, если использована настройка; `ManagerFallback`, если использован первый активный Manager; отсутствует, если активного Manager нет и старший не найден.

## Основные решения

1. **Приоритет: явное назначение → настройка позиции → первый активный Manager.** Очистка явного назначения означает переход к следующему доступному источнику. Отдельного состояния «на этой дате намеренно нет старшего, несмотря на fallback» в задаче нет.
2. **Default и ManagerFallback — реальные источники доступа, а не только текст в плане.** Единый resolver используется планом, nearest, staffing, history, pending и closure. Проверки не должны независимо читать `ShiftPlanItem.ShiftLeadId` как единственного возможного старшего.
3. **Настройка привязана к позиции, а не к `Shift.Id`.** Справочник смен при сохранении пересоздаёт строки и их Guid, поэтому FK на `Shifts` не вводится. Позиция соответствует текущему порядку интервалов по `StartMinutes`, как и в существующем плане.
4. **Оба fallback действуют на виртуальные и сохранённые незакрытые смены.** Изменение default или состава активных менеджеров автоматически меняет эффективного старшего там, где нет более приоритетного источника; явные назначения не переписываются.
5. **Closed — граница изменчивости.** При закрытии эффективный старший фиксируется в `ShiftPlanItem.ShiftLeadId`. После этого он обрабатывается как явный и не зависит от настройки или последующего порядка активных менеджеров.
6. **Замена и очистка default сохраняют операционные данные.** Замена эквивалентна переназначению незакрытых смен. Очистка переводит их к первому активному Manager; запрет нужен только если ни default, ни активного Manager после операции не остаётся и данные оказались бы без ответственного.
7. **Материализация ленивая и идемпотентная.** Нет фонового создания дней на бесконечное будущее или прошлое. Сохраняется полный день только при выборе fallback-смены nearest, явном открытии из плана или существующем назначении старшего.
8. **История содержит реально материализованные смены.** Не создаются пустые рапорты за все прошлые даты. При необходимости Manager/Admin материализует прошлую fallback-смену из плана и передаёт её в обычный контур pending/history.
9. **Права и кандидаты не расширяются.** Кандидаты для явного/default-назначения — активные `ShiftLead` и `Manager`; Manager может назначить себя, Admin не становится старшим только из-за своей роли. В ManagerFallback участвуют только активные пользователи ровно с ролью `Manager`.
10. **Первый Manager определяется по серверной дате создания.** В `User` добавляется `CreatedAt`; сортировка — `CreatedAt ASC`, затем `Id ASC`. Клиентское время и табельный номер не используются.
11. **Общий график не раскрывает настройку лишним ролям.** Существующий общедоступный авторизованным пользователям `GET /api/shifts` остаётся без персональных данных. Настройки доступны только Manager/Admin.

## Модель данных

### `User.CreatedAt`

В `AspNetUsers` добавляется поле:

- `User.CreatedAt` — обязательное `DateTime` (`timestamptz`) в UTC, заполняется сервером при создании пользователя.

- Клиент значение не передаёт и не может изменить через обычные API редактирования персонала.
- Все существующие способы создания пользователя, включая bootstrap/seed, получают серверное значение.
- Резервный менеджер выбирается запросом `IsActive && Role == Manager`, `OrderBy(CreatedAt).ThenBy(Id)`.
- При равных `CreatedAt` `Id` обеспечивает стабильный детерминированный результат; это не утверждение о фактическом порядке создания при одинаковой метке.
- При миграции существующие пользователи получают единое время миграции: прежняя фактическая дата создания в БД не хранилась и не восстанавливается. Их взаимный порядок до появления новых значений определяется tie-break по `Id`; все вновь созданные пользователи получают точные серверные метки.
- Обычный индекс `(IsActive, Role, CreatedAt, Id)` либо эквивалентный индекс для выборки первого активного Manager добавляется в той же миграции. Фильтр роли остаётся доменной проверкой, а не Identity-ролью.

### `ShiftDefaultLead`

Новая таблица `ShiftDefaultLeads`:

| Поле | Тип | Правило |
| --- | --- | --- |
| `Position` | `int` | Первичный ключ; `Position >= 1`; номер позиции текущего графика |
| `ShiftLeadId` | `string` | Обязательный FK на `Users.Id`; активный `ShiftLead` или `Manager` проверяется сервером при сохранении |

- Отсутствие строки означает отсутствие default для позиции; nullable `ShiftLeadId` не используется.
- FK на `Shifts` отсутствует, поскольку его записи пересоздаются.
- Уникальности по `ShiftLeadId` нет: один человек может быть старшим нескольких позиций.
- FK на пользователя — `Restrict`; физическое удаление пользователей доменом не предусмотрено.
- Индекс по `ShiftLeadId` нужен для проверок использования и выборок.
- Отдельные `CreatedAt`/`UpdatedAt` и история изменений настройки в задачу не входят.

### `ShiftPlanItem`

Схема не меняется:

- `ShiftLeadId` остаётся nullable и обозначает явное назначение;
- `null` у незакрытой позиции означает «использовать default, а при его отсутствии — первого активного Manager»;
- при закрытии рапорта `ShiftLeadId` заполняется эффективным старшим, если был `null`;
- отдельные `DefaultShiftLeadId` или `FallbackManagerId` в каждую позицию не копируются: это позволяет пересчитывать fallback для всех незакрытых смен без массовой перезаписи плана.

Источник `Explicit`/`Default`/`ManagerFallback` вычисляется и не хранится. После закрытия зафиксированный fallback становится `Explicit`; для закрытого документа важна неизменяемость человека, а не первоначальный способ назначения.

### Существование `ShiftPlanDay`

Прежнее правило «день существует только при явном старшем» расширяется. Сохранённый день допустим, если:

- хотя бы у одной позиции есть явный, default- или ManagerFallback-старший; либо
- у позиции есть интервалы литейщиков или сменный рапорт.

При материализации fallback-смены создаются все позиции дня, но их `ShiftLeadId` не заполняются автоматически. Остальные позиции сохранённого дня также разрешают своих эффективных старших через текущие настройки и первого активного Manager.

При очистке default или синхронизации графика пустой день без явных/эффективных старших, назначений и рапортов удаляется. День с другими явными старшими или данными сохраняется. Изменение состава активных менеджеров не запускает массовую материализацию или удаление дней: ManagerFallback вычисляется при чтении и серверных операциях.

## Единое разрешение эффективного старшего

Добавляется доменная политика, условно `EffectiveShiftLeadResolver`. Первый активный Manager загружается один раз на запрос/операцию и передаётся в чистую политику, а не запрашивается из БД отдельно для каждой позиции:

```text
Resolve(item, defaultsByPosition, firstActiveManagerId):
    if item.ShiftLeadId is not null:
        return (item.ShiftLeadId, Explicit)

    default = defaultsByPosition.Get(item.Position)
    if default exists:
        return (default.ShiftLeadId, Default)

    if firstActiveManagerId is not null:
        return (firstActiveManagerId, ManagerFallback)

    return (null, None)
```

Первый активный Manager выбирается по `IsActive = true`, `Role = Manager`, затем `CreatedAt ASC, Id ASC`. Resolver не проверяет роль текущего пользователя и не заменяет авторизацию. Он только определяет ответственного. Доступ затем проверяется по текущей роли и правилами nearest/pending/history/closed. ManagerFallback не делает пользователя ShiftLead и не открывает ему `/shift-lead`.

Все следующие вычисления используют эффективного старшего:

- `ShiftPlanItemDto.ShiftLeadId/Name` и `ShiftLeadSource`;
- `HasMissingLeadWarning` и `CanEditOperators`;
- `NearestShiftSelector.ForLead` и `IsNearestForManager`;
- чтение `ShiftStaffingItemDto`, авторизация назначений и исправлений интервалов;
- `ShiftClosureService` и `ShiftClosureReadModelLoader`;
- отбор pending и history;
- признак возможности открыть вкладку рапорта на frontend.

Не допускается реализация, где план подставляет default в DTO, а staffing/closure продолжают считать такую смену не имеющей старшего.

## Материализация и ближайшая смена

### Общий материализатор

Выделяется общий сервис, используемый существующим `SetLeadAsync`, новым `materialize` и `nearest`:

1. Под `ShiftScheduleLock` повторно читает график, сохранённый день и настройки default.
2. Для виртуальной даты строит полный день из актуального графика.
3. Для сохранённой даты использует существующие `Id`, окна, явных старших и данные.
4. Проверяет, что выбранная позиция существует и имеет эффективного старшего.
5. Идемпотентно сохраняет день и возвращает постоянный `itemId`.
6. Параллельное изменение выбора или графика даёт `409`; клиент повторно запрашивает данные, а не использует устаревший `itemId`.

Материализация сама по себе не назначает явного старшего, не создаёт `ShiftClosure`, назначения литейщиков или производственные задания.

### `nearest`

Для текущего ShiftLead:

1. Загружаются сохранённые позиции и разрешаются их эффективные старшие, включая первого активного Manager.
2. Из актуального графика строятся виртуальные дни от заводской текущей даты до первой позиции, достаточной для выбора текущей/ближайшей будущей смены.
3. Явные назначения других пользователей исключают применение default и ManagerFallback к этим позициям.
4. `NearestShiftSelector` выбирает текущую, иначе earliest future среди позиций, эффективный старший которых — текущий пользователь.
5. Если выбрана виртуальная позиция, она материализуется; после блокировки выбор и доступ проверяются повторно.
6. Если подходящих позиций нет, возвращается прежний пустой nearest. ManagerFallback сам по себе не даёт ShiftLead собственной смены, поскольку эффективным старшим в этом случае является Manager.

Благодаря материализации nearest смена, с которой старший реально работал, впоследствии автоматически попадает в history и, если завершена без закрытия, в pending.

### `history` и `pending`

- Работают с материализованными позициями, но фильтруют их по эффективному, а не только явному старшему.
- При замене default доступ к незакрытой истории/pending переходит новому старшему; при очистке default — первому активному Manager.
- При архивации или смене роли резервного Manager незакрытые ManagerFallback-позиции переходят к следующему активному Manager.
- Closed позиции остаются у зафиксированного при закрытии старшего.
- Не выполняют циклы по всем прошлым календарным датам и не материализуют пустые смены массово.
- Для прошлой виртуальной смены Manager/Admin сначала вызывает `materialize` из плана; после этого она доступна по тем же правилам.

## Изменение настроек и графика

### Сохранение настроек

`PUT /api/shifts/default-leads` заменяет весь набор настроек в одной транзакции под `ShiftScheduleLock`:

- тело содержит ровно одну запись на каждую позицию актуального графика, включая `shiftLeadId: null`;
- сервер сверяет набор позиций с актуальным графиком, чтобы устаревшая панель не удалила или не переназначила настройки незаметно;
- каждый ненулевой кандидат повторно проверяется по `IsActive` и `User.Role`;
- замена одного default другим разрешена и не изменяет явные назначения;
- удаление default переводит затронутые незакрытые позиции к первому активному Manager;
- только если активного Manager нет, удаление default проверяет все незакрытые материализованные позиции, которые его используют;
- если в отсутствие Manager удаление оставит позицию с интервалами литейщиков или рапортом без старшего, весь запрос отклоняется;
- после успешного удаления очищаются только пустые сохранённые дни по общему инварианту;
- никакие ошибки не оставляют частично применённый список.

### Изменение справочника смен

Сохранение графика, синхронизация будущих дней и синхронизация default выполняются в одной транзакции:

- позиции `1..N` сохраняют настройки по номеру;
- при увеличении графика новые позиции не получают default;
- при уменьшении строки default с `Position > N` удаляются;
- удаление таких default переводит позиции к первому активному Manager; только при его отсутствии действует запрет оставлять незакрытые операционные данные без старшего;
- перестановка интервалов не угадывается по смыслу: default остаётся у номера позиции, как и существующая позиционная синхронизация плана;
- ошибка откатывает график, план и настройки вместе.

### Изменение пользователя

Архивация, смена роли и очистка логина не переписывают default, явные назначения или закрытые смены:

- в панели текущее архивное/ставшее недопустимым значение показывается с пояснением и может быть очищено или заменено;
- выбрать такого пользователя заново нельзя;
- вход и доступ продолжают определяться актуальными правами пользователя;
- смена роли `ShiftLead` на другую роль не даёт этому пользователю доступ к `/shift-lead` независимо от default;
- назначенный Manager действует через права Manager; назначение не понижает и не повышает роль;
- при архивации первого Manager или смене его роли ManagerFallback автоматически переходит к следующему активному Manager по `CreatedAt, Id`;
- при восстановлении более раннего Manager или возврате ему роли Manager он снова становится fallback для незакрытых позиций без explicit/default;
- создание нового Manager с более поздним `CreatedAt` текущий fallback не меняет;
- если активных Manager не осталось, позиции без explicit/default остаются без старшего; уже имеющиеся литейщики и черновики не удаляются, но операции, требующие старшего, недоступны до назначения ответственного;
- архивация/восстановление и изменение роли Manager сериализуются со staffing/materialize/close через `ShiftScheduleLock`; проверка доступа после блокировки использует актуальный состав активных менеджеров;
- все такие переходы не затрагивают Closed: там старший уже зафиксирован в `ShiftPlanItem.ShiftLeadId`.

## API

### Настройки старших по умолчанию — Manager/Admin

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/shifts/default-leads` | Актуальные позиции графика, их временные поля и default-старшие |
| `PUT` | `/api/shifts/default-leads` | Атомарно заменить весь набор default |
| `GET` | `/api/shift-plan/lead-candidates` | Существующий список активных ShiftLead/Manager; используется повторно |

Ответ GET и PUT содержит `items` и сводку `fallbackManager` (`id`, `fullName`, `employeeId`, `createdAt`) для пояснения автоматического выбора в панели. Если активных Manager нет, `fallbackManager = null`. Тело PUT содержит только `items`: клиент не выбирает и не изменяет fallback напрямую.

Пример элемента `items`:

```json
{
  "position": 1,
  "number": 1,
  "startMinutes": 480,
  "durationMinutes": 720,
  "breakStartMinutes": 240,
  "breakDurationMinutes": 30,
  "timeZoneId": "Europe/Moscow",
  "defaultShiftLeadId": "user-id",
  "defaultShiftLeadName": "Иванов И. И.",
  "defaultShiftLeadEmployeeId": "0012"
}
```

Тело PUT:

```json
{
  "items": [
    { "position": 1, "shiftLeadId": "ivanov-id" },
    { "position": 2, "shiftLeadId": "petrov-id" },
    { "position": 3, "shiftLeadId": null }
  ]
}
```

PUT возвращает актуальные `items` и `fallbackManager`. `GET /api/shifts` и `SaveShiftsRequestDto` не получают поля старшего.

### План смен

`ShiftPlanItemDto` дополняется:

```csharp
public ShiftLeadSource? ShiftLeadSource { get; set; }
// Explicit | Default | ManagerFallback; null — активного Manager нет и старший не найден
```

- `ShiftLeadId/Name` становятся эффективными значениями.
- Для виртуальной default- или ManagerFallback-позиции `Id` остаётся `null`, но старший и источник заполнены.
- `HasMissingLeadWarning` вычисляется по эффективному старшему.
- `CanEditOperators` вычисляется по эффективному старшему и ближайшей/завершённой незакрытой смене; если `Id = null`, frontend сначала вызывает materialize.
- `CanEditLead` по-прежнему запрещает изменение Closed.

Существующий `PUT /api/shift-plan/days/{date}/items/{position}/lead` принимает только явного старшего:

- ненулевой `shiftLeadId` устанавливает override;
- `null` удаляет override и возвращает default, а при его отсутствии — ManagerFallback;
- ответ содержит уже эффективного старшего и его источник.

### Материализация — Manager/Admin

`POST /api/shift-plan/days/{date}/items/{position}/materialize` — идемпотентно сохраняет виртуальный день с эффективным старшим из любого источника и возвращает `ShiftPlanDayDto` с постоянными `itemId`.

Тела нет. Клиент не передаёт окна, старшего или `itemId`. Если у позиции нет эффективного старшего, возвращается `400`: материализация не является способом создать смену без ответственного.

### Staffing и closures

Пути и тела существующих операций не меняются. Меняется только серверное разрешение старшего:

- `GET /api/shift-staffing/nearest` дополнительно рассматривает виртуальные позиции с любым fallback и материализует выбранную, если её эффективный старший — текущий ShiftLead;
- `GET /api/shift-staffing/history` и `GET /api/shift-closures/pending` используют эффективного старшего;
- `ShiftStaffingItemDto`, `ShiftClosureDto` и `ShiftClosurePendingDto` возвращают эффективного `ShiftLeadId/Name`;
- все mutations повторно вычисляют доступ под существующими блокировками;
- `close` фиксирует эффективного старшего в `ShiftPlanItem.ShiftLeadId` в транзакции закрытия.

Отдельное поле источника в мобильном UI и PDF не требуется.

## UI

### Справочник смен

Для Manager/Admin в «Справочники → Смены» добавляется кнопка **«Настройка»**. Observer и остальные роли её не видят.

Кнопка открывает отдельную панель **«Настройка графика смен»**:

- таблица содержит те же временные колонки, что основная таблица справочника;
- справа добавляется колонка **«Старший смены»**;
- временные поля только для чтения; график редактируется по-прежнему через основной диалог;
- в каждой строке — раскрывающийся список активных ShiftLead/Manager с ФИО и табельным номером;
- пустое значение — **«Не задан»**;
- под таблицей показывается пояснение **«Если старший не задан, используется первый активный менеджер: {fallbackManager.fullName}»** либо предупреждение, что активных менеджеров нет;
- один пользователь доступен для выбора в нескольких строках;
- сохранение выполняется кнопкой **«Сохранить»** для всей панели; **«Отмена»** не применяет изменения;
- при `409` показывается сообщение об изменении графика и предлагается перезагрузить панель;
- при `400` показывается серверное сообщение, введённые значения не очищаются;
- архивное сохранённое значение отображается с пометкой, но отсутствует в списке для нового выбора.

Общая страница `/settings` не меняется: эта настройка принадлежит справочнику смен.

### Страница «План смен»

- В ячейке отображается эффективный старший.
- При источнике `Default` рядом показывается компактная подпись/значок **«По умолчанию»**.
- При источнике `ManagerFallback` показывается подпись **«Первый активный менеджер»** с пояснением автоматического выбора.
- При `Explicit` подпись не нужна.
- Если эффективного старшего нет (нет explicit/default и активных Manager), сохраняются «Не назначен» и существующее предупреждение.
- В диалоге назначения пустой выбор обозначается **«По умолчанию: Иванов И. И.»**, если default есть; **«Первый активный менеджер: {name}»**, если default нет; **«Не назначен»**, если нет и активного Manager.
- Для fallback-позиции dropdown не имитирует явное назначение: значение остаётся пустым, а подпись объясняет источник.
- Очистка override сразу обновляет карточку и показывает следующий доступный fallback.
- При открытии виртуальной fallback-смены для работы frontend вызывает `materialize`, затем использует возвращённый `itemId`.
- Пользователь не должен вручную назначать Иванова на каждую дату, чтобы включить ему доступ.

### UI ShiftLead и рапорт

- Экраны «Моя смена», history, pending, карточка ТПА и рапорт визуально не меняются.
- Они получают fallback-смены через существующие DTO.
- Отдельный признак «по умолчанию» или «первый активный менеджер» в мобильном UI не показывается.
- После замены default или смены первого активного Manager очередное обновление показывает смены уже нового эффективного старшего; устаревший запрос прежнего старшего отклоняется сервером.
- Closed рапорт и PDF продолжают показывать зафиксированного при закрытии человека.

## Ошибки и согласованность

| Ситуация | Ответ |
| --- | --- |
| Недопустимый или архивный кандидат, неполный/лишний набор позиций без конфликта версии, очистка default при отсутствии активного Manager с операционными данными, materialize без эффективного старшего | `400` с русским сообщением |
| Недопустимая роль для настроек; чужая/неближайшая смена ShiftLead | `403` |
| Дата/позиция/смена не найдена | `404` |
| График или выбор nearest изменился, пока панель/запрос выполнялся; параллельная материализация или изменение плана | `409`; UI перезагружает актуальные данные |

- Изменения default, графика, явных старших, материализации и закрытия сериализуются через `ShiftScheduleLock`.
- Проверки кандидата, default и доступа повторяются после получения блокировки.
- Замена default не удаляет и не переписывает интервалы литейщиков, ручные поля черновика или явные назначения; при очистке default эти данные переходят к ManagerFallback.
- Только при отсутствии активного Manager очистка default не может оставить незакрытую позицию с рапортом/литейщиками без эффективного старшего.
- Закрытие выполняется в одной транзакции с фиксацией эффективного старшего; позднейшие настройки и изменение порядка активных менеджеров Closed не меняют.
- Все сравнения окон используют серверный `now` и `DateTimeKind.Utc`; новых правил времени и часовых поясов задача не вводит.

## Тестирование

### Unit xUnit

- `EffectiveShiftLeadResolver`: explicit приоритетнее default, default приоритетнее ManagerFallback; отсутствие всех источников; источники `Explicit`/`Default`/`ManagerFallback`/none.
- Выбор первого Manager: только активные пользователи ровно с ролью Manager, порядок `CreatedAt ASC, Id ASC`, равные метки, архивные, Admin и другие роли, пустой список.

- `NearestShiftSelector.IsNearestForManager` использует эффективных старших и не выбирает позиции без них.
- Позиционная синхронизация default: столько же/больше/меньше позиций, перестановка окон, сохранение явных назначений.
- Очистка explicit с default или ManagerFallback оставляет эффективного старшего; без обоих сохраняются прежние ограничения.
- Границы current/future/history и UTC остаются неизменными.

### Integration xUnit + Testcontainers

- Миграция: `User.CreatedAt` обязателен и имеет UTC-значения у существующих/новых пользователей; индекс выборки первого Manager; PK `ShiftDefaultLeads.Position`, check `Position >= 1`, FK пользователя, индекс; отсутствие FK на пересоздаваемые `Shifts`.
- Создание пользователя через все существующие API/seed заполняет `CreatedAt` сервером; клиент не может подменить дату.
- GET/PUT настроек: полный round-trip, null = удаление строки, один пользователь на нескольких позициях, корректный `fallbackManager`, атомарность и полная матрица ролей.
- Кандидаты: активные ShiftLead/Manager, Manager сам для себя; Admin/Operator/Adjuster/Observer и архивные запрещены.
- План виртуального и сохранённого дня: эффективный старший, источники Explicit/Default/ManagerFallback, отсутствие missing-lead warning при любом найденном старшем, предупреждение при отсутствии активного Manager без других источников.

- Полный поток default- и ManagerFallback-смены: ТПА → назначение/интервалы литейщиков → черновик → pending → закрытие; резервный Manager работает через контур Manager.
- Manager/Admin могут materialize и открыть виртуальную default- или ManagerFallback-смену; materialize без эффективного старшего запрещён.
- Явный override отключает default и ManagerFallback для одной даты; очистка override выбирает следующий источник и сохраняет литейщиков/черновик.
- Замена default передаёт незакрытые nearest/pending/history новому пользователю, сохраняет данные и не затрагивает explicit.
- Очистка default передаёт незакрытые позиции первому активному Manager; без активного Manager очистка с интервалами/черновиком отклоняется атомарно, очистка без данных разрешена и удаляет только пустые дни.
- Архивация/смена роли первого Manager передаёт ManagerFallback следующему; восстановление более раннего возвращает выбор ему; новый более поздний Manager выбор не меняет; Closed неизменен.
- Закрытие фиксирует default или ManagerFallback в `ShiftLeadId`; смена настройки, архивация/восстановление менеджеров и создание новых пользователей после закрытия не меняют Closed DTO, PDF и доступ к истории.
- History/pending не генерируют прошлые виртуальные дни массово; materialize прошлой смены добавляет её в обычный контур.
- Изменение графика сохраняет default по позиции, добавляет пустые новые настройки, удаляет лишние и откатывается вместе с планом при конфликте.
- Архивация/смена роли/отсутствие логина не дают незаконного доступа; исторические ссылки остаются.
- Параллельные изменение default, архивация/смена роли Manager, nearest/materialize, explicit override и close дают согласованный результат либо `409`.
- Регрессия: при отсутствии explicit/default и активных Manager поведение смены без старшего остаётся прежним; при наличии Manager применяется новый ManagerFallback.

- Один кандидат доступен в нескольких строках; архивное текущее значение отображается с пометкой.
- План показывает default-имя и подпись источника, ManagerFallback с подписью «Первый активный менеджер», explicit без подписи; missing-lead warning появляется только при отсутствии всех источников.
- Диалог назначения показывает следующий fallback, устанавливает override и возвращается к default либо ManagerFallback при очистке.
- Открытие виртуальной fallback-смены вызывает materialize до перехода по `itemId`; ошибка не ведёт на несуществующую смену.
- Home/history/pending продолжают работать с обычными DTO и обновляются после смены доступа.
- Вкладка рапорта доступна при эффективном default- или ManagerFallback-старшем.
- Регрессионные тесты смен без старшего выполняются при отсутствии explicit/default и активных Manager.

## Документация и версия

- Добавить ADR-0032 «Старший смены по умолчанию и эффективная ответственность»: default по позиции, ManagerFallback по `User.CreatedAt, Id`, единый resolver, ленивая материализация, замена/очистка default и фиксация при закрытии.
- В ADR зафиксировать отвергнутые альтернативы: FK на пересоздаваемый `Shift.Id`, копирование default/fallback в каждый `ShiftPlanItem`, выбор менеджера по табельному номеру или клиентскому времени, массовая материализация календаря/background worker, подстановка только во frontend, динамический fallback для Closed.
- Обновить `CLAUDE.md`: прежнее правило «постоянной привязки нет» и существование `ShiftPlanDay` только при явном старшем заменяются цепочкой Explicit → Default → первый активный Manager; описать `User.CreatedAt`, возврат к следующему источнику при очистке explicit и заморозку при закрытии.
- Обновить `docs/adr/README.md` и руководства Manager/Admin и ShiftLead.
- Перед PR поднять `VERSION` **1.36.0 → 1.37.0** (новая функциональность — минор).

## Вне задачи

- Ручной выбор резервного менеджера отдельно от правила «самый ранний активный Manager» и ручное редактирование `User.CreatedAt`.
- Отдельный override «на этой дате старшего нет» при включённом default или наличии активного Manager.
- Несколько старших по умолчанию на одну позицию.
- Расписание разных default по датам, дням недели или интервалам действия.
- Аудит изменений default и автоматические уведомления старших.
- Массовая материализация будущего/прошлого и автоматическое создание пустых рапортов.
- Автоматическая очистка default при архивации/смене роли пользователя.
- Изменение ролей `Operator`, `Adjuster`, `Observer`, общего справочника пользователей и правил необязательного логина.
- Новые поля или источник старшего в Closed PDF сверх фиксации ответственного.
