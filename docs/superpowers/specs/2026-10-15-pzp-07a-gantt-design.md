# PZP-07a — План-график цеха (Гантт загрузки, только чтение)

- **Дата:** 2026-10-15
- **Эпик:** PZP-07, этап 07a (см. `2026-10-15-pzp-07-epic-decomposition.md`)
- **Ветка:** `feature/pzp-07a-gantt` → PR в `epic/pzp-07-planning`
- **Статус:** дизайн утверждён, готов к плану реализации
- **ADR:** не нужен — контракт API аддитивный, схема БД не меняется

## Проблема

План заданий есть (PZP-13 — плановое начало, PZP-14 — норматив наладки и буфер выпуска), факт
есть (метки задания, циклы), прогноз окончания выпуска есть (BL-32). Но картины загрузки цеха
нет: план и факт видны только по одному заданию (карточка) или по одной смене одного ТПА
(хронология карточки ТПА, BL-40). Начальник производства не видит неделю по всем ТПА: где
плотно, где просрочено, где факт съел буфер и следующее задание под угрозой.

## Акторы и сценарии (use cases)

- **Начальник производства (Manager/Admin), недельный план.** Открывает «Планирование →
  План-график цеха», видит неделю по всем ТПА: плотность загрузки, просроченные неначатые
  задания (красная метка), задания, у которых факт съел буфер. Чтобы сдвинуть следующее задание,
  кликает по бару → карточка задания → «Редактировать» → правит плановое начало → сохраняет;
  Гантт перезагружается.
- **Мастер смены (Manager), оперативный контроль.** Масштаб «Сутки»: видит отставание наладки
  («наладка отстала на 25 мин») и прогноз окончания выпуска — уложится ли выпуск в буфер или
  будет перерасход.
- **Руководитель (Observer).** Видит всё то же самое, карточка задания — без кнопок действий.
  Также получает доступ только на чтение к «Заказам» и «Заданиям» (раздел «Доступ Observer к
  Планированию»).
- **Наладчик (Adjuster)** Гантт не видит (мобильный интерфейс).

## Решения (зафиксированы при брейнсторминге 2026-10-15)

1. **Масштаб по умолчанию — неделя**, переключатель «Сутки / Неделя / Месяц», навигация
   «← Сегодня →». Неделя — с понедельника; сутки — от начала первой смены; месяц — календарный.
2. **Неинтерактивный Гантт.** Мышкой ничего не двигается; клик по бару открывает карточку
   задания, план правится там (решение 2026-10-11).
3. **Просроченное неначатое задание** (`Planned`/`Issued`, плановое начало прошло, наладка не
   начата) — план-бар остаётся на своём месте, на нём красная метка «не начато, опоздание N».
   - Отвергнуто: «тень» с позиции «если начать сейчас» — это прогноз коллизий, этап 07b.
   - Отвергнуто: убирать такие задания в отдельный список.
4. **Факт-бар задания в выпуске** (`InProgress`): выпуск до «сейчас» сплошной, от «сейчас» до
   прогнозного окончания (`ReleaseForecast`, ADR-0017) — штрих. Остаток буфера
   `= P − прогнозное окончание`, где P — плановое окончание с буфером (`TaskDto.PlannedEndAt`).
   Остаток > 0 — сегмент цвета буфера; < 0 — **красный сегмент перерасхода** от P до прогнозного
   окончания, в тултипе «перерасход N мин». У завершённого задания (`Completed`/`Closed`)
   остаток `= P − CompletedAt` (для `Closed` без `CompletedAt` — от `ClosedAt`).
5. **Задание на наладке** (`Setup`): прогноз и остаток **не считаются**. Если
   `now > plannedStartAt + plannedSetupMinutes`, на факт-баре текст «наладка отстала на X мин»;
   иначе текста нет.
6. **Данные — новый эндпоинт** `GET /api/planning/board`, расчёт в Core.
   - Отвергнуто: только фронт поверх `GET /api/imms` + двух `GET /api/tasks` (как в BL-40):
     прогноз привязан к ТПА, а не к заданию; для 07b/07f всё равно нужна серверная логика.
7. **Отрисовка — своя на HTML/CSS**, по образцу `ShiftTimeline` (BL-40).
   - Отвергнуто: ECharts `custom`-серия. Готового Гантта в ECharts нет, сегменты всё равно
     рисуются вручную; штриховка, обрезка текста и клики на canvas сложнее; canvas не проверить
     в Vitest/jsdom; масштаб (единицы ТПА, десятки баров) не требует canvas. Пересмотреть, если
     понадобится плавный зум мышью.
8. **Строки** — все активные ТПА в порядке дашборда; архивный ТПА — только если у него есть
   задания в окне, с пометкой «в архиве».
9. **Цвет пары** — по статусу задания; сегменты различаются оттенком (наладка светлее, буфер —
   штрих). Подпись план-бара: «№ · артикул · план шт» (многоточие). Тултип — полные данные.
10. **Сетка**: вертикальная красная линия «сейчас»; на «Сутках» — границы смен; на «Неделе» и
    «Месяце» — границы суток. **Обновление** — раз в 60 с.
11. **Меню**: в существующее подменю «Планирование» добавляется пункт «План-график цеха»
    (`/planning/gantt`). Подменю видно Admin/Manager/Observer.

## Бэкенд

### `GET /api/planning/board?from=<UTC>&to=<UTC>`

Новый `PlanningController`, роли Admin/Manager/Observer. `from`/`to` — `DateTime` UTC
(`SpecifyKind(…, Utc)` сразу после биндинга, правило CLAUDE.md); `from < to`, длина окна
≤ 62 суток (месяц с запасом), иначе 400.

```
PlanningBoardDto {
  from, to, now                       // UTC
  rows: [ {
    imm: { id, name, isActive },
    tasks: [ BoardTaskDto ]           // по plan.setupStart, затем по id
  } ]
}
BoardTaskDto {
  task: TaskDto                       // полный — его же получает TaskDetailModal
  plan: { setupStart, setupEnd, releaseEnd, bufferEnd }        // UTC; releaseEnd/bufferEnd null,
                                                                 // если план выпуска не считается
  fact: { setupStart?, setupEnd?, releaseEnd?, forecastEnd? }  // UTC
  bufferRemainingSeconds?             // < 0 — перерасход; null — не считается
  overdueNotStartedSeconds?           // > 0 только у просроченных Planned/Issued
  setupLagSeconds?                    // > 0 только у Setup с отставанием
}
```

- `plan.setupStart = PlannedStartAt`, `setupEnd = setupStart + PlannedSetupMinutes`,
  `releaseEnd = setupEnd + выпуск`, `bufferEnd = releaseEnd + буфер` — по `TaskPlanCalculator`
  (то же, что `TaskDto.PlannedEndAt`).
- `fact.setupStart = SetupStartedAt`, `fact.setupEnd = StartedAt`,
  `fact.releaseEnd = CompletedAt ?? ClosedAt` (для завершённых), `fact.forecastEnd` — только
  `InProgress`, из `ReleaseForecast`.

### Отбор заданий

Задание попадает на доску, если его **плановое окно** `[plan.setupStart, plan.bufferEnd ??
plan.setupEnd)` **или окно активности** (`TaskActivityWindow`) пересекает `[from, to)`.
План не хранится, поэтому в EF отбор грубый: `PlannedDate` в `[from − 2 сут, to + 1 сут]`
**или** `TaskActivityWindow.OverlapsPeriod`; точная фильтрация по плановому окну — в памяти после
расчёта. Архивные статусы (`Completed`/`Closed`) не исключаются. Плановое окно длиннее 2 суток
с началом раньше `from − 2 сут` и без активности в окне на доску не попадёт — принимаем
(такое задание либо идёт — тогда попадёт по активности, — либо просрочено на дни, и его видно в
списке заданий).

### Расчёт — `PlanningBoardCalculator` (Core/Policies)

Чистая функция `Build(TaskPlanInput, TaskFacts, ReleaseForecastResult?, DateTime nowUtc)` →
сегменты плана/факта, остаток буфера, просрочка, отставание наладки. Поверх
`TaskPlanCalculator` и `ReleaseForecast`, без EF.

### Попутный рефакторинг

Сбор входов прогноза (статистика закрытых циклов задания, `AVG(DurationSeconds)`,
`AVG(PauseDurationMs)`, гнёзда, эталон) сейчас живёт в `ImmController`. Выносится в сервис
Infrastructure (`IReleaseForecastInputs` или аналог, имя — в плане), которым пользуются и
`ImmController`, и `PlanningController` — прогноз на плитке ТПА и на Гантте гарантированно
одинаков. Поведение `GET /api/imms` не меняется.

## Доступ Observer к Планированию (отдельный PR, первым)

Сейчас «Заказы» и «Задания» закрыты для Observer на всех уровнях. Делаем **только чтение**:

- **Бэкенд.** `OrdersController`: `[Authorize]` на классе — Admin/Manager/Observer для `GET`
  (список, по id); все изменяющие методы — явно Admin/Manager. `TasksController.GetTaskById` —
  добавить Observer. Остальные изменяющие методы не трогаем.
- **Фронт.** Подменю «Планирование» — `canAccess(['Admin','Manager','Observer'])`; роуты
  `/orders`, `/tasks`, `/planning/gantt` — с Observer. В `OrdersView` и `TasksView` все кнопки
  изменения (создать, редактировать, выдать, завершить, закрыть, отменить, переоткрыть,
  привязать/отвязать задания) скрыты для Observer. Меню «Администрирование» остаётся только
  для Admin (уже так).
- Защита записи — на бэкенде: забытая кнопка даёт Observer 403, не порчу данных.

## Фронтенд

- `views/planning/PlanningGanttView.vue` — страница: шапка (масштаб, навигация, подпись
  периода), загрузка доски, таймер 60 с, модалки `TaskDetailModal`, `TaskFormModal`,
  `IssueTaskDialog`; после сохранения — перезагрузка доски.
- `components/planning/GanttBoard.vue` — колонка ТПА, ось с тиками, сетка, линия «сейчас»,
  строки.
- `components/planning/GanttTaskPair.vue` — пара план/факт одного задания: сегменты, подписи,
  метки, тултип, клик.
- `utils/planningBoard.js` — чистые функции: окно периода по масштабу и якорю; время → % ширины
  с обрезкой по краям окна; тики сетки; раскладка пар по дорожкам (переиспользует `assignLanes`
  из `shiftTimeline.js`); сегменты к отрисовке без нулевых; тексты меток («не начато, опоздание
  2 ч 10 мин», «наладка отстала на 25 мин», «перерасход 40 мин»).
- Время на экране — в поясе браузера; на сервер — UTC.

## Обработка ошибок

- Ошибка загрузки доски — `ElMessage` с текстом из `apiError.js`, на экране остаётся последняя
  загруженная доска; таймер продолжает попытки.
- 400 на окно (длина/порядок) — невозможна из UI; при ручном вызове API — текст ошибки.
- Задание без плана выпуска (нет эталона/гнёзд) — план-бар только из наладки, остаток буфера
  `null`.

## Тестирование

- **xUnit (Core):** `PlanningBoardCalculator` — все статусы; нулевые сегменты; остаток > 0, = 0,
  < 0; `Closed` без `CompletedAt`; просрочка неначатого; отставание наладки и его отсутствие;
  `InProgress` без прогноза.
- **xUnit (интеграция):** отбор по плановому окну и по окну активности, задание вне окна не
  попадает, архивный ТПА — только с заданиями; роли: Observer 200, Adjuster 403; окно > 62 сут
  → 400. Observer: `GET /api/orders` 200, `POST /api/orders` 403, `GET /api/tasks/{id}` 200.
- **Vitest:** `planningBoard.js` (периоды для трёх масштабов, тики, дорожки, сегменты, тексты);
  `GanttTaskPair` (перерасход, штрих прогноза, метки); Observer не видит кнопок изменения в
  `OrdersView`/`TasksView`/`TaskDetailModal`.
