# BL-32: прогноз окончания выпуска на плитке ТПА — дизайн

Дата: 2026-10-14 · Статус: утверждён · Беклог: BL-32 (требование ПЗП), расчёт общий с PZP-07

## Проблема

Плитка ТПА на дашборде (`ImmCard.vue`) показывает «Темп» и «Прогноз окончания». Оба считаются
только на фронте: темп = `факт / (сейчас − StartedAt)`, прогноз = `сейчас + (план − факт) / темп`.
Начальная наладка исключена (`StartedAt` — момент Setup→InProgress), но в знаменатель попадает всё,
что было после неё: повторная наладка (`Manual`), простои, аварии, нет связи. Час простоя занижает темп,
и прогноз переносит эту долю простоя на весь остаток выпуска.

Требование заказчика: **время наладки не входит в прогноз**. Решено строить прогноз по чистой работе:
по фактическому периоду цикла, без экстраполяции прошлых остановок на будущее.

Дату в прогнозе («сегодня/завтра/ДД.ММ в ЧЧ:ММ») уже добавил PR #123, здесь её не трогаем.

## Ключевой факт: длительность цикла не включает паузу

По контракту v2 `lastCycle.startTime` = фронт `MoldClosed`, `endTime` = фронт `MoldOpened`
(коннектор USR-Modbus, `MachineStateMachine.cs`, состояние S2). Выталкивание, съём детали и ожидание
оператора в полуавтомате идут после `MoldOpened` (состояние S5) и в `ImmCycle.DurationSeconds` не
входят. Прогноз только по `DurationSeconds` систематически занижен, поэтому темп считаем по
**полному периоду** = цикл + пауза перед следующим циклом.

## Акторы и сценарии (use cases)

Актор — любой пользователь дашборда (Admin, Manager, Adjuster, Observer). Сценарии 1–6 видны на плитке ТПА
(`GET /api/imm` → `ImmCard.vue`).

1. **Ровная работа.** Задание в `InProgress`, закрыто ≥ 3 циклов. Плитка показывает темп
   `гнёзда × 3600 / период` шт/ч и прогноз `сейчас + ⌈(план − факт) / гнёзда⌉ × период`.
   Тест: `ReleaseForecastTests`, `ImmControllerTests` (поля DTO).
2. **Начало выпуска.** Закрыто меньше 3 циклов → период = эталон задания `PlannedFullCycleSeconds`.
   Тест: `ReleaseForecastTests`.
3. **Простой в середине задания.** Цикл закрылся, ТПА сломался, через 15 мин коннектор перевёл
   его в `Idle`, через 30 мин работа возобновилась. Пауза 45 мин записывается как `null` и в средний
   период не входит. Прогноз после возобновления — от нового «сейчас» по прежнему темпу.
   Тест: `CyclePauseTests`, интеграционный тест хендлера.
4. **Короткая ручная наладка.** Между циклами ТПА 5 мин был в `Manual` → пауза `null`.
   Тест: `CyclePauseTests`.
5. **Залипание формы / ожидание оператора.** Пауза 2 мин, статус всё время `Auto` → пауза
   записывается и увеличивает средний период: частые сбои честно замедляют прогноз.
   Тест: `CyclePauseTests`.
6. **Кратковременный обрыв связи.** Между циклами 20 с `Offline` → пауза записывается.
   Долгий обрыв (пауза ≥ 900 с) → `null`. Тест: `CyclePauseTests`.
7. **Нет прогноза.** Задание в `Setup`, нет активного задания, факт ≥ плана, у ПФ 0 гнёзд, нет ни
   циклов, ни эталона → темп «—», строка прогноза скрыта. Тест: `ReleaseForecastTests`, Vitest.

## Решение

### 1. Пауза перед циклом — `ImmCycle.PauseDurationMs`

Поле уже есть в схеме (всегда `null`), миграция не нужна. Заполняет `CycleProcessingHandler` при
**создании** строки `ImmCycle` (открытие по `currentCycle` или «внезапное» закрытие по `lastCycle`):

- предыдущий цикл — последний по `StartTime` `ImmCycle` **этого ТПА** (`StartTime < StartTime`
  нового), независимо от задания; если он ещё открыт (`EndTime = null`) — `null`;
- пауза = `StartTime(новый) − EndTime(предыдущий)`, мс;
- `null`, если:
  - предыдущего цикла нет;
  - пауза ≥ `DowntimeSettings.IdleThresholdSeconds` (900 с, ADR-0010);
  - в `ImmStatusHistory` есть запись со статусом **не** из `{Auto, Offline}`, чей интервал
    `[ChangedAt, EndedAt ?? ∞)` пересекает `(EndTime пред., StartTime нов.)`;
  - пауза < 0 (часы/порядок сообщений) — защитно.

Решение «значение или `null`» — чистая функция `CyclePause.Resolve(prevEnd, newStart,
hasForeignStatus, thresholdSeconds)` в `Core/Policies`. Хендлер достаёт `prevEnd` и
`hasForeignStatus` двумя запросами (по индексу `(ImmId, StartTime)` и по истории статусов ТПА)
и передаёт в неё.

Пауза принадлежит ТПА, а не заданию. У первого цикла задания она обычно `null`: между заданиями
идёт наладка (`Manual`) или пауза больше порога.

### 2. Прогноз — `ReleaseForecast` (`Core/Policies`, чистая функция)

Вход: `PlanQuantity`, `ActualQuantity`, текущие `Mold.Cavities` (это прогноз, не история, как в
`TaskPlanCalculator`), число закрытых циклов задания, `AVG(DurationSeconds)` и
`AVG(PauseDurationMs)` по закрытым циклам задания, `PlannedFullCycleSeconds`, `now`.

```
период = закрытых ≥ 3 ? AVG(DurationSeconds) + (AVG(PauseDurationMs) ?? 0) / 1000
                      : PlannedFullCycleSeconds
темп   = гнёзда × 3600 / период                      (шт/ч)
окончание = now + ⌈(план − факт) / гнёзда⌉ × период
```

Выход: `RatePerHour` и `ForecastAt` (оба nullable). `null`, если гнёзд ≤ 0 или период ≤ 0.
`ForecastAt = null` дополнительно при факт ≥ план. Порог 3 — константа в политике.
Статус задания проверяет вызывающий: прогноз только для `InProgress`.

Функция переиспользуется Ганттом PZP-07 (прогноз завершения выпуска на баре, остаток буфера).

### 3. API — `GET /api/imm`

В `ImmController.GetImmList` уже есть агрегат по циклам текущего задания (`Count`, `AvgDuration`).
Расширяем его: число закрытых циклов, `AVG(PauseDurationMs)` (`null` не учитываются). Для заданий
в `InProgress` из проекции нужны `PlannedFullCycleSeconds`, `Mold.Cavities`, статус.

`ImmDto` — новые поля:
- `ReleaseRatePerHour` (`decimal?`) — темп, шт/ч;
- `ReleaseForecastAt` (`DateTime?`, UTC) — прогноз окончания выпуска.

`TaskStartedAt` после этого фронту не нужен; поле оставляем (дешёвое, может понадобиться).

### 4. Фронтенд — `ImmCard.vue`

- «Темп» = `Math.round(imm.releaseRatePerHour)` шт/ч или «—».
- «Прогноз окончания» = `formatForecastMoment(new Date(imm.releaseForecastAt))`, строка скрыта
  при `null`.
- Расчёт `ratePerHour`/`etaLabel` по прошедшему времени удаляется. Маппинг полей — в
  `stores/dashboard.js`.

### 5. Документация

- **ADR-0017** «Прогноз окончания выпуска по среднему периоду цикла»: методика, правила `null` для
  паузы, fallback на эталон; отвергнутые варианты — темп по прошедшему времени (с вычетом наладки
  или без), выборка последних N / 10% циклов (точность среднего зависит от абсолютного размера
  выборки, а не от доли; `AVG` по всем циклам задания — агрегат в БД по индексу, он дешёвый),
  только `DurationSeconds` без паузы.
- **ADR-0012** — уточнение в «Последствиях» (не по существу): «потребитель» паузы — Control; она
  вычисляется в Control и хранится в `ImmCycle.PauseDurationMs`, способ — ADR-0017.
- **CLAUDE.md** — заменить фразу «`PauseDurationMs` … ничем не заполняется» на правило-итог и
  ссылку на ADR-0017.
- Руководство пользователя `docs/user-guide/manager.md` (строки «Темп», «Прогноз окончания») — новый смысл: темп по среднему периоду цикла, прогноз без наладки и простоев.

## Тесты

- xUnit unit: `CyclePauseTests` (сценарии 3–6, нет предыдущего, отрицательная пауза, ровно порог),
  `ReleaseForecastTests` (1, 2, 7; округление вверх по смыканиям; пауза `null` → 0).
- xUnit integration: `CycleProcessingHandler` пишет `PauseDurationMs` (значение / `null` при `Idle`
  в истории); `GET /api/imm` отдаёт `ReleaseRatePerHour`/`ReleaseForecastAt`.
- Vitest: `ImmCard` выводит темп и прогноз из полей DTO, скрывает прогноз при `null`.

## Вне объёма

- Точный вычет короткой ручной наладки, если статус `Manual` не был зафиксирован (полагаемся на
  статус из телеметрии).
- Прогноз в `Setup` (остаток наладки + выпуск) — для Гантта PZP-07, не для плитки.
- Пауза между циклами разных заданий в аналитике — поле хранится сырым по ТПА; трактовка на стороне
  отчётов.
