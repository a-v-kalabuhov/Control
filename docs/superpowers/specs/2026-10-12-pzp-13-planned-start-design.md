# PZP-13 — Плановая дата и время начала наладки в задании

- **Дата:** 2026-10-12
- **Задача:** PZP-13 (🔴 приоритет, первый шаг к PZP-07 «Планирование на Гантте»)
- **Статус:** дизайн утверждён, готов к плану реализации
- **ADR:** ADR-0014 (пишется в рамках задачи)

## Проблема

Планировщик раз в месяц смотрит заказы и сразу заводит из них задания. Задание может длиться
несколько смен и начинается, только когда подойдёт его время. Сейчас:

- у задания есть только `ShiftTask.PlannedDate` — необязательное, только дата, хранится как
  UTC-полночь, правится **только в черновике**;
- наладчик видит задания на планшете разложенными по моменту **выдачи** (`IssuedAt` относительно
  начала смены). Задания, выданные на месяц вперёд, сразу попадают в «Незавершённые с прошлых
  смен» — порядок работы из этого не понять;
- наладчик в задании необязателен, но назначить его можно только при создании
  (`UpdateTaskRequestDto` не содержит `PersonnelId`), а выдать можно и без наладчика — такое
  задание не увидит ни один планшет.

Программа решает у заказчиков две разные задачи:

1. **Контроль выполнения заданий и анализ простоев** — базовый сценарий. Мощности обычно в
   избытке (проблема в поиске заказов, а не в выпуске), детальное планирование не нужно.
   Достаточно плановой **даты**.
2. **Повышение загрузки ТПА за счёт точного планирования** — нужен Гантт (PZP-07) и точное
   **время** начала наладки.

Модель задания должна обслуживать оба сценария, не заставляя первую группу вводить время.

## Решения (зафиксированы при брейнсторминге 2026-10-12)

1. **Два поля вместо одного.**
   - `PlannedDate` — `DateOnly` (колонка `date`), **обязательное**. Календарная дата завода.
   - `PlannedSetupStartTime` — `TimeOnly?` (колонка `time`), **необязательное**. Время по часам
     завода — в той же системе, что минуты смен (`Shift.StartMinutes` в `Shift.TimeZoneId`).
   - Отвергнуто: одно поле «дата+время» (`timestamptz`) — пришлось бы различать «время не задано»
     и «полночь», а пользователь думает именно «15-го» или «15-го в 14:00».
   - Отвергнуто: добавить новое поле рядом со старым `PlannedDate` как UTC-полночью — два похожих
     источника правды. Legacy-данных нет (идёт пилот), старое поле переделываем.
2. **Эффективное плановое начало вычисляется, не хранится.** Чистая функция
   `PlannedTaskStart.Resolve` (`Core/Policies`, по образцу `ImmEffectiveStatus`):
   - время задано → `PlannedDate + PlannedSetupStartTime` в поясе завода → UTC;
   - время пустое → начало **самой ранней смены** (минимальный `StartMinutes`) в этот день;
   - смен нет → 00:00 этого дня.
   Пояс завода — `TimeZoneId` самой ранней смены (как в `ReportService`), по умолчанию
   `Europe/Moscow`. Результат отдаётся в `TaskDto.PlannedStartAt` (UTC). Фронт и будущий Гантт
   берут его оттуда и логику не дублируют. Для пользователей первой группы задание на Гантте
   начинается с начала смены.
3. **Правка плана — в «Планируется» и «Выдано».** После начала наладки план замораживается: он
   нужен для сравнения план/факт (Гантт, BL-06, BL-12).
4. **Наладчик обязателен для выдачи.** Задание без наладчика нельзя выдать — оно остаётся в
   «Планируется». Кнопка «Выдать» открывает диалог выбора наладчика (предзаполнен, если уже
   назначен): назначение и выдача — одна операция. Это соответствует процессу:
   производственный план на месяц — по ТПА без наладчиков; перед сменой начальник производства
   назначает наладчиков — получается план работ на смену.
5. **Переназначение наладчика в «Выдано»** разрешено (заболел — передать другому без отката в
   черновик), но снять наладчика у выданного задания нельзя.
6. **«Черновик» → «Планируется».** Меняется только подпись в UI и текстах ошибок. Enum
   `TaskStatus.Draft` и строка `"Draft"` в API не меняются.
7. **Планшет наладчика — разделы по плану:** «В работе» (Наладка/В работе) → «Очередь» (Выдано,
   по возрастанию `PlannedStartAt`, метки «опаздывает» / «сегодня») → «Архив». Граница смены для
   разбивки больше не нужна.
8. **Просрочка** = статус «Планируется» или «Выдано» и сейчас позже `PlannedStartAt`. Задания в
   работе по этому признаку не просрочены (плановое окончание — PZP-14).

## Акторы и сценарии (use cases)

**Акторы:** Менеджер/Администратор (далее «менеджер» — права `ManagerOrAdmin`), Наладчик (`Adjuster`).

### UC-1. Менеджер планирует задание на дату (без времени)
- **Поток:** менеджер создаёт задание: ТПА, ПФ, план, эталон цикла, **плановая дата**, наладчик и
  время не указаны → задание в статусе «Планируется»; `PlannedStartAt` = начало первой смены этой
  даты.
- **Альтернативы:**
  - дата не указана → 400 «Укажите плановую дату»;
  - дата в прошлом (раньше сегодняшней даты завода) → 400 «Плановая дата не может быть в прошлом».
- **Endpoint:** `POST /api/tasks`. **Тесты:** `CreateTask_WithDateOnly_PlannedStartIsFirstShiftStart`,
  `CreateTask_WithoutPlannedDate_Returns400`, `CreateTask_PastDate_Returns400`.

### UC-2. Менеджер планирует задание с точным временем начала наладки
- **Поток:** как UC-1 + «время начала наладки» 14:00 → `PlannedStartAt` = дата 14:00 по поясу завода
  (в UTC).
- **Альтернативы:** дата — сегодня, время уже прошло (с допуском 5 минут) → 400 «Время начала
  наладки не может быть в прошлом».
- **Endpoint:** `POST /api/tasks`. **Тесты:** `CreateTask_WithTime_PlannedStartIsDatePlusTime`,
  `CreateTask_TodayPastTime_Returns400`; юнит-тесты `PlannedTaskStart.Resolve`.

### UC-3. Менеджер переносит задание (в «Планируется» или «Выдано»)
- **Поток:** менеджер открывает карточку задания, меняет дату и/или время (может очистить время),
  сохраняет. В «Выдано» в форме доступны только плановая дата, время и наладчик, остальные поля
  заблокированы.
- **Альтернативы:**
  - статус Наладка / В работе / Завершено / Закрыто → 400 «Плановое начало можно изменить только
    до начала наладки»;
  - новое значение в прошлом → 400 (как в UC-1/UC-2); проверяется только изменённое значение —
    сохранение формы с прежней (уже прошедшей) датой не падает.
- **Endpoint:** `PUT /api/tasks/{id}`. **Тесты:** `UpdateTask_IssuedTask_ChangesPlannedDate`,
  `UpdateTask_ClearTime_SetsNull`, `UpdateTask_InProgress_ChangePlan_Returns400`,
  `UpdateTask_UnchangedPastDate_Succeeds`; доменные тесты `ShiftTask.SetPlannedStart`.

### UC-4. Менеджер назначает / снимает / переназначает наладчика
- **Поток:** в карточке задания выбирает наладчика (или очищает поле в «Планируется»), сохраняет.
- **Альтернативы:**
  - «Выдано» и наладчик очищается → 400 «У выданного задания должен быть наладчик»;
  - статус после начала наладки → 400 «Наладчика можно изменить только до начала наладки»;
  - пользователь не найден, в архиве или не наладчик → 400 «Укажите активного наладчика».
- **Endpoint:** `PUT /api/tasks/{id}/personnel` `{ personnelId: string | null }`.
  **Тесты:** `SetPersonnel_Draft_AssignsAndClears`, `SetPersonnel_Issued_Reassigns`,
  `SetPersonnel_Issued_Clear_Returns400`, `SetPersonnel_InProgress_Returns400`,
  `SetPersonnel_NotAdjuster_Returns400`.

### UC-5. Менеджер выдаёт задание
- **Поток:** «Выдать» → диалог выбора наладчика (предзаполнен назначенным) → «Выдать» → задание
  получает наладчика (если выбран другой) и переходит в «Выдано», `IssuedAt = now`.
- **Альтернативы:**
  - наладчик не выбран и не был назначен → 400 «Назначьте наладчика»;
  - задание не в «Планируется» → 400 «Задание не в статусе «Планируется»»;
  - наладчик невалиден → 400 (как в UC-4).
- **Endpoint:** `POST /api/tasks/{id}/issue` с необязательным телом `{ personnelId }`.
  **Тесты:** `IssueTask_WithPersonnelInBody_AssignsAndIssues`, `IssueTask_AlreadyAssigned_NoBody_Issues`,
  `IssueTask_NoPersonnel_Returns400`; доменный `Issue_WithoutPersonnel_Throws`.

### UC-6. Наладчик видит свою очередь
- **Поток:** наладчик открывает планшет: «В работе» — его задания в Наладке/В работе; «Очередь» —
  выданные ему задания по возрастанию `PlannedStartAt`; у задания, чьё плановое начало прошло, —
  метка «опаздывает», у задания на сегодня — «сегодня»; «Архив» — завершённые/закрытые, новые
  сверху, постранично. Поиск по ТПА/ПФ работает во всех разделах.
- **Альтернативы:** задания в «Планируется» на планшете не видны (как сейчас).
- **Endpoint:** `GET /api/tasks/my?search=&archivePage=&archivePageSize=`.
  **Тесты:** `GetMyTasks_QueueSortedByPlannedStart`, `GetMyTasks_ActiveSectionHasSetupAndInProgress`,
  `GetMyTasks_ArchivePagedNewestFirst`, `GetMyTasks_DraftHidden`; Vitest на разделы и метки.

### UC-7. Менеджер видит просроченные задания
- **Поток:** на странице заданий счётчик «Просрочено» и колонка «Плановое начало» («15.10» или
  «15.10 14:00», сортировка по `PlannedStartAt`).
- **Endpoint:** `GET /api/tasks` (поле `plannedStartAt` в DTO). **Тесты:** Vitest
  `overdueTasks` (Issued после `plannedStartAt` — просрочено; InProgress — нет).

## Схема и миграция

`ShiftTask`:

| Было | Стало |
|---|---|
| `DateTime? PlannedDate` (`timestamptz`) | `DateOnly PlannedDate` (`date`, NOT NULL) |
| — | `TimeOnly? PlannedSetupStartTime` (`time`, NULL) |

Миграция `PlannedStartDateTime` (одна):
1. добавить `PlannedDateNew date NULL`, заполнить
   `COALESCE("PlannedDate", "IssuedAt", "CreatedAt")::date`;
2. удалить старую колонку, переименовать новую в `PlannedDate`, `SET NOT NULL`;
3. добавить `PlannedSetupStartTime time NULL`.

Пилотная база ПЗП мигрирует без ручной работы. Приведение `::date` берёт UTC-дату — для старых
записей погрешность в сутки допустима.

Отдельно: `CreateTask` перестаёт ставить `IssuedAt = DateTime.UtcNow` черновику — `IssuedAt`
проставляет только `ShiftTask.Issue()`.

## Домен (`ShiftTask`, ADR-0002)

- `SetPlannedStart(DateOnly date, TimeOnly? time, DateTime nowLocal)` — статус `Draft` или `Issued`
  (иначе `DomainException`); если значение изменилось: дата ≥ `DateOnly.FromDateTime(nowLocal)`,
  при дате = сегодня и заданном времени — время ≥ `nowLocal − 5 мин`. `nowLocal` — текущее время
  в поясе завода, вычисляет вызывающий (сущность не знает про смены). При создании задания
  вызывается из конструирующего кода с той же проверкой.
- `AssignPersonnel(string? personnelId)` — `Draft`: назначить/снять; `Issued`: только непустое;
  иначе `DomainException`. Валидность пользователя (существует, `IsActive`, `Role == Adjuster`)
  проверяет контроллер до вызова.
- `Issue()` — дополнительно `PersonnelId` не пустой, иначе `DomainException("Назначьте наладчика")`.
- Тексты ошибок со словом «черновик» → «Планируется».

## Политика `PlannedTaskStart` (`Core/Policies`)

```csharp
public static class PlannedTaskStart
{
    /// <summary>Плановое начало задания в UTC.</summary>
    public static DateTime Resolve(DateOnly date, TimeOnly? time,
                                   int? firstShiftStartMinutes, TimeZoneInfo factoryTz);
}
```

`firstShiftStartMinutes` — `MIN(Shift.StartMinutes)` или `null`, если смен нет. Локальное
`date + (time ?? firstShiftStart ?? 00:00)` переводится в UTC через `factoryTz`. Для
повторного использования контроллерами — сервис `IFactoryClock` (Infrastructure): читает самую
раннюю смену один раз на запрос и отдаёт `Now` (локальное), `TimeZone`, `FirstShiftStartMinutes`
и `ResolvePlannedStart(task)`. Существующий `FactoryCalendar` в `Reports` не трогаем.

## API

- `CreateTaskRequestDto`: `DateOnly? PlannedDate` (обязателен — `null` → 400),
  `TimeOnly? PlannedSetupStartTime`. JSON: `"2026-10-15"`, `"14:00:00"`.
- `UpdateTaskRequestDto`: `DateOnly? PlannedDate` (`null` — не менять),
  `TimeOnly? PlannedSetupStartTime`, `bool ClearPlannedSetupStartTime` (явная очистка времени —
  `null` в PUT означает «не менять»). Блок применяется, если передано хоть одно из трёх.
- `TaskDto`: `PlannedDate`, `PlannedSetupStartTime`, **`PlannedStartAt`** (UTC, вычислено).
- `PUT /api/tasks/{id}/personnel` — новый, `ManagerOrAdmin`, тело `{ personnelId }`, 204.
- `POST /api/tasks/{id}/issue` — необязательное тело `{ personnelId }`.
- `GET /api/tasks/my` — **контракт меняется**: параметр `boundary` удалён;
  `MyTasksDto { Active, Queue, Archive: PagedTasksDto }` вместо
  `{ CurrentShift, Unfinished, Archive }`. Очередь сортируется в памяти по `PlannedStartAt`
  (выданных заданий одного наладчика — единицы). Архив — `ORDER BY COALESCE(CompletedAt, ClosedAt) DESC`.
- `UnplannedRunController`: `taskDate = PlannedDate` (через `ToDateTime(TimeOnly.MinValue)`, Kind=Utc),
  без fallback на `IssuedAt`/`CreatedAt`.

## Фронтенд

**Менеджер (`TaskFormModal`, `TasksView`, `TaskDetailModal`):**
- Поля «Плановая дата» (`el-date-picker`, обязательно, прошлые даты недоступны) и «Время начала
  наладки» (`el-time-picker`, формат `HH:mm`, необязательно, подсказка «пусто — с начала смены»).
- «Наладчик» необязателен; в режиме правки сохраняется через `tasksApi.setPersonnel` (только при
  изменении), как заказ через `setTaskOrder`.
- Правка (`canEditTask`) — `Draft` и `Issued`. В `Issued` заблокированы ТПА, ПФ, заказ, план,
  режим, эталоны, примечание.
- «Выдать» в `TaskDetailModal` — диалог `IssueTaskDialog` с селектом наладчика (активные
  `Adjuster`), обязателен, предзаполнен `task.personnelId`.
- Колонка «Плановое начало» в `TasksView` (формат `DD.MM` или `DD.MM HH:mm`, сортировка по
  `plannedStartAt`); в деталях задания — строка «Плановое начало».
- `stores/tasks.js` `overdueTasks`: `['Draft','Issued']` и `now > plannedStartAt`.
- Сообщение после создания «Задание выдано» → «Задание создано».
- Подпись `Draft` → «Планируется»: `constants/taskStatus.js`, `TaskStatusBadge`, `MobileStatusBadge`,
  `TaskFilters`, карточка «Черновики» → «Планируются» в `TasksView`.

**Наладчик (`MobileTasksView`, `stores/mobile.js`, `api/mobile.js`):**
- Разделы `activeTasks` / `queueTasks` / `archiveTasks`; `computeShiftBoundary` и загрузка расписания
  смен для этого экрана убираются (если больше нигде не используются — удалить).
- В карточке очереди — плановое начало и метка: «опаздывает» (`now > plannedStartAt`), иначе
  «сегодня» (дата `plannedStartAt` в поясе браузера = сегодня).
- `setupTask` ищется в `activeTasks`.

Время показывается в поясе браузера (как везде в UI); вводимое время — по часам завода.
На пилоте пояса совпадают; расхождение — известное ограничение (см. «Вне объёма»).

## Вне объёма

- **Плановое окончание задания** — PZP-14 (норматив наладки + буфер выпуска).
- **Роль мастера участка** и экран «план работ на смену» (массовое назначение наладчиков на ТПА
  перед сменой) — в беклог.
- **Чистка `PUT /api/tasks`**: сейчас позволяет менять `Status`, `PlanQuantity` и эталоны в любом
  статусе. Новые гарды касаются только плановых полей; остальное — отдельная задача.
- **Пояс браузера ≠ пояс завода**: ввод времени по часам завода, отображение по браузеру. Пока
  совпадают — не решаем.
- `dateFrom/dateTo`-фильтр `GET /api/tasks` и прогресс смен в `TasksView` по-прежнему по `IssuedAt`.
