# PZP-22 — Справочники материалов: пластики и красители

- **Дата:** 2026-11-01
- **Задача:** PZP-22 (фидбек пилота ПЗП, блок В «Рецепты и справочники», первая задача блока)
- **Статус:** дизайн утверждён, ждёт ревью спеки
- **ADR:** не нужен — обычная справочная сущность по существующим паттернам. Общий ADR блока
  («изделие хранит технологические умолчания, задание — копию») заводится в BL-36/PZP-24.

## Проблема

ПЗП ведёт рецепты изделий: из какого пластика и с каким красителем отливается деталь. В системе
нет справочника материалов, поэтому рецепт (BL-36) не на что сослаться. Справочник нужен первым:
на него опираются рецепты, копии рецептов в заданиях, импорт номенклатуры (PZP-20) и прогноз
потребности в материалах.

## Акторы и сценарии (use cases)

| Актор | Сценарий |
|---|---|
| Менеджер / Админ | Заводит пластик: артикул, наименование, производитель (выбирает из ранее введённых или вводит новый), цвет — по желанию |
| Менеджер / Админ | Заводит краситель: то же, цвет обязателен; выбор цвета из подсказки заполняет наименование и код |
| Менеджер / Админ | Правит материал, отправляет в архив, возвращает из архива |
| Менеджер / Админ | Удаляет ошибочно заведённый материал, пока он нигде не использован |
| Менеджер / Админ | Ищет материал по артикулу, наименованию, производителю, цвету; фильтрует по активности |
| Наладчик / Наблюдатель | Только чтение через API: материал увидят в рецепте изделия и задания (BL-36), отдельного экрана нет |

## Решения

1. **Одна таблица `Materials`, тип — enum `MaterialType`** (`Plastic = 0`, `Colorant = 1`), хранится
   как int, как `MoldStatus`. В UI — два отдельных справочника.
   - Новый тип (добавки, регранулят) добавляется значением enum, без миграции схемы.
   - Отвергнуто: таблица типов. Тип несёт логику в коде (обязательность цвета; замена ингредиента в
     рецепте только материалом того же типа — BL-36), так что код всё равно знает каждый тип.
   - Отвергнуто: две таблицы. Рецепт ссылался бы на материал двумя разными FK.
2. **Тип задаётся при создании и не меняется.** Иначе краситель в рецепте изделия стал бы пластиком
   и нарушил правило замены по типу.
3. **Обязательные поля:** артикул и наименование; у красителя ещё наименование цвета. Производитель,
   код цвета, комментарий необязательны. Обязательный производитель отвергнут: импорт из Excel
   (PZP-20) может принести неполные строки.
4. **Нормализация:** артикул — Trim + верхний регистр (`ProductArticle.Normalize`); остальные
   строки — Trim, пустая строка → `null`.
5. **Уникальность внутри типа, без учёта регистра:**
   - `(Type, Article)` — обычный unique-индекс (артикул уже нормализован в верхний регистр);
   - `(Type, lower(coalesce(Manufacturer, '')), lower(Name))` — unique-индекс на выражении, сырым
     SQL в миграции. Пустой производитель считается одним значением.
   - Контроллер заранее проверяет коллизию и отдаёт 409 с понятным текстом; индекс страхует от
     гонки (`IsUniqueViolation`, как в `ProductTypesController`).
   - Отвергнуто: хранимые нормализованные колонки (`NameKey`…) — дублирующие поля, которые надо
     синхронизировать. Отвергнуто: недетерминированная ICU-коллация — в PostgreSQL 16 на таких
     колонках не работает `LIKE`/`ILIKE`, а поиск справочников строится на `ILike`.
   - Между типами совпадения допустимы: пластик и краситель могут иметь одинаковый артикул.
6. **Архив — `IsActive`** (мягкое удаление), как у остальных справочников. Архивный материал нельзя
   выбрать в новом рецепте (BL-36), существующие ссылки сохраняются.
7. **Физическое удаление — только если на материал нет ссылок.** В PZP-22 ссылающихся таблиц нет,
   поэтому проверка — точка расширения (`MaterialUsage`/метод в контроллере, сейчас всегда «не
   используется»). BL-36 допишет туда рецепты изделий и копии рецептов в заданиях (включая архивные).
   Это второе исключение из мягкого удаления (первое — изделие без заказов и заданий) — правка CLAUDE.md.
8. **Подсказки для свободного текста** — distinct-значения по **обоим** типам, включая архивные
   материалы: производитель один и тот же для пластиков и красителей, а архив хранит ранее введённые
   написания.
9. **Права:** чтение — Admin/Manager/Adjuster/Observer (как у типов изделий); запись и удаление —
   Admin/Manager. Экраны справочника — только Admin/Manager, как остальные справочники.

## Модель

`Wintime.Control.Core.Entities.Material : BaseEntity`

| Поле | Тип | Правило |
|---|---|---|
| `Type` | `MaterialType` | обязателен, не меняется после создания |
| `Article` | `string` (≤ 50) | обязателен, Trim + верхний регистр |
| `Name` | `string` (≤ 200) | обязателен, Trim |
| `Manufacturer` | `string?` (≤ 200) | Trim, пусто → `null` |
| `ColorName` | `string?` (≤ 100) | обязателен у `Colorant` |
| `ColorCode` | `string?` (≤ 50) | необязателен, Trim (регистр не трогаем: RAL 9005, #1A1A1A, Pantone…) |
| `Comment` | `string?` (≤ 1000) | необязателен |
| `IsActive` | `bool` | архивный флаг, по умолчанию `true` |

Правила нормализации и валидации — чистая политика `Core/Policies/MaterialRules`:
`Normalize(input) → нормализованные поля` и `Validate(type, fields) → ошибка | null`
(обязательность артикула, наименования, цвета у красителя; длины). Контроллер вызывает политику,
затем проверяет уникальность в БД.

Миграция `AddMaterials`: таблица, индекс `(Type, Article)` unique, индекс на выражении
`(Type, lower(coalesce("Manufacturer", '')), lower("Name"))` unique через `migrationBuilder.Sql`,
индекс `(Type, IsActive)` для списков.

## API — `MaterialsController` (`/api/materials`)

| Метод | Путь | Роли | Описание |
|---|---|---|---|
| GET | `/api/materials?type=&isActive=&search=` | Admin, Manager, Adjuster, Observer | Список. `search` — `ILike` по артикулу, наименованию, производителю, цвету. Сортировка по артикулу |
| GET | `/api/materials/{id}` | те же | Один материал |
| POST | `/api/materials` | Admin, Manager | Создание. 400 — валидация, 409 — коллизия уникальности |
| PUT | `/api/materials/{id}` | Admin, Manager | Правка полей и `isActive` (архив/возврат — тем же PUT, как в остальных справочниках). Поле `type` не принимается |
| DELETE | `/api/materials/{id}` | Admin, Manager | 204; 409 — материал используется (после BL-36) |
| GET | `/api/materials/suggestions/manufacturers?search=` | Admin, Manager | До 20 distinct-производителей по обоим типам, включая архивные; сортировка по алфавиту |
| GET | `/api/materials/suggestions/colors?search=` | Admin, Manager | До 20 distinct-пар `{ name, code }` по обоим типам, включая архивные |

`MaterialDto`: `id, type, article, name, manufacturer, colorName, colorCode, comment, isActive, isUsed`
(`isUsed` управляет кнопкой «Удалить»; в PZP-22 всегда `false`).

Тексты 409 — в духе ADR-0020: «Артикул X уже есть у пластика «Name»»,
«Краситель «Name» производителя «M» уже есть (артикул X)».

## UI

- **Меню «Справочники»:** после «Типы изделий» — «Пластики» (`/dictionary/plastics`) и «Красители»
  (`/dictionary/colorants`), роли Admin/Manager.
- **`views/dictionary/MaterialDictionary.vue`** — один компонент, тип берётся из `meta.materialType`
  маршрута. Раскладка как в `ProductTypeDictionary.vue`: заголовок с кнопкой «Добавить», фильтры
  (поиск, активность), таблица (Артикул · Наименование · Производитель · Цвет (наименование · код) ·
  Статус · Действия: «Редактировать», «В архив»/«Вернуть», «Удалить» при `!isUsed`).
- **Диалог материала:** Артикул (на лету в верхний регистр), Наименование, Производитель
  (подсказки), Цвет — наименование (подсказки) и код, Комментарий. У красителя наименование цвета
  помечено обязательным.
- **`components/common/SuggestInput.vue`** — общий компонент свободного текста с подсказками
  (обёртка над `el-autocomplete`): проп `fetch(search) → Promise<items>`, отображение элемента,
  событие `select(item)`; ввод значения не из списка разрешён. Для цвета `select` заполняет оба поля.
  Его же используют заказчик (PZP-23) и фильтр по заказчику (PZP-28).
- **`api/materials.js`** — по образцу `productTypes.js`.

## Тесты

- **xUnit unit — `MaterialRules`:** нормализация (Trim, верхний регистр артикула, пусто → `null`,
  регистр кода цвета сохраняется); обязательность артикула и наименования; цвет обязателен у
  красителя и необязателен у пластика; длины.
- **xUnit integration — `MaterialsController`:** создание и чтение; коллизия артикула в другом
  регистре и с пробелами → 409; коллизия (производитель, наименование) без учёта регистра → 409, в
  том числе при пустом производителе у обоих; одинаковый артикул у пластика и красителя допустим;
  PUT не меняет тип; архив/возврат через PUT; DELETE неиспользуемого → 204; подсказки — distinct по
  обоим типам, включая архивные, лимит 20; права (Adjuster не может писать).
- **Vitest:** `SuggestInput` (вызывает fetch, свободный ввод, select); `MaterialDictionary`
  (артикул в верхнем регистре, обязательность цвета зависит от типа, выбор цвета из подсказки
  заполняет оба поля, кнопка «Удалить» только при `!isUsed`).

## Вне задачи

- Рецепты и ссылки на материалы — BL-36.
- Импорт материалов из Excel — PZP-20.
- Складские остатки — не ведём (не WMS).
- Единицы измерения материала — не нужны: рецепт задаётся процентом от веса изделия (BL-36).
