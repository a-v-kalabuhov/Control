# BL-23 — Дашборд сырой телеметрии и циклов одного ТПА

> Дата: 2026-07-27 · Статус: дизайн согласован, ждёт ревью перед планом реализации

## 1. Контекст и проблема

Сырая телеметрия ТПА уже персистится (таблица `Telemetry`, COV-фильтрация, типизация датчиков
из шаблона ТПА), но её **негде посмотреть человеку**. Нет экрана, который показал бы, как вели себя
сигналы станка (температуры, давления, подушка, сухие контакты) и как ложились производственные циклы
на реальном отрезке времени. Это нужно для диагностики техпроцесса и разбора инцидентов — «что
происходило со станком в эти 40 минут».

Хранилище готово, поэтому задача — **read-only визуализация**: собрать окно данных и нарисовать его.
Новый слой хранения не требуется.

## 2. Рамки

**В рамках (v1):**
- Автономный экран одного ТПА, drill-in из карточки/детального окна ТПА.
- Два режима: **История** (произвольный диапазон, максимум 4 часа) и **Живые данные** (скользящее
  окно, polling).
- По-сигнальные ступенчатые тренды (один сигнал — одна диаграмма, столбиком), синхронизированные
  по оси времени.
- Фоновая заливка эффективного статуса ТПА и вертикальные отметки границ циклов.
- Доступ — роли **Manager и Admin** (десктопный аналитический экран). Наладчик (Adjuster) работает
  только в мобильном UI и сюда не заходит — мобильный интерфейс сырой телеметрией не перегружаем.

**Вне рамок (осознанно отложено):**
- Общая навигационная модель модуля аналитики (BL-12 / BL-16 / BL-24) — только точка входа, без
  проектирования единого модуля.
- Downsampling / LTTB / политика ретеншена и агрегации старых данных.
- Push-доставка через SignalR (вместе с BL-11); в v1 — polling.
- Консолидация с ROS-09 «Анализ качества» (учитываем как надмножество, реализуем в рамках РОСОМС
  отдельно; ROS-09 = отчётная проекция этого дашборда + ФИО наладчика/оператора в периоде).

## 3. Акторы и сценарии (use cases)

**Акторы:** Начальник цеха (Manager), Администратор (Admin). Доступ к экрану — `ManagerOrAdmin`.
Наладчик (Adjuster) исключён: он работает только в мобильном UI, а это десктопный аналитический
экран — перегружать мобильный интерфейс сырой телеметрией не хотим.

- **UC-1. Открыть телеметрию конкретного ТПА.** Пользователь на дашборде/в карточке ТПА нажимает
  «Телеметрия» → открывается экран уже в контексте этого ТПА (`/imm/:id/telemetry`), по умолчанию —
  режим «Живые данные», период наблюдения 15 минут, отмечен первый доступный сигнал.
- **UC-2. Смотреть живые данные.** Пользователь выбирает режим «Живые», задаёт период наблюдения
  (1/5/15/30 мин, 1/2/4 ч). Диаграммы показывают скользящее окно `[now − период, now]` и
  автообновляются по таймеру; новые точки дописываются справа, ушедшие за левую границу — отбрасываются.
- **UC-3. Смотреть историю за период.** Пользователь выбирает режим «История», задаёт начало и конец
  (дата + время до секунд, диапазон ≤ 4 часов), получает статичный срез окна.
- **UC-4. Выбрать сигналы.** Пользователь отмечает галками сигналы для отображения (из набора шаблона
  ТПА). Всегда должен быть отмечен ≥1 сигнал. Каждый отмеченный сигнал = отдельная диаграмма.
- **UC-5. Сопоставить значения по времени.** Пользователь ведёт курсор над любой диаграммой → по всем
  диаграммам столбца проходит синхронный вертикальный «прицел» (crosshair), tooltip показывает значение
  каждого сигнала в момент времени под курсором.
- **UC-6. Переупорядочить диаграммы.** Пользователь перетаскивает диаграмму вверх/вниз в столбце,
  чтобы поставить рядом интересующие сигналы.
- **UC-7. Увидеть контекст статуса и циклов.** На всех диаграммах пользователь видит фоновую заливку
  эффективного статуса (включая зоны Offline) и вертикальные линии начала/конца циклов (тон зависит
  от годности цикла) — чтобы связать поведение сигналов с работой станка.
- **UC-8. Понять, что данные обрезаны.** Если за окно набралось аномально много точек (дребезг датчика),
  пользователь видит предупреждение «показано не всё, сузьте период», а не молчаливо неполный график.

## 4. Архитектура и поток данных

```
Telemetry (COV, готово) ──────────────┐
ImmCycle (готово) ─────────────────────┼─► GET /api/imm/{id}/telemetry-dashboard
ImmStatusHistory + ShiftTask + Event ──┘        │ (EffectiveStatusTimeline.Build, готов)
   └── приватный хелпер сбора рядов ─────────────┘
                                                 ▼
                                { signals[], cycles[], statusSegments[], truncated }
                                                 ▼
                       Vue: TelemetryDashboardView → столбик SignalChart (echarts)
```

Единый агрегирующий read-эндпоинт собирает окно `[from, to]` из трёх источников. Логику сбора статус-рядов
(`raw` / `tasks` / `downtimes`), сейчас встроенную в `GET .../effective-status-history`
([`ImmController.cs`](../../Wintime.Control.API/Controllers/ImmController.cs) строки ~413–451),
выносим в приватный хелпер контроллера и переиспользуем в новом эндпоинте — без дублирования. Сборка
окна серверная и покрывается интеграционными тестами.

Эффективное состояние по-прежнему **не хранится** — считается на лету чистой функцией
`EffectiveStatusTimeline.Build` (`Core/Policies`). Отрезки сигналов строятся **только** по строкам
`Telemetry`; статус — наложение поверх, а не источник обрезки отрезков (см. §7).

## 5. API-контракт

### Новый эндпоинт

```
GET /api/imm/{id:guid}/telemetry-dashboard?from={iso}&to={iso}&parameters={a}&parameters={b}...
[Authorize(Policy = "ManagerOrAdmin")]
```

**Guard-проверки (в начале метода, до обращения к БД):**
- ТПА не найден → `404`.
- `parameters` пуст → `400` («выберите хотя бы один сигнал») — инвариант «≥1 сигнал».
- Ширина окна `to − from > 4 ч` → `400` («период не может превышать 4 часа»).
- UTC: `from`/`to` сразу через `DateTime.SpecifyKind(..., DateTimeKind.Utc)` (инвариант CLAUDE.md,
  колонки `timestamptz`). Клампинг `to` по `now` — как в существующем эндпоинте.

**Guard по объёму (после выборки, дёшево):** телеметрию читаем `Take(maxPoints + 1)`; если вернулось
`> maxPoints` строк — усечь до `maxPoints` и выставить `truncated = true`. `maxPoints` — параметр
`appsettings` (`TelemetryDashboard:MaxPoints`, дефолт подберём на данных пилота, ориентир ~50 000).

**Ответ `TelemetryDashboardDto`:**
```jsonc
{
  "signals": [
    {
      "parameterName": "MeltTemp",
      "type": "float",                 // из Template.Sensors: float|int|cycleCounter|boolean|string
      "points": [
        { "t": "2026-07-27T08:00:03Z", "num": 218.4 },   // ValueNumeric → num
        { "t": "2026-07-27T08:01:10Z", "txt": "true" }    // ValueText   → txt (boolean/string)
      ]
    }
  ],
  "cycles":  [ { "start": "…Z", "end": "…Z", "isSuccessful": true } ],
  "statusSegments": [ { "effectiveStatus": "Production", "start": "…Z", "end": "…Z" } ],
  "truncated": false
}
```
- Точки каждого сигнала упорядочены по времени. Отрезок сигнала (фронт) = `[t_i, t_{i+1})`, ступень.
- `type` берётся из `Template.Sensors[parameterName].ParameterType`; фронт по нему решает
  «числовая ось» vs «дорожка состояний».
- `cycles` — границы циклов из `ImmCycle`, пересекающиеся с окном (`StartTime < to && EndTime > from`).
- `statusSegments` — результат `EffectiveStatusTimeline.Build`, формат как у `EffectiveStatusSegmentDto`.

### Удаляемый эндпоинт

`GET /api/imm/{id}/telemetry` ([`ImmController.cs:334`](../../Wintime.Control.API/Controllers/ImmController.cs))
**удаляется** вместе с `TelemetryDto` и двумя мёртвыми фронт-обёртками
(`dashboard.js:getImmTelemetry`, `imm.js:getTelemetry`). Обоснование: единственных потребителей нет
(обёртки нигде не вызываются), плюс у эндпоинта баг UTC-Kind (`from`/`to` уходят в `.Where()` без
`SpecifyKind`). Новый агрегирующий эндпоинт его полностью замещает.

## 6. Фронт — компоненты и режимы

- **`TelemetryDashboardView.vue`** — страница: панель фильтров + столбик диаграмм. Route
  `/imm/:id/telemetry`, вход из карточки ТПА.
- **Панель фильтров (сверху):**
  - Режим: `История` / `Живые данные` (выпадающий список).
  - Сигналы: чекбоксы из набора шаблона ТПА; ≥1 всегда отмечен (снять последний нельзя).
  - Режим «История»: начало и конец периода — дата + время до секунд; клиентская валидация ≤ 4 ч.
  - Режим «Живые»: период наблюдения — выпадающий список `1 мин / 5 мин / 15 мин / 30 мин / 1 ч / 2 ч / 4 ч`.
- **`SignalChart.vue`** — одна диаграмма = один сигнал (echarts). Диаграммы в вертикальном столбце,
  синхронизированы по X (общий crosshair и зум) через `axisPointer.link` + `echarts.connect` группы.
- **Перетаскивание диаграмм** вверх/вниз — reorder списка в состоянии (порядок сигналов), без
  переинициализации echarts-инстансов.
- **Живой режим (polling):** окно `[now − период, now]`, тик по таймеру. Частота обновления —
  **выпадающий список на экране** (2/5/10 c, дефолт 5 c); отдельный от выбора периода наблюдения.
  Существующую настройку `telemetryIntervalSeconds` не переиспользуем — она нерабочая (не
  персистится и нигде не потребляется, см. бэклог). **Дельта-подгрузка:** очередной запрос с
  `from = максимальный t уже полученных точек`; новые точки дописываются, вышедшие за левую границу
  окна — отбрасываются (скользящее окно). Легче, чем перезабирать всё окно каждый тик.
- **Палитра/подписи статусов** — существующая
  [`src/constants/effectiveStatus.js`](../../Wintime-Control-Frontend/src/constants/effectiveStatus.js).

## 7. Отрисовка на диаграмме

- **Сигнал — ступенчатая линия (step-after):** отрезок от `t_i` до `t_{i+1}`; последний отрезок —
  до правой границы окна (в live — до `now`). Это корректно при COV-хранении: значение «держится»
  до следующего сэмпла.
- **Отрезки строятся строго по строкам `Telemetry`** и **не** обрываются искусственно в Offline-зоне.
  Если отрезок сигнала попадает в зону эффективного статуса Offline — это видимый сигнал о возможной
  ошибке детекции Offline, а не замаскированный дефект. Правило «в Offline нет отрезков» не зашиваем.
- **Числовые сигналы** (float/int/cycleCounter): авто-шкала Y с округлением границ (echarts
  `yAxis.scale: true`) + тумблер «шкала с нуля» на диаграмме. Причина авто-шкалы: абсолютный ноль
  скрыл бы мелкую динамику (температура 180–240 °C схлопнулась бы в узкую полосу).
- **Boolean / string сигналы:** дорожки состояний (0/1 или дискретные полосы), без числовой оси.
- **Циклы:** вертикальные линии начала и конца (`markLine`), общие для всех диаграмм столбца; тон
  зависит от `isSuccessful` (годный / брак).
- **Эффективный статус:** фоновая заливка (`markArea`) по `statusSegments`, включая Offline-зоны.
- **Crosshair:** синхронный вертикальный «прицел» по всем диаграммам (`axisPointer.link` по общей оси
  X); tooltip показывает значение каждого сигнала в точке под курсором (UC-5).

## 8. Гарды, индекс, масштаб

- Читаем сырые (COV-прорежённые) точки; downsampling/ретеншен отложены (YAGNI для пилота).
- **Новый составной индекс** `IX_Telemetry_Imm_Param_Time (ImmId, ParameterName, Timestamp)` — под
  фильтр «окно + выбранные сигналы одного ТПА». Миграция аддитивна (только индекс).
- Guard по ширине окна (4 ч) и guard по числу точек (`truncated`) — см. §5.

## 9. Тестирование

- **xUnit (интеграция) на новый эндпоинт:**
  - окно с телеметрией + циклами + статусом → корректная сборка `signals/cycles/statusSegments`;
  - `parameters` пуст → `400`; окно > 4 ч → `400`; несуществующий ТПА → `404`;
  - клампинг `to` по `now`;
  - guard объёма: при `> maxPoints` строк — `truncated = true` и усечение;
  - роли Manager и Admin проходят; Adjuster (и ниже) → `403`; аноним → `401`.
- **Vitest (фронт):**
  - сборка step-серии из точек (в т.ч. хвостовой отрезок до границы окна / до `now`);
  - маппинг `type` → (числовая ось / дорожка состояний);
  - дельта-подгрузка в live (append новых + сброс левого края скользящего окна);
  - валидатор «нельзя снять последний сигнал».
- `EffectiveStatusTimeline.Build` уже покрыт юнитами — не дублируем.

## 10. Решение по ADR

**ADR не заводим.** Изменение аддитивно: новый read-эндпоинт, схему БД не меняем (только индекс),
доменных инвариантов не вводим, чистую функцию статуса переиспользуем. Удаление неиспользуемого
`GET .../telemetry` зафиксировано здесь как явное решение (§5).

## 11. Открытые вопросы / отложено

- **Downsampling/LTTB и ретеншен** — когда упрёмся в объём данных на реальном парке.
- **SignalR** вместо polling — вместе с BL-11.
- **Консолидация с ROS-09** — этот дашборд как надмножество; отчётную проекцию (+ФИО персонала)
  делаем в рамках РОСОМС отдельно.
- **Точное значение `MaxPoints`** и интервала live-поллинга — подобрать на данных пилота.
