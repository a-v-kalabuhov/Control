# PZP-38: Администрирование телеметрии — статистика и очистка

**Дата:** 2026-11-27
**Статус:** дизайн согласован в brainstorming; спецификация ожидает ревью пользователя
**Приоритет:** блок перед следующим обновлением пилота ПЗП

## Контекст

Таблица `Telemetry` непрерывно пополняется и может становиться очень большой. Администратору нужны
фактические сведения о её размере и количестве записей, а также управляемый способ удалить старую
телеметрию до выбранной даты.

Функция размещается в существующем меню **«Администрирование»** и доступна только роли `Admin`.
Все счётчики должны быть точными. Удаление выполняется синхронно, после предварительного подсчёта
и явного подтверждения.

## Цели

- Показывать общее количество записей `Telemetry`.
- Показывать размер данных таблицы отдельно от суммарного размера её индексов.
- Показывать точную статистику за текущий календарный месяц, последние четыре календарные недели
  и три предыдущих полных календарных месяца.
- Обновлять все показатели по требованию администратора.
- Перед очисткой показывать точное количество записей, подлежащих удалению.
- Удалять только записи с `Timestamp` строго раньше начала выбранной локальной даты.
- Синхронно дожидаться результата удаления и затем обновлять панель.
- Обеспечивать доступ только администратору и в frontend, и в backend.

## Не входит в PZP-38

- Изменение состава индексов `Telemetry` — это PZP-39; задачи выпускаются вместе.
- `VACUUM`, `VACUUM FULL`, `REINDEX` и другие автоматические операции обслуживания БД.
- Фоновые задания, отображение прогресса удаления и очередь операций.
- Постоянная история очисток или отдельная таблица аудита.
- Автоматическое обновление панели по таймеру.
- Приблизительные счётчики и кеширование статистики.
- Изменение `ImmCycles`, `ImmStatusHistory` и других таблиц при очистке `Telemetry`.
- Новые сущности, таблицы, EF-миграции и ADR.

## Принятые решения

- «Последний месяц» означает **текущий календарный месяц**, даже неполный.
- Недельная статистика — **последние четыре календарные недели, включая текущую**, независимо от границ месяцев.
- Календарная неделя начинается в понедельник и заканчивается в воскресенье.
- Дополнительно показываются **три полных календарных месяца перед текущим**.
- Все счётчики вычисляются точно при каждой загрузке и обновлении.
- Для статистики используется один агрегатный SQL-запрос с условными агрегатами, а не серия сканирований.
- Удаление синхронное, без фоновой инфраструктуры.
- Будущие даты очистки запрещены; максимально допустимая дата — сегодня в часовом поясе браузера.
- Периоды и граница очистки вычисляются в часовом поясе браузера, сравнения в БД выполняются в UTC.
- Предпросмотр и удаление используют одну и ту же серверную функцию вычисления `cutoffUtc`.

## Акторы и сценарии (use cases)

### Акторы

| Актор | Возможности |
|---|---|
| Администратор (`Admin`) | Открыть страницу, загрузить и обновить статистику, рассчитать и подтвердить очистку |
| Любая другая роль | Не видит пункт меню, перенаправляется при прямом переходе, получает `403` от API |

### UC-1. Открыть или обновить панель телеметрии

**Основной поток**

1. Администратор открывает **«Администрирование → Телеметрия»** или нажимает **«Обновить»**.
2. Frontend передаёт IANA-часовой пояс браузера в API статистики.
3. Сервер одним агрегатным запросом вычисляет общий и периодические счётчики, отдельно получает размеры.
4. Страница показывает общее количество, размеры, текущий месяц, четыре недели и три предыдущих месяца.

**Альтернативы и ошибки**

- Во время запроса отображается `loading`; повторный запуск заблокирован.
- При ошибке начальной загрузки панель остаётся пустой и показывает сообщение об ошибке.
- При ошибке обновления последние успешно полученные значения сохраняются на экране.
- Неизвестный часовой пояс → `400`.
- Недостаточно прав → `403`.

**Endpoint:** `GET /api/admin/telemetry/statistics`
**Тесты:** `TelemetryAdministrationApiTests.GetStatistics_*`, `TelemetryAdminView.spec.js`.

### UC-2. Рассчитать очистку до даты

**Основной поток**

1. Администратор нажимает **«Очистить»** и выбирает дату не позднее сегодняшней.
2. Frontend передаёт локальную дату и часовой пояс браузера.
3. Сервер вычисляет `cutoffUtc` как начало этой локальной даты.
4. Сервер выполняет точный `COUNT` по условию `Timestamp < cutoffUtc`.
5. Появляется диалог с датой и текстом **«XXX записей будет удалено. Подтвердите удаление»**.
6. Предпросмотр не изменяет БД.

**Альтернативы и ошибки**

- При нулевом количестве диалог показывает `0`, кнопка подтверждения неактивна.
- При ошибке подсчёта диалог не открывается, дата остаётся выбранной.
- Будущая или некорректная дата, неизвестный часовой пояс → `400`.
- Недостаточно прав → `403`.

**Endpoint:** `GET /api/admin/telemetry/cleanup/preview`
**Тесты:** `CleanupPreview_ReturnsExactCountAndDoesNotDelete`, frontend-сценарии предпросмотра и нулевого количества.

### UC-3. Подтвердить синхронную очистку

**Основной поток**

1. Администратор подтверждает диалог.
2. Frontend повторно передаёт дату и часовой пояс; клиентский `cutoffUtc` не используется как источник истины.
3. Сервер повторно вычисляет ту же границу и выполняет один атомарный `DELETE`.
4. До ответа блокируются повторное удаление, смена даты, предпросмотр и обновление панели.
5. API возвращает фактический `deletedCount`.
6. Frontend показывает результат, закрывает форму очистки и заново загружает статистику.

**Альтернативы и ошибки**

- Если между предпросмотром и удалением появились опоздавшие записи с прошлым `Timestamp`,
  `deletedCount` может отличаться от предпросмотра; пользователю показывается фактический результат.
- Ошибка БД → `500`; таймаут → `504`. Один SQL-оператор не оставляет частично удалённого результата.
- После ошибки форма остаётся открытой, дата сохраняется, элементы управления разблокируются.
- Повторный запуск с той же границей безопасен и удаляет только оставшиеся подходящие записи.
- Если удаление успешно, но последующее обновление статистики завершилось ошибкой, успех удаления
  не заменяется сообщением об ошибке очистки; отдельно показывается ошибка обновления статистики.

**Endpoint:** `DELETE /api/admin/telemetry/cleanup`
**Тесты:** `Cleanup_DeletesOnlyRowsBeforeCutoff`, `Cleanup_ReturnsActualDeletedCount`, frontend-сценарии ожидания,
успеха, ошибки и повторной загрузки.

### UC-4. Попытка доступа без роли Admin

**Основной поток**

1. Пункт меню скрыт по роли.
2. Маршрут имеет `meta.roles: ['Admin']`; прямой переход перенаправляет на домашнюю страницу роли.
3. Каждый API-endpoint защищён политикой `AdminOnly` и возвращает `403` без выполнения операции.

**Endpoint:** все endpoints `/api/admin/telemetry`
**Тесты:** `TelemetryAdministrationApiTests.Endpoints_NonAdmin_ReturnForbidden`, тесты меню и маршрута.

## Пользовательский интерфейс

### Размещение

- Маршрут: `/admin/telemetry`.
- Заголовок страницы: **«Телеметрия»**.
- Меню: **«Администрирование → Телеметрия»**, рядом с существующим пунктом «Шаблоны».

### Панель

На странице одна панель с действиями **«Обновить»** и **«Очистить»**.

Показатели:

1. Общее количество записей.
2. Объём данных таблицы без индексов.
3. Суммарный объём индексов.
4. Текущий календарный месяц — один счётчик.
5. Последние четыре календарные недели — от старой к текущей.
6. Три предыдущих полных календарных месяца — от старого к новому.

Недели отображаются диапазонами локальных дат, месяцы — названием месяца и годом. Текущие неполные
неделя и месяц имеют понятную метку «текущая»/«текущий».

Размеры передаются в байтах и форматируются на frontend в подходящие единицы КБ/МБ/ГБ/ТБ.
Рядом размещается подсказка: после очистки физический размер таблицы и индексов может уменьшиться
не сразу из-за особенностей PostgreSQL.

### Форма очистки

- Поле даты с максимально допустимым значением «сегодня».
- Предпросмотр выполняется до появления подтверждения.
- Диалог содержит выбранную дату, точное количество и согласованный текст подтверждения.
- Отмена диалога не вызывает удаление.
- При нулевом количестве подтверждение недоступно.

## API-контракты

### Общие параметры

- `timeZone` — обязательный IANA-идентификатор, например `Europe/Moscow`.
- `date` — локальная календарная дата `YYYY-MM-DD`, обязательна для preview и cleanup.
- Все ответы используют существующие web JSON-конвенции с camelCase.

### `GET /api/admin/telemetry/statistics?timeZone={timeZone}`

Возвращает `200` со следующими полями:

| Поле | Тип | Содержание |
|---|---|---|
| `totalCount` | `long` | Точное количество всех записей таблицы |
| `tableSizeBytes` | `long` | `pg_table_size`, без индексов |
| `indexesSizeBytes` | `long` | `pg_indexes_size` |
| `currentMonth` | `PeriodCountDto` | Текущий месяц до серверного `nowUtc` |
| `recentWeeks` | `PeriodCountDto[4]` | Три предыдущие и текущая календарные недели |
| `previousMonths` | `PeriodCountDto[3]` | Три полных месяца перед текущим |

`PeriodCountDto`:

| Поле | Тип | Содержание |
|---|---|---|
| `startDate` | `DateOnly` | Локальное начало отображаемого периода |
| `endDate` | `DateOnly` | Локальный календарный конец периода, включительно |
| `count` | `long` | Точный счётчик внутри фактического UTC-окна |
| `isCurrent` | `boolean` | Признак текущего неполного периода |

Для текущего месяца `endDate` — последний календарный день месяца, хотя фактический подсчёт заканчивается
в `nowUtc`. Для текущей недели `endDate` — воскресенье, хотя подсчёт также заканчивается в `nowUtc`.

### `GET /api/admin/telemetry/cleanup/preview?date={date}&timeZone={timeZone}`

Возвращает `200`:

| Поле | Тип | Содержание |
|---|---|---|
| `date` | `DateOnly` | Запрошенная локальная дата |
| `cutoffUtc` | `DateTime` | Начало даты в UTC, `Kind=Utc` |
| `count` | `long` | Точное количество записей с `Timestamp < cutoffUtc` |

Операция не изменяет БД.

### `DELETE /api/admin/telemetry/cleanup?date={date}&timeZone={timeZone}`

Возвращает `200`:

| Поле | Тип | Содержание |
|---|---|---|
| `cutoffUtc` | `DateTime` | Повторно вычисленная сервером граница |
| `deletedCount` | `long` | Фактическое количество удалённых строк |

Ошибки валидации → `400`, отсутствие прав → `403`, ошибка БД → `500`, таймаут удаления → `504`.

## Периоды и часовые пояса

`TelemetryPeriodCalculator` один раз получает зафиксированное серверное `nowUtc` и IANA-часовой пояс.
Все периоды одного ответа используют один момент `nowUtc`.

- Текущий месяц: локальное первое число `00:00` → `min(nowUtc, следующий месяц)`.
- Текущая неделя: локальный понедельник `00:00` → `min(nowUtc, следующий понедельник)`.
- Предыдущие три недели: полные локальные интервалы понедельник–воскресенье.
- Предыдущие три месяца: полные локальные календарные месяцы.

Все запросы используют полуоткрытые интервалы:

```text
Timestamp >= startUtc AND Timestamp < endUtc
```

Для текущих периодов верхняя граница — `nowUtc`, поэтому записи с будущим `Timestamp` не включаются.
Такие записи остаются частью общего количества таблицы.

Для очистки:

```text
cutoffUtc = начало локальной date в timeZone, переведённое в UTC
Timestamp < cutoffUtc
```

Запись ровно в `cutoffUtc` остаётся. Сервер вычисляет «сегодня» в переданном часовом поясе и отклоняет
`date > today`. Все `DateTime`, передаваемые в PostgreSQL, имеют `Kind=Utc`.

## Запросы к PostgreSQL

### Статистика

Один параметризованный агрегатный SQL-запрос получает девять значений за одно сканирование:

- общий `COUNT(*)`;
- текущий месяц;
- четыре недели;
- три предыдущих месяца.

Периодические значения вычисляются условными агрегатами. Перекрытие периодов допустимо: одна запись
может входить одновременно в общий итог, текущий месяц и текущую неделю.

Размеры получаются отдельным коротким запросом:

- `pg_table_size('"Telemetry"')` — основные, TOAST и служебные данные таблицы без индексов;
- `pg_indexes_size('"Telemetry"')` — все индексы таблицы.

### Предпросмотр

Отдельный точный `COUNT` с параметром `cutoffUtc`. Никаких изменений и блокирующей транзакции между
preview и cleanup нет.

### Удаление

Один `ExecuteDeleteAsync` с условием `Timestamp < cutoffUtc` возвращает фактическое количество строк.
Для команды устанавливается таймаут **30 минут** только на время scoped-операции; исходное значение
таймаута контекста восстанавливается в `finally`.

Явная долгоживущая транзакция не нужна: единственный SQL-оператор атомарен. После удаления не вызываются
`VACUUM` и `REINDEX`.

## Обработка ошибок и логирование

- Некорректные входные параметры → `400` с понятным сообщением.
- Все роли кроме Admin → `403`.
- Ошибка статистики не затирает последние успешные значения на frontend.
- Ошибка preview не открывает подтверждение.
- Ошибка cleanup сохраняет дату и позволяет повторить операцию.
- Таймаут cleanup отображается отдельно от обычной ошибки запроса.

В серверный лог пишутся идентификатор администратора, `cutoffUtc`, начало и результат операции,
`deletedCount`, длительность, ошибка или таймаут. Постоянная таблица истории не создаётся.

## Тестирование

### Unit: `TelemetryPeriodCalculatorTests`

- Текущий месяц заканчивается в `nowUtc`, а не в будущем.
- Текущая неделя начинается в понедельник и заканчивается в `nowUtc`.
- Четыре недели пересекают границы месяцев и года.
- Три предыдущих месяца пересекают границу года.
- Високосный февраль.
- Локальная полночь переводится в UTC.
- Переход на летнее/зимнее время в тестовом IANA-поясе.
- Сегодняшняя дата разрешена, будущая отклоняется.
- Preview и cleanup получают одинаковый `cutoffUtc` для одинаковых входных данных.

### Integration: `TelemetryAdministrationApiTests`

- Admin получает статистику; Manager и другие роли получают `403` на всех endpoints.
- Общий и периодические счётчики соответствуют контрольным записям.
- Граничные записи попадают только в правильные интервалы.
- Будущие записи не попадают в текущие неполные периоды.
- Размеры таблицы и индексов неотрицательны.
- Preview возвращает точный `count` и не удаляет строки.
- Cleanup использует строгое `<`: запись ровно на границе остаётся.
- Cleanup возвращает фактический `deletedCount`.
- Нулевой preview и повторный cleanup обрабатываются корректно.
- Неверная дата, будущая дата и неизвестный часовой пояс возвращают `400`.
- Очистка не изменяет `ImmCycles`, `ImmStatusHistory` и другие таблицы.

Тестовые данные изолируются собственным ТПА и очищаются после теста. При невозможности полагаться на
глобальный итог из-за других данных проверяется приращение относительно baseline, а не предполагается
пустая общая БД.

### Frontend: Vitest

- Автоматическая загрузка и кнопка «Обновить».
- Один текущий месяц, четыре недели и три предыдущих месяца.
- Форматирование байтов.
- Запрет будущих дат.
- Preview без вызова удаления.
- Текст подтверждения с количеством.
- Неактивное подтверждение при нулевом количестве.
- Блокировка управления во время удаления.
- Показ фактического `deletedCount` и повторная загрузка статистики.
- Сохранение последних значений и состояния формы при ошибках.
- Меню и маршрут доступны только Admin.

### Ручная проверка

На реальной PostgreSQL:

1. Открыть панель и проверить все группы показателей.
2. Нажать «Обновить».
3. Выбрать дату, получить preview и отменить диалог; убедиться, что записи остались.
4. Повторить preview и подтвердить удаление.
5. Проверить фактический результат, сохранение записи на границе и обновление панели.
6. Убедиться, что Manager не может открыть страницу или вызвать API.

## Критерии готовности

- Все согласованные показатели отображаются и обновляются.
- Все счётчики точные; статистика считается одним агрегатным запросом.
- Preview ничего не удаляет и показывает точное количество.
- Cleanup выполняется синхронно и строго по `Timestamp < cutoffUtc`.
- Доступ к UI и API есть только у Admin.
- Backend unit/integration-тесты и frontend Vitest проходят.
- Ручной сценарий на PostgreSQL выполнен.
- PZP-39 поставляется в том же обновлении, но не реализуется этой спецификацией.

## Оценка

**1–2 дня** вместе с backend и frontend-тестами. Новых сущностей и миграций нет; основные сложности —
точный агрегатный запрос, локальные календарные границы и длительное синхронное удаление.
