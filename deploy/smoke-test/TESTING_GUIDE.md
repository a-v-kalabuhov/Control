# Smoke-тест: Control + коннектор UsrModbus + эмулятор Borche

Инструкция для тестировщика, у которого нет доступа к исходникам и реальному ТПА — только готовые
Docker-образы. Цель: проверить, что цепочка **эмулятор (виртуальный ТПА) → коннектор UsrModbus →
MQTT → Control** работает целиком — дашборд, задания, циклы, статусы.

Что тестируем: Control уже перешёл на MQTT-контракт v2 (циклы литья детектирует коннектор, не
Control — см. `CLAUDE.md` в репозитории Control, раздел «Цикл литья»). Коннектор `UsrModbus`
переписан под этот контракт. Эмулятор Borche — новый инструмент: раньше для теста коннектора нужен
был живой станок и шлюз USR-IO424, теперь его роль играет контейнер `emulator`.

Схема стенда:

```
┌─────────────┐   Modbus TCP   ┌───────────┐   MQTT   ┌──────────┐   HTTP   ┌────────┐
│  emulator    │◄──────────────│ connector │─────────►│ mosquitto│◄─────────│  api   │
│ (виртуальный │  (эмулятор =  │(UsrModbus)│          │          │          │(Control)│
│     ТПА)     │   slave,      │  = master)│          └──────────┘          └────────┘
└─────────────┘   коннектор    └───────────┘                                    ▲
                    подключается                                    браузер ────┘
                    как к реальному шлюзу)                       http://localhost:5000
```

## 0. Подготовка ПК (Windows)

Нужен только Docker — исходники, .NET SDK и Node.js не нужны, всё уже собрано в образы.

1. **Windows 10/11** (64-бит), минимум 4 ГБ свободной ОЗУ, ~10 ГБ на диске под образы и БД.
2. **Включить виртуализацию** в BIOS/UEFI, если выключена (нужна для WSL2).
3. Установить **WSL2**: PowerShell от администратора →
   ```powershell
   wsl --install
   ```
   После установки — перезагрузка, если попросит.
4. Установить **Docker Desktop for Windows**: https://www.docker.com/products/docker-desktop/
   При установке — оставить вариант **WSL2 backend** (по умолчанию).
5. Запустить Docker Desktop, дождаться статуса «Engine running» (значок кита в трее зелёный).
6. Проверить в PowerShell:
   ```powershell
   docker --version
   docker compose version
   ```
   Обе команды должны отработать без ошибок.
7. Убедиться, что порт **5000** на ПК свободен (не занят IIS/Skype/другим Docker-стеком) — на нём
   будет висеть дашборд Control.

На этом подготовка ПК закончена — дальше только работа с папкой пакета.

## 1. Разворачивание тестовой среды

Пакет — папка `package/` (получаешь архивом), внутри:

```
package/
├── docker-compose.test.yml   # описание всех контейнеров
├── .env.example               # шаблон паролей → скопировать в .env
├── mosquitto.conf
├── images/                    # *.tar — образы (docker load)
├── config-emulator/           # конфиг виртуального ТПА (эмулятор)
│   ├── machine-01.json
│   ├── emulator-ui.yaml
│   └── presets/               # сценарии (*.preset) и macros/*.mac, §2.3
├── config-connector/          # конфиг коннектора (список ТПА + параметры опроса)
│   ├── machines.json
│   └── machine-01.json
├── template-borche-emu.json   # шаблон ТПА для импорта в Control (Справочники → Шаблоны)
├── 1-load-images.bat
├── initdb-report/             # готовая БД для стенда отчётов (разворачивается сама)
├── 2-start.bat
├── 2-start-report.bat         # стенд отчётов — вместо 2-start.bat, см. ниже
├── 3-run-emulator.bat
├── 4-stop.bat
└── 4-stop-report.bat          # остановка стенда отчётов
```

Порядок:

1. Распаковать архив целиком в любую папку без пробелов в пути (например `C:\wtctrl-smoke\`).
2. **`1-load-images.bat`** (двойной клик) — грузит все образы (`api`, `migrations`, `connector`, `emulator`,
   `postgres`, `mosquitto`) в Docker. Один раз, займёт пару минут.
3. Скопировать `.env.example` → `.env`, открыть блокнотом, заполнить:

   | Ключ | Что вписать |
   |---|---|
   | `DB_PASSWORD` | любой пароль (латиница/цифры, без пробелов) |
   | `BOOTSTRAP_ADMIN_PASSWORD` | пароль администратора Control (логин `admin`). Обязательно: ≥8 символов, заглавная + строчная + цифра + спецсимвол (напр. `Test-2026!`) — иначе админ не создастся |

4. **`2-start.bat`** — останавливает `api`, затем пересоздаёт `migrations`, `api`, `connector`; зависимости
   `postgres` и `mosquitto` запускаются автоматически. Порядок: PostgreSQL healthy → one-shot `migrations`
   → API; `connector` запускается независимо после старта Mosquitto. При ошибке миграций API остаётся
   остановленным. Эмулятор сюда **не входит** — он не фоновый сервис, см. §3.
5. Открыть в браузере **http://localhost:5000**, войти `admin` / пароль из `.env`.
6. В Control создать:
   - **Шаблон** ТПА с типом коннектора `usr-modbus` (Справочники → Шаблоны) — проще всего
     импортировать готовый `template-borche-emu.json` из пакета. В нём описаны сенсоры
     `MoldClosed`/`Injection`/`MoldOpened` (`boolean`) и `InjectionPosition` (`float`, мм):
     их `field` совпадает с `name` регистров, помеченных `"published": true` в
     `config-connector\machine-01.json`. Сенсоры, которых нет в шаблоне, Control отбрасывает молча,
     поэтому при добавлении регистра в конфиг коннектора добавляйте его и в шаблон,

   - **ТПА** по этому шаблону (Справочники → ТПА) — открыть его на редактирование и скопировать
     `Imm.Id` из поля **ID** (кнопка «Копировать»).
7. Вписать этот `Imm.Id` в `config-connector\machines.json`, поле `immId` (вместо
   `REPLACE_WITH_Imm.Id_FROM_CONTROL_UI`), сохранить.
8. Перезапустить коннектор, чтобы он подхватил файл:
   ```powershell
   docker compose -f docker-compose.test.yml restart connector
   ```
9. Проверить логи коннектора — должна быть строка вида
   `[Borche-Emu #1] polling emulator:15020 (unit 17) every 200ms`:
   ```powershell
   docker compose -f docker-compose.test.yml logs -f connector
   ```
   Пока эмулятор не запущен (см. §3) — коннектор будет писать ошибки подключения, это ожидаемо,
   он ретраит сам.

**Остановка:** `4-stop.bat` (данные БД сохраняются в Docker-volume; `docker compose ... down -v`
для полной очистки с нуля).

**Стенд отчётов.** Для проверки отчётов вместо `2-start.bat` запустите **`2-start-report.bat`**. Он поднимает отдельную БД `WintimeControl_ReportTest`, которая при первом запуске сама заполняется тестовыми данными (июнь–сентябрь 2026, 3 ТПА, ~0,9 млн циклов), ничего дополнительно выполнять не нужно. Порядок запуска: PostgreSQL healthy → one-shot `migrations` → API; `connector` запускается независимо после старта Mosquitto. Восстановление report-дампа завершается до запуска migrator благодаря healthcheck с `start_period: 15m`. Вход: `admin` / `Demo@123` (наладчики `adj1`, `adj2`, пароль тот же); `BOOTSTRAP_ADMIN_PASSWORD` на этом стенде не используется. Данные двух стендов хранятся в разных volume и друг другу не мешают, но одновременно стенды не запускаются (общие порты и имена контейнеров) — перед переключением остановите текущий. Остановка стенда отчётов — **`4-stop-report.bat`**. Вернуть исходные тестовые данные: `docker compose -f docker-compose.test-report.yml down -v`, затем снова `2-start-report.bat`.

**Диагностика миграций.** При ошибке миграций или запуска API остаётся остановленным; старый API после
ошибки не запускать. Для обычного стенда:

```powershell
docker compose -f docker-compose.test.yml ps -a
docker compose -f docker-compose.test.yml logs --tail 100 migrations
```

Для стенда отчётов:

```powershell
docker compose -f docker-compose.test-report.yml ps -a
docker compose -f docker-compose.test-report.yml logs --tail 100 migrations
```

## 2. Конфигурирование эмулятора+

Эмулятор — виртуальный modbus-slave: изображает шлюз USR-IO424, к которому подключается коннектор.
Два вида файлов конфигурации, оба монтируются volume'ом из `config-emulator/`:

### 2.1. Device-конфиг (`machine-01.json`) — какие регистры и на чём

Формат совпадает с конфигом самого коннектора (общая схема ядра `Wintime.Connector.UsrModbus.Core`) —
одна и та же структура `device` / `stateMachine` / `registers`, разница только в смысле поля
`device.host`:

- в конфиге **эмулятора** — адрес, на котором эмулятор **слушает** (`0.0.0.0` = все интерфейсы
  контейнера);
- в конфиге **коннектора** — адрес, куда коннектор **стучится** (в этом стенде — имя сервиса
  `emulator` в Docker-сети, см. §4).

Готовый пример уже лежит в пакете (`config-emulator/machine-01.json`) — четыре обязательные роли
(`moldClosed`/`injection`/`moldOpened`/`injectionPosition`), которые понимает автомат состояния
коннектора. Имя файла = алиас ТПА — должно совпадать с `connectorAlias` в `machines.json`
коннектора (§4). Чтобы добавить второй виртуальный ТПА — положить ещё один `<alias>.json` рядом,
с другим `device.port` (один процесс эмулятора поднимает столько slave-инстансов, сколько файлов
найдёт в каталоге при старте). Каждый ТПА эмулируется независимо — своя строка на главном экране,
свой пресет и своё состояние связи (§3). Конфиг с ошибкой или занятым портом пропускается —
предупреждение показывается перед главным экраном, остальные ТПА поднимаются.

Подробное описание всех полей (`scale`/`offset`/`invert`/`published` и т.д.) — `CONFIGURATION.md`
в репозитории коннектора (раздел 2); формат идентичен.

### 2.2. `emulator-ui.yaml` — диапазоны бегунков для ручного режима (опционально)

Нужен только для live-режима (§3.1) — задаёт, в каких пределах двигать аналоговые регистры
(положение шнека и т.п.) через ползунок в консоли. Без файла — дефолт (0–10 для сигналов в мВ,
иначе 0–100). Формат — по alias'у, внутри по имени регистра:

```yaml
machine-01:
  InjectionPosition:
    min: 0
    max: 10000   # сырые мВ, как в machine-01.json
```

### 2.3. Как создавать файлы пресетов (`.preset`) и макросов (`.mac`)

Пресет — сценарий: что и когда происходит на виртуальном станке, эмулятор проигрывает его
автоматически (не нужно руками щёлкать каждый шаг). Пресеты лежат в пакете в
`config-emulator\presets\` (макросы — в `config-emulator\presets\macros\`) и монтируются в
контейнер volume'ом, как и конфиги. Три готовых:

| Файл | Сценарий |
|---|---|
| `uc1_normal_auto.preset` | Наладка (3 цикла) → автоматический выпуск партии (495 деталей) без сбоев |
| `uc2_semi_auto.preset` | Полуавтомат: паузы между циклами 10–20с + редкие длинные паузы (проверка порога простоя) |
| `uc3_alarm.preset` | Авария: несколько нормальных циклов → форма не открывается → долгая пауза |

Этого обычно достаточно для smoke-теста (§3.2). Если нужен свой сценарий — правила формата:

**Пресет** (`*.preset`) — текстовый файл, одна инструкция на строку, `#` — комментарий. Время —
мс от начала воспроизведения (`AT <t_ms|+delta>`):

```text
# мой сценарий
AT +0       REPEAT CYCLE_NORMAL FROM "macros/cycle_normal" x3     # 3 цикла наладки
AT +2000    REPEAT CYCLE_NORMAL x50                                 # затем 50 автоматических
```

Доступные инструкции (всегда начинаются с `AT`):
- `SET <Регистр> <значение>` — мгновенно выставить значение (для дискретных — единственный способ).
- `RAMP <Регистр> <целевое_значение> <длительность_мс>` — плавно, линейно (только аналоговые).
- `DISCONNECT <длительность_мс>` — эмулятор рвёт TCP-соединение этого ТПА на это время и поднимает
  снова (имитация обрыва связи); пресет при этом идёт дальше. Повторный `DISCONNECT` во время обрыва
  продлевает его, но не укорачивает. Если ТПА выключен вручную, по истечении срока он остаётся
  `offline`, пока его не включат (§3).
- `REPEAT <макрос> [FROM "<путь_без_.mac>"] x<N>` — прогнать макрос N раз. Путь указывается только
  при первом упоминании макроса в файле, дальше — просто `REPEAT <макрос> xN`.

**Макрос** (`*.mac`, каталог `macros/` рядом с пресетами) — переиспользуемый блок с тем же
синтаксисом, но время в нём — от начала **своего** исполнения. Ограничения (осознанные, не баг):
макрос не может ссылаться на другой макрос; нет условий/переменных, кроме:
- `{n}` — номер текущего повторения (с 1), например `SET PartCounter {n}`;
- `rand(min_ms, max_ms)` — случайная задержка, только в позиции времени у `AT` (не в значении
  регистра) — для имитации «плавающих» пауз (как в `uc2_semi_auto.preset`).

Пример нормального цикла (`macros/cycle_normal.mac` — уже готов, можно взять за образец). Цикл
длится около 47 с, аналоговые значения — сырые мВ (в `machine-01.json` у них `scale` 1.0):
```text
# Начальное состояние: форма разомкнута, впрыска нет
AT 0     SET MoldClosed 0
AT 0     SET MoldOpened 1
AT 0     SET FwdEjectorReached 0
AT 0     SET BwdEjectorReached 0
AT 0     SET Injection 0
AT 0     SET MoldPosition 10000.0       # подвижная плита — 10000 мВ
AT 0     SET InjectionPosition 8000.0   # шнек — 8000 мВ
# Смыкание: через 1 с плита за 3 с идёт в 0
AT 1000  SET MoldOpened 0
AT 1000  RAMP MoldPosition 0.0 3000
AT 4000  SET MoldClosed 1
# Впрыск: шнек к 1500 мВ за 2 с, затем выдержка — до 1200 мВ (подушка) за 4 с
AT 7000  SET Injection 1
AT 7000  RAMP InjectionPosition 1500.0 2000
AT 9000  RAMP InjectionPosition 1200.0 4000
# Охлаждение: впрыск закончился, шнек отходит назад за 25 с
AT 13000 SET Injection 0
AT 13000 RAMP InjectionPosition 8000.0 25000
# Раскрытие формы: плита за 5 с в крайнее положение
AT 38000 SET MoldClosed 0
AT 38000 RAMP MoldPosition 10000.0 5000
AT 43000 SET MoldOpened 1
# Выталкиватель: вперёд и назад, импульсы по 400 мс
AT 45000 SET FwdEjectorReached 1
AT 45400 SET FwdEjectorReached 0
AT 47000 SET BwdEjectorReached 1
AT 47400 SET BwdEjectorReached 0
```

Импульс дискретного сигнала (SET 1, затем SET 0) и «дно» аналогового (подушка) должны держаться
не меньше ~3× `pollIntervalMs` из конфига. Иначе опрос коннектора может их пропустить.

Свой сценарий — положить `.preset` в `config-emulator\presets\`, `.mac` — в
`config-emulator\presets\macros\`. Пересборка образа не нужна. Список пресетов перечитывается при
каждом «Запустить пресет…», поэтому новый `.preset` виден без перезапуска эмулятора. Макросы
кэшируются при первом использовании: если изменили уже использованный `.mac`, перезапустите
эмулятор (`3-run-emulator.bat`).

Если строка пресета некорректна (например, нечисловое значение у аналогового `SET` или `RAMP` на
дискретный регистр), пресет на этом ТПА автоматически останавливается, а текст ошибки появляется на
экране ТПА. Остальные ТПА продолжают работать.

## 3. Работа с эмулятором во время тестирования

Эмулятор — **интерактивная консоль** (TUI), не фоновый сервис. Запускается отдельно от остального
стека:

```
3-run-emulator.bat
```
(эквивалент: `docker compose -f docker-compose.test.yml run --rm -it --use-aliases emulator --config-dir /app/config`)

Открывается **главный экран** — живая таблица всех поднятых ТПА (по одному на `*.json` в
`config-emulator/`), обновляется раз в секунду:

| Колонка | Что показывает |
|---|---|
| ТПА | имя файла конфига без расширения |
| Статус | имя выполняемого пресета или `idle` |
| Команда | последняя выполненная команда пресета (`SET MoldClosed 1`, `DISCONNECT 5000`…) или `-` |
| Сеть | `online` / `offline` — подключается ли коннектор к этому ТПА |

↑↓ — выбор ТПА, Enter — экран управления ТПА, Q — выход (`Ctrl+C` тоже работает).

Каждый ТПА эмулируется независимо: на разных ТПА могут одновременно идти разные пресеты.
Коннектор может опрашивать все поднятые ТПА в любой момент, какой бы экран ни был открыт.

**Экран ТПА** (Esc — назад) показывает только допустимые сейчас действия:

- **Запустить пресет…** — только если ТПА в `idle` (§3.2);
- **Ручное управление сигналами** — только в `idle` (§3.1);
- **Остановить пресет** — если пресет идёт; регистры остаются в текущем состоянии;
- **Выключить ТПА / Включить ТПА** — имитация выключения питания/обрыва кабеля: связь пропадает,
  пока ТПА не включат обратно. Если на ТПА идёт пресет, он продолжает выполняться «в темноте» —
  после включения коннектор застаёт ТПА в другой фазе цикла.

`offline` в колонке «Сеть» — если ТПА выключен вручную **или** идёт обрыв из команды `DISCONNECT`
пресета; одно другое не отменяет.

### 3.1. Ручное управление сигналами

Таблица всех регистров ТПА с live-обновлением, любая клавиша — выбрать регистр:
- **дискретный** (MoldClosed/Injection/MoldOpened) — переключается 0/1 мгновенно;
- **аналоговый** (InjectionPosition) — вводишь целевое число, эмулятор **плавно** доведёт до него
  значение (не скачком) в пределах диапазона из `emulator-ui.yaml`.

Для чего: ад-хок проверки — потыкать конкретный сигнал и посмотреть, как Control/дашборд реагирует
на конкретное состояние, без прогона целого сценария. Пока на ТПА идёт пресет, ручное управление
недоступно — сначала остановить пресет.

### 3.2. Пресеты

Выбираешь `.preset`-файл из списка → он начинает проигрываться **сам** в фоне, по заложенной в нём
временной шкале, а ты возвращаешься на экран ТПА. Паузы нет: «Остановить пресет» и запустить заново.
По окончании ТПА переходит в `idle`, регистры остаются в последнем состоянии — конечное состояние
задаёт сам пресет.

Параллельно смотри:
- в Docker-логах коннектора (`docker compose -f docker-compose.test.yml logs -f connector`) —
  идёт ли опрос, нет ли ошибок;
- в Control (http://localhost:5000) — карточка ТПА, дашборд, и после назначения задания — счётчик
  циклов, статус (Работа/Наладка/Простой/Авария).

**Рекомендуемый порядок smoke-теста:**
1. `uc1_normal_auto.preset` — базовый happy path: наладка → автовыпуск. Проверить, что циклы
   считаются, статус ТПА на дашборде переключается Наладка → Работа.
2. `uc2_semi_auto.preset` — паузы между циклами не должны ложно фиксироваться как простой (порог
   `seriesGapMs=30000` в тестовом конфиге), а длинная пауза — должна.
3. `uc3_alarm.preset` — авария (форма не открывается) → статус на дашборде должен показать простой/
   аварию, а не «работа».
4. «Выключить ТПА» на 10–60 секунд во время активного пресета, затем «Включить ТПА» — коннектор
   должен пережить обрыв и переподключиться (см. логи), Control — отразить потерю связи (статус
   «Нет связи») и восстановление.
5. Если конфигов несколько — разные пресеты на 2–3 ТПА одновременно, затем выключить один:
   остальные ТПА в Control работают без перерыва.

## 4. Конфигурирование коннектора UsrModbus

Коннектор — отдельный контейнер (`wintime/connector`), в стенде уже настроен переменными окружения
в `docker-compose.test.yml`:

| Переменная | Значение | Смысл |
|---|---|---|
| `Connector__Source` | `file` | Список ТПА берётся из локального файла, а не из Control API (проще для теста без API-ключа) |
| `Connector__SourcePath` | `config/machines.json` | Файл со списком ТПА |
| `Connector__ConfigDir` | `config` | Каталог с `<alias>.json` device-конфигами |
| `Mqtt__BrokerHost` | `mosquitto` | Имя сервиса брокера в той же Docker-сети |

Файлы, которые правит тестировщик — оба в `config-connector/`:

### 4.1. `machines.json` — список ТПА
```json
[ { "immId": "<Imm.Id из Control>", "immName": "Borche-Emu #1", "connectorAlias": "machine-01" } ]
```
`connectorAlias` обязан совпадать с именем файла device-конфига (без `.json`) и с именем файла в
`config-emulator/` — это и есть связка «какой ТПА в Control» ↔ «какой виртуальный станок эмулирует».

### 4.2. `machine-01.json` — параметры опроса и роли сигналов
Та же схема, что у эмулятора (§2.1), но `device.host` — **куда стучаться**: в этом стенде это
`emulator` (Docker резолвит имя сервиса сам, реальный IP не нужен). Роли регистров
(`moldClosed`/`injection`/`moldOpened`/`injectionPosition`) должны быть теми же, что задал эмулятор
для этого alias'а — иначе автомат коннектора не соберёт цикл. Полное описание всех полей и правил
валидации — `CONFIGURATION.md` в репозитории коннектора.

### 4.3. Применение изменений — только перезапуском
Коннектор читает оба файла **один раз при старте**, hot-reload нет. После любой правки:
```powershell
docker compose -f docker-compose.test.yml restart connector
```
Проверка, что подхватилось — по логам (`docker compose ... logs -f connector`):
- ✅ `[Borche-Emu #1] polling emulator:15020 (unit 17) every 200ms` — всё ок;
- ⚠️ `config 'machine-01.json' not found` — не совпало имя файла/alias;
- ⚠️ `No pollable machines configured` — ни один ТПА не прошёл валидацию, проверить оба файла.

## Troubleshooting

| Симптом | Проверить |
|---|---|
| `docker compose` не находится | Docker Desktop запущен? (см. §0) |
| Дашборд `localhost:5000` не открывается | `2-start.bat` отработал без ошибок? Порт 5000 свободен? `docker compose ... ps` — все контейнеры `Up`/`healthy`? |
| Коннектор не подключается к эмулятору | Эмулятор вообще запущен (`3-run-emulator.bat`)? `device.host` в `config-connector/machine-01.json` = `emulator`? Порты в обоих конфигах (`config-emulator`/`config-connector`) совпадают? |
| В Control ТПА не появляется / нет данных | `immId` в `machines.json` реально совпадает с `Imm.Id` из карточки ТПА в Control? Коннектор перезапущен после правки? |
| `cycleCounter`/статус не меняются при прогоне пресета | Смотри логи коннектора на ошибки Modbus; проверь, что роли регистров у эмулятора и коннектора совпадают (§4.2) |
| Эмулятор не реагирует на клавиши | Запущен через `run -it` (а не `up -d`)? Если открыт в обычном `cmd.exe` без ANSI — попробовать Windows Terminal |
| Нужно всё сбросить с нуля | `docker compose -f docker-compose.test.yml down -v` — удалит и БД, и MQTT-данные |
