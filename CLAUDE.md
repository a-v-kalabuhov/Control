# CLAUDE.md

## Что это
Wintime Control — веб-система управления производством для термопластавтоматов (ТПА):
сбор телеметрии по MQTT, производственные задания, отчёты.
Backend: ASP.NET Core 9 (`API` хостит SPA + `Core` + `Infrastructure` + `Shared`,
`Emulator` — автономный MQTT-эмулятор оборудования). Frontend: Vue 3 + Vite
(в проде встроен в `wwwroot` API). БД: PostgreSQL 16 (EF Core 9 + Npgsql).

## Команды (только неочевидное)
```powershell
dotnet run --project Wintime.Control.API        # API на https://localhost:7001
dotnet run --project Wintime.Control.Emulator   # MQTT-эмулятор оборудования

# Миграции — важны ОБА флага:
dotnet ef migrations add <Name> --project Wintime.Control.Infrastructure --startup-project Wintime.Control.API
dotnet ef database update       --project Wintime.Control.Infrastructure --startup-project Wintime.Control.API

docker-compose up   # PostgreSQL + Mosquitto + API

.\deploy\demo\deploy.ps1   # деплой демо-VPS (GHCR + ssh); ПЕРЕД ним поднять номер в VERSION (SemVer); -ResetDbOnly — сброс БД
```
Frontend: `cd Wintime-Control-Frontend && npm run dev` — порт 3000, проксирует `/api` → `https://localhost:5001`.

## Инварианты домена (нарушение = баг)

### Роль — только `User.Role`
Единственный источник правды по роли — `User.Role` (enum `UserRole`), одна роль на пользователя.
JWT-клейм `role` и все `[Authorize(Roles=…)]`/политики опираются на него.
Identity-роли (`AspNetRoles`/`AspNetUserRoles`) **не используются** — никогда не вызывай
`AddToRoleAsync`/`RemoveFromRolesAsync`/`GetRolesAsync` для прав доступа.
Первый админ в проде создаётся при старте из секрета `Bootstrap__AdminPassword`, не из исходников.
Политики: `AdminOnly`, `ManagerOrAdmin`, `AdjusterOrHigher` (Adjuster < Manager < Admin). См. ADR-0004.
`ShiftLead` (старший смены, PZP-32) вне этой иерархии и не входит в `AdjusterOrHigher`: только
отдельный контур `/shift-lead` и новые API `/api/shift-staffing` под собственной политикой
`ShiftLeadOrManagerOrAdmin`; `/api/shift-plan` — Manager/Admin. ShiftLead видит свою ближайшую
смену и историю, Manager/Admin — план и ближайшие позиции для изменения литейщиков. Общие API
заданий, произвольной истории ТПА и полного справочника персонала ShiftLead закрыты.
`Operator` (литейщик, PZP-30) вне этой иерархии: только дашборд и карточка ТПА (состояние,
хронология и задания текущей/последней смены) в режиме чтения; остальные страницы, мобильный UI и API закрыты.
Для карточки используются только `GET /api/dashboard/imm-card/{immId}` и
`GET /api/dashboard/task-results/{taskId}`: окно смены и допустимые задания определяет сервер
(`CurrentShiftWindow`), общие endpoint'ы заданий и истории `Operator` недоступны.
При создании сотрудника роль выбирается явно, без значения по умолчанию.

**Логин необязателен для любой роли.** Без логина пользователь остаётся в справочнике и отчётах,
не имеет пароля и не может войти; пустой `UserName` разрешает `OptionalLoginUserValidator`.
При включении входа пароль обязателен. Очистка логина удаляет хеш пароля и отзывает все
refresh-токены; уже выданный access-token действует до истечения (blacklist нет). Нельзя очистить
логин, деактивировать или понизить роль последнего активного администратора с доступом.

**Политика паролей — `SecuritySettings.AllowWeakPasswords`.** По умолчанию `false`: действуют
строгие правила Identity (минимум 8 символов, цифра, строчная и прописная буквы, спецсимвол).
При `true` `ConfigurablePasswordValidator` принимает любой непустой пароль. Настройка меняется
через `/api/settings/security` (Manager/Admin), действует только на последующее создание
пользователей и смену паролей; существующие пароли и вход не затрагиваются. Хранение — по ADR-0015.

### План смен и литейщики (PZP-32)

`ShiftPlanDay` существует только для заводской даты хотя бы с одним старшим; его
`ShiftPlanItem` — полный snapshot позиций графика с UTC-окном и `Position`, **без `ShiftId`**.
Остальные дни виртуально вычисляются из актуального графика. Первый старший материализует все
позиции дня, очистка последнего удаляет пустой день. График и план меняются в одной транзакции:
позиционно синхронизируются только `ShiftDate > factoryToday`, у оставшихся позиций сохраняются
`Id`, старшие и назначения; сохранённые текущие и прошлые дни неизменны.

Nearest/history вычисляются по серверному `now`, статус смены и background worker не нужны:
текущая — `StartAtUtc <= now < EndAtUtc`, ровно в `EndAtUtc` nearest переходит к следующей.
Завершённая незакрытая смена попадает в отдельный `pending`, не вытесняет nearest и остаётся
доступной для ручного ввода и исправления интервалов до закрытия. ShiftLead работает только с
собственными nearest/pending/history; Manager/Admin меняют литейщиков в ближайшей или завершённой
незакрытой смене. Старшего Manager/Admin назначают и заменяют в любой незакрытой смене: будущей,
текущей или завершённой. Только Closed делает старшего, состав и историю рапорта неизменяемыми.

`ShiftImmOperatorAssignment` — интервальный журнал: `AssignedAt`/`UnassignedAt` — фактические
границы внутри смены, а отдельные Created/Updated-поля — авторы и серверное время аудита. Начало по
умолчанию — `ShiftStart`, конец — `ShiftEnd` (`UnassignedAt = null`); снятие без явной границы —
`min(max(now, WorkStart), ShiftEnd)`. Снятие не удаляет строку, повторное назначение создаёт новую.
Назначение требует старшего, но не задания; на ТПА не более двух одновременных литейщиков, `Slot`
1/2 выбирает сервер на весь интервал, один Operator может работать на разных ТПА. Вместо partial
unique indexes временные exclusion constraints запрещают пересечения одного Slot и одного Operator
на `(ShiftPlanItemId, ImmId)`; `23P01`, serialization failure и deadlock → 409. Изменения
графика/старших/состава и закрытие сериализует `ShiftScheduleLock`; несовместимое новое окно
будущей позиции отклоняется и откатывает график и план вместе. `ActiveOperatorCount` — только
текущее отображение по `WorkStart <= now < WorkEnd`, не клиентский capacity gate; снятие по умолчанию
отправляет `{}`. Для PZP-31 `WorkStart = max(AssignedAt, StartAtUtc)` и
`WorkEnd = min(UnassignedAt ?? EndAtUtc, EndAtUtc)`. См. ADR-0027/0030.

### Сменный рапорт и закрытие смены (PZP-31)

Рапорт относится к `ShiftPlanItem` со старшим. До первого ручного сохранения `ShiftClosure` не
существует; в Draft хранятся только шесть ручных полей, а состав строк и вычисляемые значения —
динамическая read model. `Planned`/`Issued` отбираются по `PlannedStartAt` внутри смены, остальные
статусы — по `ShiftTaskWindow`/`TaskActivityWindow`; одно переходящее задание входит в несколько
рапортов без переноса сменных значений в общий итог задания.

Закрытие — единая транзакция под `ShiftScheduleLock`: сервер повторно читает исходники, валидирует
и сохраняет все строки и доли. До `StartAtUtc` закрывать нельзя; `FactEnd = min(ClosedAt, EndAtUtc)`,
досрочное закрытие требует `confirmEarlyClose: true`, ограничивает факт `ClosedAt`, но сохраняет
полный план смены. Автоматический выпуск и средний цикл — только успешные закрытые циклы задания по
`EndTime` в `[ShiftStart, FactEnd)`, без паузы; план ограничен остатком задания, расход включает
литник изделия за каждое смыкание. Рапорт никогда не меняет выпуск/брак или другие итоги `ShiftTask`.

Границы назначений образуют elementary intervals; соседние с одинаковым множеством Operator без
разрыва объединяются **до** округления, независимо от Slot и границ заданий. Один литейщик получает
весь выпуск, при двух Slot 1 на начало merged interval получает `⌈Q/2⌉`, второй — `⌊Q/2⌋`; нулевые
доли сохраняются. Ненулевой выпуск без литейщика — orphan, виден на timeline/в плане и блокирует
закрытие; сумма Shares + orphans = automatic для каждой строки. Любой посчитанный ретро-цикл в
`[ShiftStart, FactEnd)` распределяется или становится orphan даже вне `TaskActivityWindow.Activity`;
окно активности ограничивает только разрешённый состав нулевых долей и не отбрасывает положительный
выпуск. Ручной выпуск не распределяется и не сверяется с
автоматическим. Сырой `Offline` из `ImmStatusHistory` в окне активности строки с литейщиками требует
manual cycle/good/defect; отсутствие циклов само fallback не включает. При автоматическом или
ручном выпуске обязательны фактический вес и эффективная тарная единица.

Closed Entries/Shares — типизированный неизменяемый снимок; отдельных timeline-таблиц нет, шкала
восстанавливается из замороженного журнала назначений и Shares. Идентичность каждого оператора
timeline (включая оператора без Shares) разрешается по `OperatorId` в текущие `User.FullName` /
`EmployeeId` через журнал, без новых снимков и таблиц; текущие задания/циклы/статусы не читаются.
Текущие имена ShiftLead/ClosedBy допустимы. После закрытия только
Manager/Admin через correction с причиной меняет шесть ручных полей; typed values + JSON-аудит
сохраняются атомарно без reopen, ShiftLead не корректирует Closed. Blank PDF использует актуальный
черновик и очищает ручные поля, Closed PDF — только снимок. БД/API — UTC, UI — пояс браузера, PDF —
`ShiftPlanItem.TimeZoneId`; индикаторы closure/orphan в плане загружаются пакетно. См. ADR-0030/0031.

### `IsActive` — архивный флаг (мягкое удаление)

На `Imm`/`Mold`/`User` `IsActive` — вывод из оборота, **не** признак текущей активности. `false` → в архиве: скрыт из списков выбора, нельзя назначить в новое СЗ, история сохраняется и доступна в отчётах.
Никогда не удалять сущности физически — только `IsActive = false` (исключения: изделие и материал без ссылок, см. ниже). ТПА/ПФ с незавершёнными заданиями (`Planned`…`InProgress`) в архив перевести нельзя (PZP-07b).

### Тип изделия и изделие (`ProductType` → `Product`)

Двухуровневый каталог (ADR-0020, заменяет ADR-0007): ПФ → **тип** (`Mold.ProductTypeId`, 1:N;
nullable только у старых ПФ), заказ и задание → **изделие** (`ProductId` обязателен, `Order.ProductTypeId`
нет). Создать ПФ без типа, задание для ПФ без типа нельзя; тип ПФ с заданиями (любой статус) менять
нельзя — **исключение** `null → value`. Полный артикул `FullArticle` = `ТИП.ЧАСТЬ` (`ProductArticle`,
Trim + заглавные), уникален и не совпадает ни с одним артикулом типа (и наоборот); правка артикула типа
пересчитывает полные артикулы изделий в одной транзакции. У типа всегда ≥1 изделия (по умолчанию —
часть `0`, «По умолчанию»), у активного типа ≥1 активного. Изделие задания — из типа его ПФ, меняется
только в `Planned` без заказа; привязка к заказу — `task.ProductId == order.ProductId`
(`OrderTaskBinding`). Архивное изделие/тип выбрать нельзя, ссылки сохраняются. Физически удаляется
только изделие без заказов и заданий и не последнее у типа — исключение из мягкого
удаления (второе — материал, см. ниже).

### Заказчик (`ProductType.Company` / `Order.Customer`)

Заказчик — необязательный свободный текст у типа изделия и заказа (PZP-23), отдельной сущности нет.
Подсказки объединяют оба источника, но не ограничивают ввод. Карточка задания показывает
`Order.Customer`, если заказ привязан, иначе `ProductType.Company`; привязанный заказ без заказчика
не подставляет компанию типа. Расхождение значений — только предупреждение, не блокировка.

### Веса детали и литника, цикл литья (`Product` → `ShiftTask`)

`Product.PartWeightGrams` и `Product.RunnerWeightGrams` (неотрицательные), а также
`Product.PlannedInjectionCycleSeconds` (int?, > 0) — технологические параметры изделия
(PZP-24, ADR-0024/0029). `Mold.PartWeightGrams` и `Mold.RunnerWeightGrams` **не существуют**.
Полного цикла в изделии нет: он зависит от ТПА и обязателен только в задании.
`ShiftTask.PartWeightGrams` — копия веса детали изделия при создании и реальной смене изделия;
при создании/правке менеджер/админ может задать другое значение **в любом статусе**. При изменении
веса детали задания `ActualMaterialWeightGrams` пересчитывается заново по всем успешным циклам.
Правка `Product.PartWeightGrams` существующие задания не меняет. Вес литника в задание не копируется:
расчёты используют актуальный `Product.RunnerWeightGrams` изделия задания. При смене изделия задания
или изменении `Product.RunnerWeightGrams` накопленный расход затронутых заданий пересчитывается
по успешным закрытым циклам. Расход успешного цикла =
`ImmCycle.Cavities × ShiftTask(c.TaskId).PartWeightGrams + ShiftTask(c.TaskId).Product.RunnerWeightGrams`
(обработчик выпуска, ретро-привязка/откат, отчёты); цикл без задания расхода не даёт даже при
заполненном `MoldId`. Карточка ПФ справочно показывает вес каждого изделия типа и вес за смыкание
(деталь × `Product.Cavities ?? Mold.Cavities`); одинаковый вес и вес за смыкание всех изделий — одной строкой.

### Образец и тарная единица (PZP-29)

`Product.HasSample` (bool) — признак физического образца отдельного изделия; в списке изделий показывается
значком. `ProductType.PackagingUnit` (int?, > 0) — тарная единица по умолчанию для типа. При создании задания
она копируется в `ShiftTask.PackagingUnit`; менеджер/админ может изменить или очистить копию **в любом статусе**.
Правка типа существующие задания не меняет. Оба признака только справочные: не влияют на планирование и учёт
выпуска; тарная единица показывается в карточках, без отдельных колонок в таблицах.

### Материалы (`Material`)

Справочник сырья — одна таблица, тип `MaterialType` (`Plastic`/`Colorant`); в UI два справочника.
Тип задаётся при создании и **не меняется**. `Article` уникален среди **всех материалов** без учёта
регистра, независимо от типа. `(Type, Manufacturer, Name)` уникальны внутри типа без учёта регистра
(пустой производитель — одно значение; индекс на выражении в миграции `AddMaterials`). У красителя
обязателен цвет. Физически удаляется только
материал без ссылок (рецепты и их копии в заданиях) — второе исключение из мягкого удаления.

### Рецепт изделия и копия в задании (`ProductRecipeIngredient` / `ShiftTaskRecipeIngredient`)

Изделие хранит рецепт — состав сырья в процентах от массы (ADR-0023). В 100 % входят **только
пластики**; краситель в сумму не входит, сумма пластиков ≠ 100 % — предупреждение, не запрет.
Задание при создании получает **копию** рецепта; правка рецепта изделия задания не меняет.
Смена изделия в `Planned` перезаписывает копию рецептом нового изделия (то же изделие — no-op;
подтверждение при правленой копии — только фронт). Правила — `RecipeRules` (`Core/Policies`):
не больше 8 строк, процент 0.01..100 с двумя знаками, без повторов материала, непустой рецепт
обязан содержать пластик, новую строку с архивным материалом добавить нельзя (сохранённую —
можно). Тип ингредиента не хранится — это `Material.Type`. В копии задания меняется только
материал (`ShiftTask.ReplaceIngredient`, менеджер/админ, тот же тип, активный, **любой статус**);
`RecipeEdited` вычисляется как `MaterialId != OriginalMaterialId`. Наладчик и наблюдатель —
только чтение. Материал, на который ссылается рецепт (включая `OriginalMaterialId`), физически
не удаляется — только в архив.

### Импорт номенклатуры из XLSX (PZP-20)

`POST /api/nomenclature-import` (менеджер/админ, multipart XLSX A:L) без блокирующих ошибок применяет
файл сразу; иначе возвращает `ConfirmationRequired` без изменений БД. Повторная отправка с
`skipInvalidRows=true` пропускает ошибочные строки. Серверного preview/токена нет; CSV-отчёт строится
на frontend. Upsert — по `Mold.FormId` и `Product.FullArticle`, одной транзакцией, без удаления или
архивации отсутствующих записей; существующие задания и их рецепты не меняются. `Mold.Cavities` —
максимум по строкам ПФ, `Product.Cavities` — из собственной строки; колонка F — `Product.Comment`.
Один пластик = 100 %, краситель = указанный %. Два разных пластика через `;` — по 0 % с неблокирующим
замечанием: импорт пишет эти строки напрямую, ручное `RecipeRules.Validate` по-прежнему требует
0,01…100 %. Прочие неоднозначные рецепты не угадываются: изделие сохраняется с пустым рецептом и
замечанием. Материалы сопоставляются по типу/имени без учёта регистра, при неоднозначных производителях
создаётся материал без производителя. См. ADR-0026.

### Особенности пресс-формы

`Mold.HasMovingParts` (подвижные знаки), `Mold.RequiresRobot` и `Mold.RequiresConveyor` — справочные
bool-признаки (PZP-26), по умолчанию `false`. Они **не влияют** на планирование, совместимость и учёт выпуска;
фильтров по ним нет. Менеджер/админ меняет признаки только у активной ПФ; у архивной они доступны только для
чтения, API отклоняет их фактическое изменение (повторная передача неизменных значений не мешает правке
остальных полей). Список ПФ показывает в колонке «Особенности» значки только включённых признаков.

### Совместимые ТПА пресс-формы

`Mold.CompatibleImms` (таблица `MoldCompatibleImms`) — ручной список ТПА, на которые ставится ПФ.
**Пусто = совместимость не указана = любой ТПА.** Задание с ТПА вне непустого списка создать нельзя
(`MoldImmCompatibility.IsCompatible`, проверка в `CreateTask`). Архивный ТПА в список не добавить,
ранее привязанный остаётся. Существующие задания при правке списка не трогаются. См. ADR-0018.

### Плановое начало и выдача задания

`ShiftTask.PlannedDate` (`DateOnly`, обязательна) + `PlannedSetupStartTime` (`TimeOnly?`, по часам
завода). Эффективное начало — `PlannedTaskStart.Resolve` (без времени — начало первой смены),
**не хранится**, в API — `TaskDto.PlannedStartAt`. Менять план и наладчика можно только в
`Planned`/`Issued`. Выдать задание (`Issue`) без наладчика нельзя; в `Issued` наладчика можно
переназначить, но не снять. См. ADR-0014.

**Норматив наладки и буфер выпуска** (PZP-14) — снапшот умолчаний `PlanningDefaults` в задании:
`PlannedSetupMinutes`, `ReleaseBufferFixedMinutes` (минуты 0..1440), `ReleaseBufferPercent`
(целое 0..100, % от плановой длительности **выпуска**, без наладки). Смена умолчаний задания не
трогает. Норматив правится в `Planned`/`Issued`, буфер — до завершения выпуска
(`Planned`…`InProgress`). План задания (выпуск `⌈План/Гнёзда⌉ × PlannedFullCycleSeconds`, буфер,
`TaskDto.PlannedEndAt`) считает `TaskPlanCalculator`, **не хранится**; гнёзда — рабочая копия
`ShiftTask.Cavities` (это прогноз, не история). Настройки приложения — по ADR-0015.

### Задание длиннее смены — окно активности

Задание может идти через несколько смен и суток; смена/сутки — только ось отчётности (ADR-0016).
Окно активности `[SetupStartedAt, CompletedAt ?? ClosedAt ?? now)` (окно выпуска — от `StartedAt`)
— `TaskActivityWindow`. Задание относится к периоду **только** по пересечению окна
(`TaskActivityWindow.OverlapsPeriod` в EF), никогда по одной точке (`StartedAt`/`IssuedAt`).
План за период — нормативный (`TaskPeriodPlan`, сумма по дням ≤ плана задания (= min(P, норматив за весь выпуск)), не зависит от нарезки периода). Наладка относится к
периоду своего завершения. Статусы задания сравнивать только `==` (`Setup = 5` вне порядка ЖЦ).
`GET /api/tasks`: фильтры `issued*`/`planned*`/`active*` через И; без `status` архив скрыт, кроме `active*`.

### Конфликты плана — подсвечивают, не блокируют

Ресурсы — ТПА и ПФ (на любом ТПА); участвуют `Planned`/`Issued`/`Setup`/`InProgress`. Отрезки —
`TaskOccupancy` (план с буфером до начала; дальше факт + прогноз конца выпуска без буфера по стадиям,
задержка 10 мин — константа), пары — `PlanConflictDetector`: пересечение > `PlanningDefaults.ConflictThresholdMinutes`
(20 мин, не снапшот). Вид: только план — конфликт плана, иначе — конфликт отклонения. Не хранятся, считает
`IPlanConflictService` (`GET /api/planning/conflicts`). Конфликты плана не блокируют сохранение, выдачу и переходы
статусов; старт наладки с ПФ, занятой на другом ТПА, — 409 `moldBusy` + `confirmMoldBusy`. Пересекающиеся планы
на одном ТПА допустимы, но одновременно выполняться (`Setup`/`InProgress`) там может только одно задание:
это гарантирует partial unique index `UX_ShiftTasks_ImmId_Active`; параллельный `/start` проигравшего получает 400.
Это ограничение факта выполнения, а не блокировка планового конфликта. ТПА/ПФ с незавершёнными заданиями в
архив не переводятся. См. ADR-0022.

### Гнёздность — максимум ПФ, умолчание изделия, рабочая копия задания (PZP-36)

`Mold.Cavities` (> 0) — **максимум** гнёзд оснастки, не гарантированный выпуск цикла: наладчик может
заглушить часть гнёзд. `Product.Cavities` (int?, > 0) — необязательное технологическое умолчание;
`null` = максимум выбранной ПФ. У типа с несколькими активными ПФ умолчание не превышает минимальный
из их максимумов; создание/уменьшение/возврат ПФ проверяется против умолчаний всех изделий типа.
`ShiftTask.Cavities` (> 0) — обязательная рабочая копия `Product.Cavities ?? Mold.Cavities`.
Менеджер/админ может выбрать значение **в любом статусе** от 1 до `Mold.Cavities` (после уменьшения
можно вернуть любое значение в тех же границах). При реальной смене изделия в `Planned` копия сначала
перезаписывается умолчанием нового изделия, затем — явным значением запроса. Правка изделия/ПФ существующие
задания не меняет; неизменное значение старого задания допустимо выше нового умолчания изделия, но не выше
текущего максимума выбранной ПФ. План, конфликты, нормативный план и прогноз используют `ShiftTask.Cavities`;
вес за смыкание — `PartWeightGrams × (Product.Cavities ?? Mold.Cavities)`. См. ADR-0028 (заменяет ADR-0025).

### `Cavities` — снапшот, не текущее значение

`ImmCycle.Cavities` — снапшот `ShiftTask.Cavities` на момент записи цикла (включая ретро-привязку);
уже открытая строка при правке задания не переписывается. Выпуск и расход истории считать только по
снапшотам циклов: изменение рабочей гнёздовости не пересчитывает старые циклы, `ActualQuantity` или
`ActualMaterialWeightGrams`. Fallback для старых записей (= 0) — `Mold.Cavities`.
(Будущее — `ImmCycle.MoldVersionId` → `MoldVersion`, см. ADR.)

### Рабочий режим — параметр задания, не телеметрия

`ShiftTask.WorkMode` (`Auto`/`SemiAuto`) — как технолог назначил работать; ручного режима
нет, он же наладка. Не путать с `ImmMode` (`auto`/`manual`/`idle`/`alarm`) — это состояние
ТПА из телеметрии. Режим влияет только на учёт выпуска: в полуавтомате условие
`mode == auto` в `ShouldCountOutput` снято, потому что ТПА между циклами ждёт оператора.
Цикл засчитывается только если закрыт коннектором (`endedByCounter`, под контрактом v2 всегда
`true` — цикл закрывается исключительно по `lastCycle`, старой развилки "закрыт счётчиком vs
закрыт сменой режима" из MQTT-контракта v1 больше нет; параметр в `CompletedCycle` сохранён
для формы, не за логику).
На детект простоя режим **не влияет** — порог единый и высокий (900 с), см. ADR-0010.
Эталон полного цикла `PlannedFullCycleSeconds` (обязателен) хранится только в задании;
эталон цикла литья по умолчанию — в `Product.PlannedInjectionCycleSeconds`, а его рабочая копия —
в задании (PZP-24). Оба эталона задания используются для планирования и аналитики.

### Цикл литья — коннектор детектирует, Control открывает/закрывает одну строку

Коннектор сам ведёт автомат состояний цикла литья и публикует в каждом MQTT-сообщении
структурированные блоки `currentCycle`/`lastCycle` (контракт v2, ADR-0012, отменяет
ADR-0011). Control не детектирует границы — `CycleProcessingHandler` открывает
`ImmCycle` (`EndTime = null`) по `currentCycle`, закрывает (`EndTime`,
`DurationSeconds`, `InjectionDurationMs`, `Cushion`) по совпавшему `lastCycle`.
Идентичность цикла — составной ключ `(CycleNumber, StartTime)`, **не** один номер:
счётчик коннектора легитимно обнуляется между сериями выпуска без разрыва связи,
поэтому номер может повторяться для разных физических циклов. Открытые
(`EndTime = null`) циклы уже учитываются в износе формы (`Cavities`), но исключены из
агрегатов длительности/среднего цикла (`ReportService`) до закрытия.
`ImmCycle.PauseDurationMs` — пауза перед циклом (от раскрытия предыдущего цикла ТПА), пишет Control
при создании строки (`CyclePause`); `null` — нет предыдущего, предыдущий цикл ещё открыт, пауза ≥ порога простоя или в паузе был
статус кроме `Auto`/`Offline`. Темп и прогноз окончания выпуска на плитке ТПА — `ReleaseForecast`
по среднему полному периоду (`AVG(DurationSeconds) + AVG(PauseDurationMs)` по закрытым циклам
задания, < 3 циклов — эталон), не хранятся; наладка и простои в прогноз не входят. См. ADR-0017.

### Статусы ТПА

Статус — строка по MQTT, хранится в `ImmStatusHistory.Status`, кешируется в `IImmStatusCache`.
Единственная точка записи — `IImmStatusService.UpdateStatusAsync` (обновляет и БД, и кеш):
- `Auto` — работа по программе · `Manual` — наладка · `Idle` — включён, простой · `Alarm` — авария · `Offline` — нет MQTT
Дашборд показывает **эффективное состояние** — чистая функция `ImmEffectiveStatus.Resolve`
(`Core/Policies`), **не хранится**, считается на лету; история — `EffectiveStatusTimeline.Build`.
6 значений: `Production` (Работа) · `Setup` (Наладка) · `Downtime` (Простой) ·
`Unplanned` (Работа без задания) · `NoTask` (Без задания) · `Offline` (Нет связи).
Сырой `Offline` → **всегда** `Offline` («Нет связи»): доминирует над наладкой, простоем (авто и ручным)
и порогом — нет данных, значит нет ни «работы», ни «простоя». Авто-простой по `Offline` не открывается;
открытый до обрыва — не закрывается. См. ADR-0021.
Палитра/подписи на фронте — `src/constants/effectiveStatus.js`.
Дизайн: `docs/superpowers/specs/2026-06-24-effective-status-dashboard-design.md`.

Все отчёты по ТПА («Картина рабочего дня», «Производительность оборудования») и карточка ТПА показывают
**эффективное состояние** (одна палитра `effectiveStatus.js`); сырой режим — только `ImmStatusHistory`/телеметрия.

## Правила кода

### DateTime → PostgreSQL (Npgsql)

Все `DateTime` в EF-запросах к Postgres обязаны иметь `Kind=Utc` (колонки `timestamptz`, иначе
исключение `Cannot write DateTime with Kind=Unspecified`). ASP.NET биндит даты из query string как
`Unspecified`; `.Date`/`.AddDays` сохраняют Kind. Конвертируй сразу после получения параметра:
```csharp
var dateUtc = DateTime.SpecifyKind(date.Date, DateTimeKind.Utc); // AddDays/AddMinutes от Utc безопасны
```
Никогда не передавай `date.Date` в `.Where()` напрямую — только через `SpecifyKind`-переменную.

## Процесс работы (superpowers)
`superpowers:brainstorming` и его цепочка (`writing-plans` → `subagent-driven-development`,
фазы по сессиям) запускаются **только по прямому указанию пользователя**; правило «1% → вызывай
skill» из `using-superpowers` на них не распространяется. Порядок:
1. Короткое обсуждение задачи. Claude называет свою оценку трудоёмкости и признаки сложности:
   новая сущность или миграция, новый endpoint/контракт API, изменение инварианта из этого файла.
   Решает пользователь.
2. Без указания — план нумерованным списком в чате (без файлов спеки и плана), затем реализация.
3. Указание «brainstorming» — полный процесс superpowers.

Остальные skills (TDD, systematic-debugging, verification-before-completion, code review) — как обычно.

## ADR
Архитектурные решения — в `docs/adr/` (формат MADR, см. `docs/adr/README.md`).
ADR хранят *почему* решили так и какие альтернативы отвергли; CLAUDE.md — правило-итог (*как*); git — *что* изменилось.
Доменный словарь и описание сущностей (*что это за понятие*) — `docs/domain/` (необязательно к загрузке).
